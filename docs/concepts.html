Glidex

Concepts

This page explains the objects Glidex manages and the words the rest of these docs use for them. Each entry links to the page with the details.

Control plane

The control plane (glidex-control-plane) is the service that holds the state of everything (VMs, disks, images, networks, projects, users) and acts on it: it starts hypervisors, creates disks and asks the host’s network helper to set up networks. It serves:

  • the REST API and the RPC API (gRPC, gRPC-Web and Connect) on HTTPS port 8841, and on a local Unix socket for gxctl on the host;
  • the console of every VM.

The web UI (glidex-ui, HTTPS port 5173) and gxctl are clients of that API: anything you do in one you can do in the other. See the API reference and the gxctl reference.

The control plane doesn’t sit between a VM and its hypervisor: with the installer’s systemd units, each VM runs in its own unit, so VMs keep running when the control plane restarts or is upgraded.

Nodes, servers and agents

A node is a host that runs VMs. A standalone host is a single node.

Several hosts can form a cluster. Each node has a role:

  • A server keeps a copy of the cluster’s state in a replicated (Raft) store and answers the API. Run one, or three or more for a quorum that survives the loss of a server.
  • An agent only runs VMs. It has no API of its own; opening its web UI takes you to a server’s, at that agent’s Host page.

Each node has a Host page in the web UI (/hosts/<node>): its capacity, topology, networking, VMs, disks, roles and operations, reachable from any server. Servers publish their web UI’s address (cluster.ui_url, or the one glidex-ui reports), and agents send browsers there. See Host pages.

Nodes join with a one-time join token and talk to each other over mutual TLS. A scheduler picks the node for each new VM, and explains its choice. A node can be drained (no new VMs are placed on it), removed, and rejoined. See Clusters.

A VM stays on the node it was placed on. An administrator can place a stopped VM, or a lost one whose node was forgotten, again on another node, when its disks can go there (see Placing a stopped or lost VM again).

Tenants and projects

A project is where VMs, disks, guest credentials and project networks live. Each of these belongs to exactly one project. A project has members with roles, and optional quotas: limits on VMs, running VMs, vCPUs, memory, disk, networks and routers.

Every install starts with a project named default. In gxctl, --project <p> picks a project for one command and project use <p> sets your default; in the web UI, the Project selector in the header does both. See Projects.

A tenant is the organization that owns projects. A standalone host has an operator tenant admin, which runs the host, and a tenant default, which holds the default project. Most single-site installs don’t need more than that.

The directory is where users, teams, login connectors and tenants are kept; a control plane hosts one, shared by every server of a cluster. The web UI’s Directory page shows it.

Virtual machines

A VM has a name, a project, a hypervisor, vCPUs and memory, a boot disk, zero or more data disks, network interfaces (one per network it attaches to), optional PCI devices, and an optional guest credential.

Glidex separates what you ask for from what it last saw:

  • The desired state (the spec) is what you want: the VM’s configuration, and whether it should be running, paused or stopped. Start, stop, pause and edits change only this, and return at once.

  • The state (the status) is what the control plane last observed:

    StateMeaning
    createdNever started.
    startingThe hypervisor is being launched.
    runningThe guest is running.
    pausedThe guest is paused.
    stoppingA stop is in progress.
    stoppedNot running.
    failedIt couldn’t be started, or it crashed.
    unknownThe control plane can’t tell whether its hypervisor is still running.

A controller keeps working until the state matches the desired state. While it does, the web UI shows both (for example, Stopped → Running) and gxctl start waits for it. Some changes only apply at the next start; the VM then says a restart is required.

Two settings say what happens when the VM stops on its own:

  • Restart policy (If It Crashes in the web UI): restart it with backoff (the default) or leave it stopped.
  • On host boot (After a Host Reboot): start it again if it was running, or leave it stopped.

Stopping is either graceful (press the guest’s power button, wait, then stop) or immediate. Each VM keeps a short list of events: starts, exits, restarts. See Virtual machines.

A VM boots in one of two ways, fixed when it is created:

  • Firmware boot (the default): UEFI firmware runs the boot loader on the root disk, which picks the kernel.
  • Direct kernel boot: the hypervisor loads a kernel, an optional initramfs (the small root filesystem a kernel starts from before it mounts the real one) and a command line that Glidex hands it. With following the guest’s kernel (kernel_from_disk), Glidex takes the kernel the guest installed out of its disk before a start, so it boots next time.

See Kernel boot.

Hypervisors

Each VM runs on one hypervisor:

  • Cloud Hypervisor (cloudhypervisor in gxctl, HYPERVISOR_CLOUD_HYPERVISOR in the API), the default.
  • QEMU (qemu in gxctl, HYPERVISOR_QEMU in the API).

Both support the same features in Glidex: UEFI boot of cloud images, direct kernel boot, networks, disks, PCI passthrough (VFIO), pause and resume, and graceful shutdown. You pick the hypervisor when you create the VM.

Images and firmware images

An image is a read-only file disks are made from. Images belong to the host (or cluster), not to a project: everyone can use them, and administrators with the image role pull and delete them.

  • A cloud image is a bootable distribution disk image (qcow2 or raw). Pull one from the built-in catalog by key (for example ubuntu-26.04, debian-13, fedora-cloud) or from an HTTPS URL. Catalog images are checked against their published SHA-256; an image from a URL without a checksum is kept but marked unverified.

  • A firmware image is the UEFI firmware a VM boots through, built for one hypervisor: cloudhv-edk2 (CLOUDHV.fd) for Cloud Hypervisor, ovmf for QEMU. A new VM uses the newest firmware image for its hypervisor unless you choose another.

  • A kernel image is a kernel, an optional initramfs and a default command line, for direct kernel boot. Pulling a catalog image also makes one from it by kernel extraction: Glidex reads the image’s /boot inside a small VM, never on the host. A kernel taken from a VM’s own disk is a VM-owned kernel image, deleted once no VM uses it.

An image is downloading, verifying, extracting (a kernel image), ready, failed or missing (its file is gone). See Images and disks and Kernel boot.

Disks

A disk is a virtual disk in a project. It is attached to at most one VM at a time, as its boot (root) disk or as a data disk. A disk is:

  • blank, of a size you choose, or
  • made from an image: either linked (thin: a qcow2 overlay on the image, so it takes space only for what the VM writes) or a full copy.

When you create a VM from an image, Glidex makes a linked root disk for it, grows it to the size you ask for, and extends the guest’s root partition to fill it. That disk belongs to the VM and is deleted with it unless you keep it. Disks can be resized; a resize of a disk that is in use is held until it can be applied.

Datastores

A datastore is where disks live; every disk is on one. See Datastores.

  • local, built in: each node’s own disk directory. The default for new disks until an administrator picks another.
  • A node-local datastore is a directory each node has its own of. A disk on it, as on local, is bound to one node, and so is its VM.
  • A shared datastore is one filesystem every node mounts (NFS, CephFS). Its disks are bound to no node: their VM can be placed on any node that reaches it. A marker file in its directory proves to each node that it sees the right filesystem; the disk’s worker is the node that works on its file; a volume lock keeps two nodes from using one disk at once.
  • An LVM-thin datastore (driver lvm) keeps disks as raw thin volumes carved from a thin pool in a volume group on each node; it is node-local. A root helper, glidex-stord, manages the volumes, and only in the volume groups an administrator allows. Each node keeps an image volume, a read-only copy of an image, that linked disks there are thin snapshots of. A full thin pool stalls the guests. See LVM-thin.

A disk no running VM uses can move to another datastore. A linked disk is then rebased on the image’s copy there, or flattened into a standalone copy.

Host resources

Glidex knows each host’s host topology: its NUMA nodes, cores, hugepages and PCIe tree. See Host resources.

  • A NUMA policy keeps a VM’s memory, vCPUs and devices on one NUMA node (a socket, or part of one): preferred, or strict. The aligned policy instead splits the VM over exactly its devices’ NUMA nodes, one guest NUMA node each.
  • Dedicated CPUs give each vCPU a host CPU no other VM uses.
  • Hugepages back guest memory with large pages (2M or 1G), counted per node; a VM’s page_kib says what it got.
  • A device pool is a named set of like devices (GPUs, NICs) a VM asks for by count. A tenant pool is a tenant’s share of one, split among its projects. A pool’s per-device sizing (per_device) is the vCPUs and memory a VM gets with each device.
  • A GPU request (gpus) asks for N GPUs from a pool: the VM gets the aligned NUMA policy and, unless it sizes itself, the pool’s per-device sizing. See GPU requests.
  • Boot devices are the devices the installer’s --vfio-devices and --sriov bind to vfio-pci, or give VFs, at every boot (glidex-vfio-boot.service). See Keep it across reboots.
  • A device is ready when it can be passed through as it is, and cordoned when an administrator keeps it from new VMs.

Guest credentials

A guest credential is a login for inside VMs: a username with a password, SSH public keys, or both. Credentials belong to a project. Glidex stores only a hash of the password.

When you create a VM with a credential, Glidex generates a cloud-init seed that creates that user in the guest. It is applied on the VM’s first boot only: later changes to the credential don’t reach VMs that already booted. You can also give your own cloud-init seed instead. See Guest credentials.

Networks

A network connects VM interfaces. Its mode is one of:

  • NAT: a private subnet with DHCP; VMs reach the outside through the host (masquerade).
  • Isolated: VMs on it reach each other and nothing else.
  • Bridged: VMs sit on an existing network of the host (in a cluster, a provider network on a physical network).

A host network is created by an administrator and offered to the projects allowed to use it. A project network belongs to a project, and its owner can share it with other projects.

On a standalone host, networks are Open vSwitch bridges on that host. In a cluster with OVN enabled, a cluster network spans every node. A VM’s interface is a tap device (the default) or a vhost-user port (with OVS-DPDK).

A network is pending, ready or degraded, or reports that the host’s network helper is unavailable. See Networks and Host networking.

Console

Every VM has one serial console. Any number of clients (browser tabs, gxctl connect) can share it at once, and everything it prints is logged to disk, so you can read what happened before you connected. See The console.

Users, teams and roles

A user is a person known to Glidex. Users log in through a login connector: local accounts (PAM), or single sign-on through an OIDC provider, Google or JumpCloud. On the host itself, gxctl identifies you by your Unix account. A user can have several sign-in methods (a local password and a Google account, say), each giving the same roles. A passkey is one more: a WebAuthn credential (the device’s fingerprint, face or PIN, or a security key) that signs in to the web UI and counts as multi-factor. Passkeys belong to the passkeys’ domain (auth.passkeys.rp_id) and work on every web UI name under it. See Passkeys. A team is a group of users; teams can mirror Unix or identity-provider groups.

A connector can also be provisioned: the identity provider (IdP) creates, changes and removes its users and groups in Glidex over SCIM, and only those users can log in through it. Such users and teams are managed by the connector: their names, and whether a user is enabled, are changed at the IdP, not in Glidex.

A Google Workspace connector can pull instead (directory sync): Glidex reads the members of the Google groups you name, as a Google service account whose key you give it, every 15 minutes, and the users it brings in are managed the same way. A safety stop holds a run that would disable too many users until an administrator confirms it. See Directory sync from Google Workspace.

An invitation is a one-time link that lets one email address into a tenant, with a role, through one connector, even when that connector doesn’t create users by itself. It expires, after 7 days by default.

A role binding gives a user, team or token a role on a resource. Project roles, each including the one before it:

RoleCan
viewerSee the project, its VMs, disks and usage.
operatorAlso start, stop and pause VMs, and use their consoles.
editorAlso create, change and delete VMs and disks, manage guest credentials, and attach networks.
ownerAlso manage members, and manage and share project networks.

Host roles cover the host or cluster itself: auditor (read-only, including the audit log), image-admin (images), net-admin (host networks and PCI devices), and system-admin (everything). In a cluster, auditor and net-admin can also be given on one host only. Tenant roles (tenant-admin, tenant-auditor) cover one tenant and its projects. See Access control.

Tokens

An API token lets a script or another machine call the API. A token has a name and always expires: after a default lifetime, or after the number of days you choose, up to a limit the site sets.

  • A personal token acts as you. It can be narrowed to some of your roles.
  • A service-account token belongs to a project and has only the roles it is given.

The secret is shown once, when you create the token. Create tokens with gxctl token create or on the web UI’s Tokens page; revoke them the same way. See Logging in.

A workload federation lets CI jobs and other workloads (GitHub Actions, GitLab CI, Kubernetes) use the API without a stored token. A tenant trusts their issuer and maps tokens whose claims match a rule to one of its service accounts; a job exchanges its platform’s token for a short-lived Glidex token acting as that service account. See Workload federation.

Policies and the audit log

Every request is authorized by Cedar policies: built-in ones that implement the roles above, plus optional site policies an administrator adds to allow or forbid more. Some sensitive operations also need a recent login. Changes, and refused requests, are recorded in the audit log: who did what, to what, and with what result. See Access control.

Usage

Glidex meters what each VM, disk and network uses (CPU, memory, disk I/O and network traffic) and reports it per project, VM, disk, NIC or network, by hour, day or billing month. See Usage.
