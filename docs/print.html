Glidex

Introduction

Glidex is a control plane for KVM virtual machines. It runs VMs on Cloud Hypervisor (the default) or QEMU, and you drive it from a web UI, the gxctl CLI, or its REST and RPC APIs. It runs on a single Linux host, or on many hosts joined into one cluster.

Features

  • Two hypervisors, one feature set. Cloud Hypervisor and QEMU both boot distribution cloud images through UEFI firmware, take networks, disks and PCI (VFIO) devices, and support pause, resume and graceful shutdown.
  • Images and disks. Pull checksum-verified cloud images (Ubuntu, Debian, Fedora) from a built-in catalog, or any image from an HTTPS URL. Each VM gets a thin root disk linked to its image, grown together with its root partition.
  • Guest logins. Store a username with a password and/or SSH keys once, and pick it when you create a VM. Glidex puts it into a cloud-init seed it generates for the VM.
  • Networking. NAT networks with DHCP, isolated networks, and bridged networks on the host’s own LAN, built on Open vSwitch. Uplinks can use the kernel, AF_XDP or DPDK; VM ports are tap or vhost-user.
  • Console. Each VM’s serial console in the browser or in gxctl, shared by any number of clients and logged to disk.
  • Projects and access control. Projects with members and quotas, roles and teams, API tokens, login with local accounts (PAM) or OIDC, Cedar policies, and an audit log.
  • Usage. Metered CPU, memory, disk and network use, per project, VM, disk or network, by hour, day or billing month.
  • Clustering. Many hosts act as one. Servers keep the cluster’s state in a replicated store; agents only run VMs. Nodes join with a one-time token over mutual TLS, a scheduler places VMs and explains its choice, and nodes can be drained, removed and rejoined. Every node serves the web UI.
  • Cluster networks. With OVN, networks span every node, NAT traffic leaves through shared gateway nodes, and projects can have their own routers.

Quick start

This page takes one Linux host from nothing to a running VM: install Glidex, log in, create a NAT network, pull a cloud image, add a login for the guest, then create, start, use and stop a VM. Each step shows gxctl and, where it helps, the web UI.

For more choices at any step, see the User guide and the Operator guide.

Requirements

  • Linux on x86_64 or aarch64, with KVM enabled (/dev/kvm exists).
  • A package manager the installer knows: apt-get, dnf/yum or pacman.
  • An account with sudo rights. The installer asks for your sudo password and nothing else.
  • git, and a Rust toolchain to run the installer from source (for example from rustup.rs). The installer then installs or updates everything else, including Rust itself.
  • Internet access, to download packages, the hypervisors and images.

Check KVM first:

ls -l /dev/kvm

If it’s missing, enable virtualization in the firmware settings and load the module (sudo modprobe kvm_intel or sudo modprobe kvm_amd).

1. Install

git clone https://github.com/CMKL-APEX/glidex.git && cd glidex
cargo run -p glidex-install

The installer installs what is missing and updates what is outdated: system packages, Cloud Hypervisor and its UEFI firmware, QEMU with OVMF, Open vSwitch for VM networking, and the Glidex binaries and web UI. It sets up these systemd services:

  • glidex-control-plane: the API, running as the glidex system user.
  • glidex-ui: the web UI, running as glidex-ui.
  • glidex-authd: checks local account passwords (PAM) for the web UI.

When it finishes, it prints a summary like this:

glidex runs as systemd services (control plane as 'glidex', web UI as 'glidex-ui'):
     web UI:  https://host.example.org:5173
     API:     /run/glidex-cp/api.sock (members of glidex-users), https://host.example.org:8841 (tokens)
     web UI certificate SHA-256: 3A:7F:…:C2
     API certificate SHA-256: 91:0B:…:5E

Keep the two certificate fingerprints: you check them in step 3. The installer doesn’t open any firewall ports; if you’ll use the web UI from another machine, allow TCP 5173 (and 8841 for the API) yourself.

Re-run cargo run -p glidex-install at any time to update. See Installation for its options.

2. Log out and back in

The installer adds you to two groups:

  • glidex-users: lets you use gxctl on this host and log in to the web UI with your account’s password.
  • glidex-admin: makes you an administrator of this Glidex host, and owner of its default project.

Group changes apply to new logins only, so log out and back in (or reconnect your SSH session). Then check:

id -nG            # lists glidex-users and glidex-admin
gxctl whoami

On the host, gxctl talks to the control plane over its Unix socket (/run/glidex-cp/api.sock) and identifies you by your Unix account: there is no separate login.

gxctl with no arguments starts an interactive shell (gxctl>, with Tab completion and help). With arguments it runs one command and exits. This page uses the one-command form; inside the shell, type the same words without gxctl.

3. Open the web UI

Print its address:

gxctl ui

Open https://<host>:5173 in a browser. Unless an administrator configured a certificate, the UI uses a self-signed one, so the browser warns you. Before you accept the warning, open the certificate details in the browser and compare its SHA-256 fingerprint with the web UI certificate SHA-256 line the installer printed. Accept only if they match.

If you no longer have the installer’s output, print the fingerprint on the host:

sudo openssl x509 -in /var/lib/glidex-ui/tls/ui.crt -noout -fingerprint -sha256

Sign in with your Unix username and password. The header shows the pages you can use (VMs, Images, Disks, Credentials, Networking, Projects and, as an administrator, more) and a Project selector; leave it on default.

To replace the self-signed certificates, see TLS.

4. Create a NAT network

Glidex creates no network by itself. Create a NAT network: VMs on it get an address by DHCP and reach the outside through the host. Name it default and the VM forms preselect it.

gxctl network-add default

network-add makes a NAT network unless you pass --isolated or --bridged <bridge>. Its subnet is the first free /24 in 10.88.0.0/16 unless you pass --subnet <cidr>. Only your default project (here, default) may use it until you grant it to others.

In the web UI: Networking → Add Network, enter the name default, keep Mode at NAT (DHCP + masquerade), and click Create.

More in Networks and Host networking.

5. Pull a cloud image

List the catalog, then pull an image. gxctl follows the download until the image is verified and ready.

gxctl image catalog
gxctl image pull ubuntu-26.04

The catalog also lists UEFI firmware. The control plane imports the firmware the installer set up (cloudhv-edk2 for Cloud Hypervisor, ovmf for QEMU) at its first start, so you don’t need to pull it. gxctl image list shows both.

In the web UI: Images → Cloud image catalog, then Pull on the image you want.

More in Images and disks.

6. Add a guest credential

A credential is a username with a password, SSH public keys, or both. Glidex sets it up in the guest when the VM first boots. Without one, you can’t log in to the VM.

gxctl credential-add

It asks for a username (default: yours), a password (twice; leave it empty for SSH-key-only login), and SSH public key files (default: your ~/.ssh/*.pub). Give it a password if you want to log in on the console in step 8.

In the web UI: Credentials → Add Credential, fill in Username, a password and/or SSH public keys (optional), and click Add.

More in Guest credentials.

7. Create and start a VM

gxctl create asks its questions one by one; press Enter to take the default shown in brackets. For an Ubuntu VM on Cloud Hypervisor:

$ gxctl create
VM name: my-vm
vCPU count [1]: 2
Memory (MiB) [512]: 2048
Hypervisor [cloudhypervisor/qemu] (default: cloudhypervisor):
UEFI firmware [...] [cloudhv-edk2]:
Boot disk from [image/disk/path] [image]:
Image (ubuntu-26.04) [ubuntu-26.04]:
Root disk size in GiB [10]: 20
Data disks (optional, comma-separated disk names):
cloud-init seed image (optional, default: auto-generated):
Login credential (...) [alice]:
Networks (comma-separated; available: default; 'none' for no NIC) [default]:
VFIO PCI devices (comma-separated, e.g. /sys/bus/pci/devices/0000:41:00.0):
VM created successfully!

Type the root disk size rather than taking the default: an empty answer makes the disk the size of the image itself.

The VM is created stopped. Start it; start waits until it runs:

gxctl start my-vm
gxctl list

In the web UI: VMs → + Create VM. Fill in VM Name, set vCPU Count and Memory (MiB), keep Boot Mode at UEFI firmware (distro cloud image) and Boot Disk at New disk from an image, pick the Image, set Root disk (GiB), pick your Login Credential, and check the default network under Networks. Check Start it now to skip the separate start, then click Create VM. Without Start it now, click Start on the VM’s card.

More in Virtual machines.

8. Open the console

gxctl connect my-vm

You’re on the VM’s serial console. The first boot takes a little while for cloud-init to apply the credential; then log in with its username and password. Press Ctrl+] to detach; the VM keeps running. gxctl log my-vm prints what the console showed so far.

In the web UI: Open Console on the VM’s card or its detail page.

Once the guest has an address on the NAT network (gxctl get my-vm shows it), you can also SSH to it from the host with the keys in your credential.

More in The console.

9. Stop the VM

gxctl stop my-vm --graceful

--graceful presses the guest’s power button and waits up to 60 seconds (--graceful <secs> to change that) for it to shut down, then stops it. Without --graceful, stop ends the VM at once, like pulling the plug.

In the web UI: Shut down for the graceful stop, Stop for the immediate one.

To remove the VM and the root disk made for it (it asks first; add --keep-disk to keep the disk):

gxctl delete my-vm

Concepts

This page explains the objects Glidex manages and the words the rest of these docs use for them. Each entry links to the page with the details.

Control plane

The control plane (glidex-control-plane) is the service that holds the state of everything (VMs, disks, images, networks, projects, users) and acts on it: it starts hypervisors, creates disks and asks the host’s network helper to set up networks. It serves:

  • the REST API and the RPC API (gRPC, gRPC-Web and Connect) on HTTPS port 8841, and on a local Unix socket for gxctl on the host;
  • the console of every VM.

The web UI (glidex-ui, HTTPS port 5173) and gxctl are clients of that API: anything you do in one you can do in the other. See the API reference and the gxctl reference.

The control plane doesn’t sit between a VM and its hypervisor: with the installer’s systemd units, each VM runs in its own unit, so VMs keep running when the control plane restarts or is upgraded.

Nodes, servers and agents

A node is a host that runs VMs. A standalone host is a single node.

Several hosts can form a cluster. Each node has a role:

  • A server keeps a copy of the cluster’s state in a replicated (Raft) store and answers the API. Run one, or three or more for a quorum that survives the loss of a server.
  • An agent only runs VMs. It has no API of its own; its web UI relays to the servers.

Nodes join with a one-time join token and talk to each other over mutual TLS. A scheduler picks the node for each new VM, and explains its choice. A node can be drained (no new VMs are placed on it), removed, and rejoined. See Clusters.

Tenants and projects

A project is where VMs, disks, guest credentials and project networks live. Each of these belongs to exactly one project. A project has members with roles, and optional quotas: limits on VMs, running VMs, vCPUs, memory, disk, networks and routers.

Every install starts with a project named default. In gxctl, --project <p> picks a project for one command and project use <p> sets your default; in the web UI, the Project selector in the header does both. See Projects.

A tenant is the organization that owns projects. A standalone host has an operator tenant admin, which runs the host, and a tenant default, which holds the default project. Most single-site installs don’t need more than that.

Virtual machines

A VM has a name, a project, a hypervisor, vCPUs and memory, a boot disk, zero or more data disks, network interfaces (one per network it attaches to), optional PCI devices, and an optional guest credential.

Glidex separates what you ask for from what it last saw:

  • The desired state (the spec) is what you want: the VM’s configuration, and whether it should be running, paused or stopped. Start, stop, pause and edits change only this, and return at once.

  • The state (the status) is what the control plane last observed:

    StateMeaning
    createdNever started.
    startingThe hypervisor is being launched.
    runningThe guest is running.
    pausedThe guest is paused.
    stoppingA stop is in progress.
    stoppedNot running.
    failedIt couldn’t be started, or it crashed.
    unknownThe control plane can’t tell whether its hypervisor is still running.

A controller keeps working until the state matches the desired state. While it does, the web UI shows both (for example, Stopped → Running) and gxctl start waits for it. Some changes only apply at the next start; the VM then says a restart is required.

Two settings say what happens when the VM stops on its own:

  • Restart policy (If It Crashes in the web UI): restart it with backoff (the default) or leave it stopped.
  • On host boot (After a Host Reboot): start it again if it was running, or leave it stopped.

Stopping is either graceful (press the guest’s power button, wait, then stop) or immediate. Each VM keeps a short list of events: starts, exits, restarts. See Virtual machines.

Hypervisors

Each VM runs on one hypervisor:

  • Cloud Hypervisor (cloudhypervisor), the default.
  • QEMU (qemu).

Both support the same features in Glidex: UEFI boot of cloud images, direct kernel boot, networks, disks, PCI passthrough (VFIO), pause and resume, and graceful shutdown. You pick the hypervisor when you create the VM.

Images and firmware images

An image is a read-only file disks are made from. Images belong to the host (or cluster), not to a project: everyone can use them, and administrators with the image role pull and delete them.

  • A cloud image is a bootable distribution disk image (qcow2 or raw). Pull one from the built-in catalog by key (for example ubuntu-26.04, debian-13, fedora-cloud) or from an HTTPS URL. Catalog images are checked against their published SHA-256; an image from a URL without a checksum is kept but marked unverified.
  • A firmware image is the UEFI firmware a VM boots through, built for one hypervisor: cloudhv-edk2 (CLOUDHV.fd) for Cloud Hypervisor, ovmf for QEMU. A new VM uses the newest firmware image for its hypervisor unless you choose another.

An image is downloading, verifying, ready, failed or missing (its file is gone). See Images and disks.

Disks

A disk is a virtual disk in a project. It is attached to at most one VM at a time, as its boot (root) disk or as a data disk. A disk is:

  • blank, of a size you choose, or
  • made from an image: either linked (thin: a qcow2 overlay on the image, so it takes space only for what the VM writes) or a full copy.

When you create a VM from an image, Glidex makes a linked root disk for it, grows it to the size you ask for, and extends the guest’s root partition to fill it. That disk belongs to the VM and is deleted with it unless you keep it. Disks can be resized; a resize of a disk that is in use is held until it can be applied.

Guest credentials

A guest credential is a login for inside VMs: a username with a password, SSH public keys, or both. Credentials belong to a project. Glidex stores only a hash of the password.

When you create a VM with a credential, Glidex generates a cloud-init seed that creates that user in the guest. It is applied on the VM’s first boot only: later changes to the credential don’t reach VMs that already booted. You can also give your own cloud-init seed instead. See Guest credentials.

Networks

A network connects VM interfaces. Its mode is one of:

  • NAT: a private subnet with DHCP; VMs reach the outside through the host (masquerade).
  • Isolated: VMs on it reach each other and nothing else.
  • Bridged: VMs sit on an existing network of the host (in a cluster, a provider network on a physical network).

A host network is created by an administrator and offered to the projects allowed to use it. A project network belongs to a project, and its owner can share it with other projects.

On a standalone host, networks are Open vSwitch bridges on that host. In a cluster with OVN enabled, a cluster network spans every node. A VM’s interface is a tap device (the default) or a vhost-user port (with OVS-DPDK).

A network is pending, ready or degraded, or reports that the host’s network helper is unavailable. See Networks and Host networking.

Console

Every VM has a serial console. Any number of clients (browser tabs, gxctl connect) can share it at once, and everything it prints is logged to disk, so you can read what happened before you connected. See The console.

Users, teams and roles

A user is a person known to Glidex. Users log in through a login connector: local accounts (PAM) or OIDC single sign-on. On the host itself, gxctl identifies you by your Unix account. A team is a group of users; teams can mirror Unix or identity-provider groups.

A role binding gives a user, team or token a role on a resource. Project roles, each including the one before it:

RoleCan
viewerSee the project, its VMs, disks and usage.
operatorAlso start, stop and pause VMs, and use their consoles.
editorAlso create, change and delete VMs and disks, manage guest credentials, and attach networks.
ownerAlso manage members, and manage and share project networks.

Host roles cover the host or cluster itself: auditor (read-only, including the audit log), image-admin (images), net-admin (host networks and PCI devices), and system-admin (everything). See Access control.

Tokens

An API token lets a script or another machine call the API. A token has a name and always expires: after a default lifetime, or after the number of days you choose, up to a limit the site sets.

  • A personal token acts as you. It can be narrowed to some of your roles.
  • A service-account token belongs to a project and has only the roles it is given.

The secret is shown once, when you create the token. Create tokens with gxctl token create or on the web UI’s Tokens page; revoke them the same way. See Logging in.

Policies and the audit log

Every request is authorized by Cedar policies: built-in ones that implement the roles above, plus optional site policies an administrator adds to allow or forbid more. Some sensitive operations also need a recent login. Changes, and refused requests, are recorded in the audit log: who did what, to what, and with what result. See Access control.

Usage

Glidex meters what each VM, disk and network uses (CPU, memory, disk I/O and network traffic) and reports it per project, VM, disk, NIC or network, by hour, day or billing month. See Usage.

User guide

This guide is for people who run VMs on a Glidex host or cluster that someone else installed: logging in, working inside a project, and creating, connecting to and removing VMs and what they use.

If you are setting Glidex up, start with the Quick start and the Operator guide. The Concepts page explains the words used here: projects, images, disks, credentials, networks.

Three ways in

Everything in this guide can be done in at least one of these:

  • Web UI, at https://<host>:5173 by default. Sign in with your account; the header has a project selector and a page per resource (VMs, Images, Disks, Credentials, Networking, Projects, Usage).

  • gxctl, the command-line client. Run gxctl for an interactive shell (gxctl> prompt, Tab completion, help lists every command), or gxctl <command> to run one command and exit:

    gxctl list                  # one command, then exit
gxctl                       # the shell

    On the host itself it uses the local socket and needs no login; from another machine it logs in once and keeps a token.

  • The API, REST over HTTPS on port 8841 by default, plus an RPC API, authenticated with a bearer token. The web UI and gxctl use it too, so anything they do can be scripted. See the REST API and RPC API references.

Each page shows the web UI path and the gxctl commands, with a short API example where it helps. The full command list is in the gxctl reference.

What you can do depends on your role

Glidex checks every request against your roles. Within a project you are a viewer, operator, editor or owner (see Roles); a few things, such as pulling images or changing host networking, need a host-wide role that administrators hold. The web UI hides or disables what you can’t do; gxctl and the API answer not allowed: <action>, naming what was refused. If you need more access, ask a project owner or an administrator.

Logging in

How you prove who you are depends on where you connect from:

FromHow
The web UIYour account’s password (PAM) or single sign-on (OIDC), whichever the site enables
gxctl on a Glidex hostNothing: the local socket knows your Unix account
gxctl on another machinegxctl auth login once; it saves a token in a login profile
Scripts and the APIAn API token, sent as Authorization: Bearer <token>

Which login methods exist, and who may log in, is set by the operator (see Authentication).

The web UI

Open https://<host>:5173 (gxctl ui prints the address it knows). The sign-in page shows what the site enables:

  • Username and Password, then Sign in: a local account of the host, or of the site’s PAM setup. By default the account must be in the glidex-users group.
  • Sign in with <provider> (or Sign in with SSO): your organisation’s single sign-on.

If the page says No login method is enabled on this host, ask an administrator, or use gxctl on the host.

The first time, your browser may warn that the certificate is not trusted: the host made its own. Compare the SHA-256 fingerprint the browser shows with the one your operator gives you before you accept it (see TLS).

A browser session ends after 30 minutes without activity and after 12 hours at most, unless the operator changed these. Log out, in the header, ends it now. Some actions (changing policies, host networking or the cluster) need a recent login: the UI then asks you to sign in again (Confirm it’s you) and retries the action.

The header also shows who you are and the project you are working in; see Projects.

gxctl on a Glidex host

On a host that runs the control plane, gxctl talks to its Unix socket (/run/glidex-cp/api.sock) and the control plane identifies you by your Unix account. There is no login and no token:

gxctl whoami

You need to be in the glidex-users group (log out and back in after being added). Members of glidex-admin are administrators.

--socket <path> (or GLIDEX_SOCKET) picks another socket. On a cluster agent node there is no local API: log in to a server node from there as from any other machine.

gxctl from another machine

gxctl auth login connects to a control plane over HTTPS, checks its certificate, gets you a token and saves the lot as a named login profile in ~/.config/glidex/config.json (mode 0600). Later commands use the current profile without asking again.

Pick a profile name and a way to prove who you are:

# Your account's password (asked for, never on the command line)
gxctl auth login --url https://host.example.org:8841 --profile lab --pam-user alice

# Single sign-on: open the link it prints and enter the code
gxctl auth login --url https://host.example.org:8841 --profile lab --oidc

# An API token you already have (typed hidden, or piped)
gxctl auth login --url https://host.example.org:8841 --profile ci --token < token.txt
  • --connector <id> picks one of several sign-in providers.
  • --name <name> names the token it creates (default gxctl@<profile>), so you can tell your machines apart in gxctl token list.
  • --days N asks for a shorter or longer --pam-user token, within the site’s limit (30 days unless the operator changed it). An --oidc login gets a token valid for one day.
  • For a cluster, repeat --url with several server nodes; gxctl tries them in turn.
  • Without --profile, --url refreshes the profile that already points at that host; for a new host add --save to name the profile after it.

The first profile you create becomes the current one; --use makes a later one current. Run the same auth login --profile lab again when its token expires.

Certificates and fingerprint pinning

gxctl verifies the control plane’s certificate. A certificate from a CA your machine trusts just works. A self-signed one (the default) is not trusted, and auth login shows its fingerprint:

the certificate of host.example.org is not trusted by this system:
  SHA-256 AB:CD:…   (the control plane prints this line at startup)
  reported by the server as its own: it matches what we are being handed (…)
Trust this exact certificate for profile 'lab'? [y/N]:

Compare the fingerprint with the one your operator gave you through another channel, then answer y. The profile pins that certificate: from then on gxctl accepts exactly it for this profile, and refuses to connect if it changes. If the line says the two do not match, stop and ask the operator: something between you and the host is presenting its own certificate.

Without a terminal (CI), there is no prompt; give the fingerprint up front:

gxctl auth login --url https://host.example.org:8841 --profile ci \
  --pin sha256/<fingerprint> --token < token.txt

When the operator legitimately replaces the certificate (for example after rotating a cluster’s CA), confirm the new fingerprint with them and re-pin:

gxctl auth login --profile lab --pin sha256/<new fingerprint> --rebind

--rebind is also what lets a profile log in to a machine that now answers for a different cluster than the one it first saw; without it gxctl refuses.

gxctl auth trust list shows a profile’s pins and extra CAs.

Instead of a profile, a one-off --url connection trusts a self-signed certificate through GLIDEX_CA_CERT, the path of a PEM copy of the host’s certificate that your operator provides.

Managing profiles

gxctl auth status             # the profile in use: target, cluster, trust, token
gxctl auth profiles --all     # every profile; * marks the current one
gxctl auth use lab            # make 'lab' current
gxctl --profile ci list       # use another profile for one command
gxctl auth logout             # forget this profile's token (target and pins stay)
gxctl auth logout --revoke    # revoke it on the server first, then forget it

GLIDEX_PROFILE does what --profile does. --url on a command overrides the target for that run but keeps the profile’s trust; the profile’s token is only sent if the URL points at one of the profile’s own hosts.

Once the profile file holds any profile, gxctl uses profiles instead of the local socket. To reach the local socket on a host where you also keep profiles, run it with the file switched off:

GLIDEX_CONFIG= gxctl whoami

GLIDEX_CONFIG=<path> reads profiles from another file.

Older single-token login

gxctl --url https://host.example.org:8841 login --oidc (or login --token) still works when you have no profiles: it saves one token in ~/.config/glidex/token and gxctl --url … sends it. logout [--revoke] removes it. Profiles are the better choice: they remember the target and pin its certificate.

GLIDEX_TOKEN, when set, is sent instead of any saved token.

API tokens

An API token lets a script, CI job or another tool act through the API. There are two kinds:

  • Personal: acts as you, and can never do more than you can. Give it roles to narrow it further (only viewer in project lab, say); without roles it can do everything you can.
  • Service account: belongs to a project, not a person, so it keeps working when people leave. It can only do what its roles in that project allow; without roles it can do nothing. Creating one needs the project’s owner role.

Tokens expire: after 90 days unless you ask otherwise, at most 365 (the operator sets both). The secret is shown once, when you create the token; Glidex keeps only a hash of it.

Web UI

Tokens in the header (shown when you are signed in with an account, not with a token):

  1. + Create Token.
  2. Enter a Name and Expires in (days). For a service account, choose Kind: Service account of <project> (offered if you own the selected project).

Projects

A project is where your work lives. Every VM, disk, guest credential and project network belongs to exactly one project; who may do what is granted per project; quotas cap what a project may use.

Images are different: they are a library shared by every project (see Images and disks).

Every installation has a project named default, created at install. It can’t be deleted. The members of the glidex-admin group at the control plane’s first start are made its owners.

Seeing your projects

Web UI: Projects in the header lists the projects you are a member of, with each one’s use against its quotas. Click a project for its page: quotas, members, networks.

gxctl:

gxctl project list
gxctl project show lab

If you are in no project yet, the list is empty: ask a project owner or an administrator to add you.

Choosing a project

Most commands work in one project at a time: lists show its VMs and disks, and new resources are created in it.

Web UI: the Project selector in the header. Every page then shows that project’s resources. On a project’s page, Select this project does the same. Your choice is also saved as your default project.

gxctl: a project is chosen, in this order, by

  1. --project <name|id> (or -p, or GLIDEX_PROJECT) on the command:

    gxctl --project lab list

  2. a "project" key in the login profile in use;

  3. your default project, kept by the control plane and shared with the web UI:

    gxctl project use lab     # set it
gxctl project use -       # clear it

  4. if none is set and you belong to exactly one project, that project.

gxctl whoami shows your default project and the one this session uses. Over the API, pass ?project=<name|id> or a "project" field.

Roles

Each member of a project has one of four roles. Each role includes everything of the roles above it.

RoleCan
viewerSee the project, its VMs, disks and usage
operatorAlso start, stop, pause and change VMs, and open their consoles
editorAlso create and delete VMs and disks, attach disks and networks to VMs, and see and manage guest credentials
ownerAlso manage members and service-account tokens, read the project’s audit log, and create and share project networks

Viewers and operators don’t see guest credentials.

Host-wide roles (for example image-admin for pulling images, or net-admin for host networking) and how administrators assign them are described in Access control.

Members

A member is a user or a team bound to a role in the project. Owners manage members.

Web UI: the project’s page, Members card. The table lists each binding; Remove deletes one. To add one, choose a Role, a Principal type (User or Team) and the user or team, then Add role. If you can’t list users, type the user’s id (they can find it with gxctl whoami).

gxctl:

gxctl binding list lab
gxctl binding add lab editor user:<user-id>
gxctl binding add lab viewer team:<team-id>
gxctl binding remove lab <binding-id>

Roles can be written short (editor) or in full (role.editor). A principal is user:<id>, team:<id> or token:<id>. binding list shows each binding’s id.

Over the API: GET/POST /projects/{id}/bindings and DELETE /projects/{id}/bindings/{binding-id}.

Teams

A team is a named group of users; binding a team to a project gives every member of it that role. Administrators create teams and manage their members (Access in the web UI, gxctl team …):

gxctl team list
gxctl team create ops
gxctl team add-member ops <user-id>
gxctl team remove-member ops <user-id>

Teams can also come from outside Glidex:

  • on the local socket, each of your Unix groups counts as a team named unix:<group>, so team:unix:lab-users grants a role to that group’s members when they use gxctl on the host;
  • the operator can map groups from the site’s PAM or single sign-on setup to teams.

gxctl whoami lists the teams you are in.

Creating and deleting projects

If you may create projects, Projects shows + Create Project: give a Name (1-32 lowercase letters, digits and dashes), an optional Description and, optionally, an Owner. Or:

To delete a project it must not own any VMs, disks or credentials: Delete project on its page, or gxctl project delete lab (it asks for confirmation). Its service-account tokens are revoked with it.

On an installation with several tenants (organisations), each project belongs to one tenant, shown in the Tenant column. See Access control.

Images and disks

  • An image is a read-only base: a distro cloud image that VMs’ disks are made from, or the UEFI firmware VMs boot through. Images are a library shared by every project.
  • A disk is a writable volume in a project: a VM’s root disk or an extra data disk. A disk can start blank or as a copy of an image.

Pulling and deleting images needs the host-wide image-admin role; everyone can see and use the library. Creating, resizing and deleting disks needs the editor role in the disk’s project.

Web UI: Images, then Pull on a catalog entry. The image appears under Cloud images and shows its download progress, then Ready.

gxctl:

From a URL

Any qcow2 or raw image reachable over HTTPS can be pulled too:

gxctl image pull https://images.example.org/my-image.qcow2 --name my-image --sha256 <sha256>

Listing, retrying and deleting

gxctl image list
gxctl image retry my-image     # download a failed image again
gxctl image rm my-image

An image can’t be deleted while a disk is being made from it or a linked disk still uses it as its base (see Clone modes).

In a cluster, a server downloads and checks the image, and nodes copy it from there when they need it. When pulling in the web UI you can pick Copy to nodes to have copies ready sooner; the Images page shows each node’s copy and can copy an image to another node or let a copy go.

Disks

Creating a disk

Creating a VM from an image already makes its root disk (see Virtual machines). Create disks yourself for data, or to keep a root disk independent of any one VM.

Web UI: Disks, Create Disk:

  • Name: 1-64 characters of letters, digits, ., _ and -. Disk names are unique.
  • Contents: Blank disk, or an image.
  • Size (GiB): required for a blank disk. From an image it defaults to the image’s size or 10 GiB, whichever is larger, and can’t be smaller than the image.
  • Format: qcow2 (default) or raw.
  • Clone (from an image): Linked or Full copy.

gxctl:

gxctl disk create data1 --size-gib 50                    # blank qcow2
gxctl disk create web-root --image ubuntu-24.04 --size-gib 20
gxctl disk create web-root2 --image ubuntu-24.04 --full --raw

When a disk is made from an image and given more space than the image has, Glidex extends its root partition to fill it (the guest grows the filesystem when it boots). --no-extend leaves the partition as it is.

If the image is still downloading, the disk waits for it.

Clone modes

  • Linked (default for qcow2): a thin overlay on the image. Fast and small, but the image must stay as long as the disk exists.
  • Full: an independent copy. Needed for raw disks.

Listing and inspecting disks

gxctl disk list
gxctl disk show web-root      # size, format, partitions, free space at the end

disk list shows the disks of the selected project (see Choosing a project), with their size, format, origin, status and the VM each is attached to. In the web UI, click a disk’s name for its details and partitions.

Attaching a disk to a VM

A disk is attached to one VM at a time.

  • As the root disk when you create a VM: in the web UI choose Boot Disk, Existing disk; in gxctl create answer disk at Boot disk from.

  • As a data disk: gxctl create asks for Data disks (disk names, comma-separated). For an existing VM, use the API:

    curl --cacert host.crt -H "Authorization: Bearer $GLIDEX_TOKEN" \
  -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/vms/<vm-id>/disks -d '{"disk": "data1"}'

    On a running VM it takes effect the next time the VM starts. DELETE /vms/<vm-id>/disks/<disk> detaches it.

Growing and shrinking

Web UI: Disks, Resize, enter the New size (GiB). When growing a disk made from an image, Extend the root partition into the new space is ticked.

gxctl:

gxctl disk resize web-root 40               # grow, and extend the root partition
gxctl disk resize data1 100 --no-extend     # grow, leave the partitions alone
gxctl disk resize data1 30                  # shrink
  • Growing counts against the project’s disk_gib quota.
  • Shrinking only gives back unpartitioned space at the end of the disk; Glidex never shrinks filesystems. A size that would cut into a partition is refused with the smallest size allowed.
  • A resize of a disk a running VM uses is recorded and applied once the VM stops.

To grow the root partition into space that is already there (say, after a resize with --no-extend):

gxctl disk extend-root web-root             # from the host, once no running VM uses the disk
gxctl disk extend-root web-root --on-boot   # by the guest, at its next boot

In the web UI it is Extend root on the disk’s row. --on-boot relies on the cloud-init seed Glidex generates; a VM with a custom seed has to grow the partition itself (see Guest credentials).

Deleting a disk

Web UI: Disks, Delete (disabled while the disk is attached).

gxctl:

gxctl disk rm data1

It asks for confirmation; the disk’s data is gone afterwards. A disk attached to a VM can’t be deleted: detach it or delete the VM first. A root disk that was created along with a VM is deleted with the VM, unless you delete the VM with --keep-disk.

In a cluster, a disk lives on one node. It is bound to the node of the first VM that uses it, and its VMs run there.

Guest credentials

Distro cloud images ship with no usable login: they wait for cloud-init to create one on first boot. Glidex stores the logins you want as credentials and hands the one a VM names to cloud-init.

A credential is a Linux username with a password, SSH public keys, or both. Credentials belong to a project and are used by that project’s VMs; seeing and managing them needs the editor role.

How a credential reaches the guest

When a VM boots a cloud image through UEFI firmware, Glidex writes a small cloud-init seed volume for it (NoCloud, labelled CIDATA) and attaches it. From the VM’s credential, cloud-init creates the user in the guest:

  • with passwordless sudo and /bin/bash;
  • with the credential’s password, and SSH password logins on, if it has one; the password locked otherwise;
  • with the credential’s SSH keys as authorized_keys.

The seed also sets the guest’s hostname from the VM’s name, turns on DHCP on each of its network interfaces, and grows the root filesystem to fill its partition.

cloud-init applies the user on the VM’s first boot only. Changing or deleting a credential later does not change VMs that already booted; change the login inside those guests instead.

VMs without a credential

A VM created without a credential still gets a seed, with the guest user cloud, no SSH keys and a locked password: nobody can log in, on the network or on the console. Glidex never adds keys or passwords of its own. Pick a credential when you create the VM (see Virtual machines).

Adding a credential

Web UI: Credentials, Add Credential:

  • Username: lowercase letters, digits, _ and -, starting with a letter or _, at most 32 characters.
  • Password and Confirm (optional): 8 to 256 characters.
  • SSH public keys (optional): one OpenSSH public key per line (ssh-ed25519 AAAA… alice@laptop).

A password, a key, or both is required. If you have a local account on the host, the form fills in your username and the public keys in your ~/.ssh/*.pub.

gxctl:

$ gxctl credential-add
Username [alice]:
Leave the password empty for SSH-key-only login.
Password:
Confirm password:
SSH public key files (comma-separated; 'none' for no keys) [~/.ssh/id_ed25519.pub]:
Credential created: alice (password: set, SSH keys: 1)

It offers your login name and your own ~/.ssh/*.pub files as defaults. Give .pub files, never private keys: gxctl refuses a file that holds a private key.

The credential goes into the selected project (see Choosing a project); use gxctl --project lab credential-add for another.

These usernames are refused because distro images already have them: root, ubuntu, daemon, bin, sys, sync, games, man, lp, mail, news, uucp, proxy, www-data, backup, list, irc, nobody, systemd-network, systemd-resolve, messagebus, sshd and syslog.

Listing, changing and deleting credentials

Web UI: Credentials lists each username, whether it has a password, its number of SSH keys and when it changed. Edit sets a new password (leave it empty to keep the current one) or replaces the keys; Delete removes it.

gxctl:

gxctl credentials                 # list
gxctl credential-passwd alice     # set a new password (asked twice, hidden)
gxctl credential-keys alice       # replace the SSH keys; empty removes them all
gxctl credential-rm alice

A credential must keep a password or at least one key, and can’t be deleted while a VM uses it.

Passwords are hashed (SHA-512-crypt) as soon as they arrive. Glidex never stores, logs or returns the password itself, and the API never returns the hash; the lists only say whether a password is set.

Using a credential

When you create a VM that boots a cloud image:

  • Web UI: choose it under Login Credential. If the project has a credential with your username, it is preselected.
  • gxctl create: answer the Login credential prompt; the default is the credential named like you, if there is one, and none creates the VM without a login.
  • API: "credential": "alice" in POST /vms.

A credential only works with the seed Glidex generates: a VM that boots a kernel directly, or brings its own seed, can’t use one.

Your own cloud-init seed

To provision a guest your own way (other users, packages, files), give the VM a cloud-init seed image you made, instead of the generated one: gxctl create asks for a cloud-init seed image, and the API takes "cloud_init_path": "/srv/seeds/web.img". The control plane then attaches that file as it is.

  • It is a path on the host, opened by the control plane: it needs the host-wide grant.host-paths permission (ask an administrator), and the file must be readable by the service (under the systemd units, not in your home directory or /tmp).
  • The VM can’t use a credential, and Glidex doesn’t add networking, hostname or root-partition growth: put what you need in the seed.

A seed is a small FAT or ISO volume labelled CIDATA holding user-data and meta-data (and optionally network-config), for example made with cloud-localds from the cloud-image-utils package.

Virtual machines

A VM belongs to one project. You create it stopped (or ask for it to start at once), then start, pause, stop and delete it. Each of these changes the VM’s desired state; the control plane then works until the VM gets there. See Concepts for the model.

In the web UI, the VMs page lists the VMs of the selected project. Click a VM for its details, actions, usage and events.

In gxctl, commands take a VM’s name or id. Names are unique within a project; use --project <p> (or project use <p>) when the same name exists in two projects you can see.

gxctl> list                       # the VMs: id, name, project, state, node, vCPUs, memory, hypervisor
gxctl> get my-vm                  # one VM: state, last exit, NICs and their addresses

Boot disk

Give exactly one of:

  • image: Glidex creates a linked root disk from the image for this VM (named <vm>-root), grows it to root_disk_size_gib, and extends the guest’s root partition at first boot. The disk belongs to the VM and is deleted with it, unless you delete with --keep-disk.

  • rootfs_path: a disk image file on the host, used as is.

The image (or the root disk’s image) and the firmware must be for the same CPU architecture.

Firmware or kernel boot

A VM with an image or root_disk boots through UEFI firmware: the newest firmware image for its hypervisor (and architecture), unless you name one with firmware. If there is none, the create fails and tells you which one to pull (cloudhv-edk2 for Cloud Hypervisor, ovmf for QEMU).

For a direct kernel boot, give kernel_image_path (and a root filesystem in rootfs_path) instead. The default kernel arguments are console=hvc0 root=/dev/vda reboot=k panic=1 on Cloud Hypervisor and console=ttyS0 root=/dev/vda reboot=k panic=1 on QEMU.

Host paths

rootfs_path, kernel_image_path, cloud_init_path and firmware_path name files on the host. Using them needs the system-admin role, and the files must be readable by the service user the control plane runs as. Most users should use images, disks and firmware images instead. A path under /tmp or /var/tmp is refused: VMs have a private /tmp.

Credential and cloud-init

With firmware boot and no cloud_init_path, Glidex generates a cloud-init seed for the VM: its hostname, the root partition grow, and, if you name a credential, that user with its password and SSH keys. cloud-init applies it on the VM’s first boot. Without a credential the guest has no login. See Guest credentials.

cloud_init_path replaces the generated seed with your own (a host path, see above); a credential can’t be combined with it.

Stop

A graceful stop presses the guest’s power button, waits for the guest to shut down, and stops the VM hard if it is still running after the timeout:

gxctl> stop my-vm --graceful          # wait up to 60 s
gxctl> stop my-vm --graceful 120      # wait up to 120 s (at most 300)

The web UI’s Shut down waits 60 seconds. Stop and stop without --graceful stop the VM like pulling the plug.

The timeout you give is kept as the VM’s stop grace (stop_grace_secs) and used again by later stops that don’t give one, including stops from the web UI’s Stop button. Pass --graceful 0 (or graceful_timeout_secs=0) for an immediate stop after a graceful one.

Pause and resume

A paused VM keeps its memory but gets no CPU time. Resume in the web UI, or start in gxctl, runs it again.

Restart

There is no restart action: stop the VM, then start it. A reboot from inside the guest restarts the guest and the VM stays running.

When the VM stops on its own

  • The guest powers off (for example poweroff inside it): the desired state becomes stopped, and the VM stays stopped whatever its restart policy.
  • The hypervisor crashes: with the restart policy on_failure, the VM is started again after 10 seconds, doubling with each crash in a row up to 5 minutes; after 10 minutes of running the count starts over. With never, the desired state becomes stopped.
  • It fails to launch: the VM is failed and Glidex retries with a growing delay. Its details and events say why.
  • The host reboots: with on_host_boot resume, a VM that was running is started again; with stop, it stays stopped.

Change these policies with the API:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X PATCH https://host.example.org:8841/vms/<id> \
  -d '{"change": {"restart_policy": "never"}, "update_mask": "restart_policy"}'

Change a VM

Change vCPUs, memory, networks, data disks, PCI devices, kernel arguments, the credential, hugepages and the policies with PATCH /vms/{id}. change holds the new values, update_mask lists the fields to change (comma-separated):

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X PATCH https://host.example.org:8841/vms/<id> \
  -d '{"change": {"vcpu_count": 4, "mem_size_mib": 8192}, "update_mask": "vcpu_count,mem_size_mib"}'

networks and data_disks replace the whole list. The hypervisor, the boot disk, the firmware and host paths can’t be changed.

The web UI and gxctl have no edit form; gxctl changes PCI devices only (attach-device, detach-device).

A change to vCPUs, memory, kernel arguments, the credential, hugepages, networks or data disks of a running VM takes effect at the next start: the web UI says Configuration changes take effect at the next start, and the API sets restart_required. Stop and start the VM to apply it. A new credential doesn’t change logins in a guest that already booted (cloud-init runs once).

Pass the VM’s resource_version in an If-Match header to refuse the change (409) if someone else changed the VM since you read it.

Placement on a cluster

On a cluster, the scheduler picks the node for a new VM when it is created. It considers only nodes that are active, ready and not draining, that have the hypervisor, enough vCPUs and memory left, the PCI devices, hugepages and physical networks the VM needs, and that hold its disks and node networks. Of those, it prefers the least loaded.

A VM stays on its node for its whole life: Glidex doesn’t move it, and doesn’t restart it elsewhere if the node fails. If no node can take the VM, it is still created and waits for one; its page says Waiting for a node with each node’s reason.

In the web UI’s create form, Placement shows Automatic (now: <node>) and each node with its free vCPUs and memory, or why it can’t take the VM. Pick a node to pin the VM there. With the API, set node when you create the VM. To ask the scheduler without creating anything:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/scheduler/preview \
  -d '{"vcpu_count": 2, "mem_size_mib": 2048, "hypervisor": "qemu"}'

The answer has the node it would pick (pick) and every node’s fit (nodes, with refused when it can’t take the VM).

The VM’s node shows in gxctl list and on its page. If the node stops reporting, the page shows the VM’s last known state; the VM may still be running there.

See Clusters for nodes and draining.

Networks

A network connects VM NICs. Glidex creates no network by itself: an administrator creates host networks and offers them to projects, and a project’s owner can create networks of the project’s own. A VM gets one NIC per network it attaches to.

This page is the user’s view. Setting up the host side (Open vSwitch, bridges, uplinks, OVN) is in Host networking.

Network modes

ModeWhat VMs getAddresses
NATA private IPv4 subnet behind the host. VMs reach the outside through the host (masquerade); nothing outside can open a connection to them.DHCP from Glidex.
IsolatedVMs on the network reach each other and nothing else, not even the host.None on a single host (configure them in the guest); DHCP on a cluster network.
BridgedVMs sit on an existing LAN through one of the host’s bridges, as if plugged into it.From the LAN (its own DHCP).

NAT networks can’t reach each other, and a guest reaches the host only for DHCP, DNS and ping on its gateway. Glidex has no port forwarding: to reach a VM from outside, put it on a bridged (or, on a cluster, provider) network.

A VM’s NIC is a tap device (the default) or a vhost-user port, which needs OVS-DPDK on the host. The network decides which.

Where a network lives

On a single host, a network is an Open vSwitch bridge on that host.

On a cluster, a network is either:

  • a cluster network (on OVN), which spans every node: VMs on any node can use it, and traffic between nodes goes through tunnels. Needs OVN turned on for the cluster. A NAT cluster network reaches the outside through the cluster’s shared edge, which an administrator sets up first;
  • a node network, a bridge on one node: only VMs placed on that node can use it, and the scheduler places them there.

On a cluster with OVN on, new networks span the cluster unless you ask for a node network. The cluster’s bridged networks are provider networks: they sit on a named physical network that the nodes map, optionally on a VLAN.

Who can use a network

  • A host network has no project. An administrator (net-admin) creates it and grants it to projects, to whole tenants, or to every project.
  • A project network belongs to a project. Its owner creates it (NAT or isolated only) and can share it with other projects. It counts against the project’s network quota.

To attach a VM to a network you need the editor role in the VM’s project, and the network must be usable by that project.

gxctl> networks                     # host networks, and project networks you can see
gxctl> network show lab             # id, mode, scope, bridge, phase, grants or shares

In the web UI, the Networking page lists the networks the selected project can attach VMs to (with host rights, every network and the host’s bridges). Its Status column shows ready, or what the network is waiting for.

A network is pending, ready, degraded (part of it is missing on the host; Glidex restores it), or reports that the host’s network helper is unavailable.

  • Name: lowercase letters, digits and -, at most 32 characters.
  • Mode: NAT (DHCP + masquerade) or Isolated (VM-to-VM).
  • VM port: tap or vhost-user (DPDK).
  • Subnet (optional): for NAT (and isolated cluster networks). On a single host, the default is the first free /24 in 10.88.0.0/16; on a cluster, a free range from the cluster’s pool.
  • Leaves through / Routed through: a router of the project, for a cluster network. See Project routers.

Share a project network

A project’s owner offers a share to another project, whose owner accepts it within 7 days. Then the other project’s VMs can attach to the network.

gxctl> network share lab <other-project-id>        # offer

Attach VMs

Pick the networks when you create the VM: the Networks checkboxes in the web UI, the Networks prompt in gxctl create, or networks in the API. One NIC per network, in order, at most 8. A network named default, if the project can use one, is preselected.

To change a VM’s networks later, PATCH its networks (the whole list); it applies at the VM’s next start. See Virtual machines.

Addresses

  • NAT (single host): the gateway is the subnet’s .1, and each NIC gets a fixed address from the rest of the subnet, by its MAC. The NIC keeps it across restarts until the VM is deleted. The gateway also answers DNS.
  • Cluster networks (NAT and isolated): Glidex reserves an address for each NIC from the network’s subnet and serves it by DHCP. A NIC can only send from its own MAC and address (on provider networks, its own MAC).
  • Bridged and provider: the LAN’s DHCP server, or static addresses in the guest.
  • Isolated (single host): no DHCP; configure addresses in the guest.

NAT networks are IPv4 only. The address of each NIC shows in the VM’s details: Network on its page in the web UI, NIC <n> in gxctl get <vm>, nics[].ipv4 in the API.

Delete a network

A network can’t be deleted while any VM uses it, even a stopped one.

gxctl> network rm lab          # or network-rm lab; waits up to a minute

In the web UI, Delete on the network’s row (project page) or on the Networking page.

Project routers (clusters)

On a cluster with OVN on, a project’s NAT cluster networks leave through the cluster’s shared edge, each on its own: they can’t reach each other. A router of the project changes that for the networks attached to it:

  • they reach each other through the router;
  • with an outside address (an external router), they leave with that address instead of the edge’s. Without one (internal only), they reach each other and nothing outside;
  • an isolated network attached to a router gets a gateway (the subnet’s .1) and is routed like a NAT one. Running VMs learn it when their DHCP lease renews, or when they restart their network or reboot.

Only NAT and isolated networks that span the cluster can go on a router; node networks can’t. VMs keep their addresses when their network moves to or from a router, but connections open through the old way out are cut.

Routers are managed on the project’s page, in the Routers card (it shows only with OVN on), with the owner role:

  1. Click New router, give it a Name, and tick Reaches outside, with its own address for an external router (possible once an administrator gave the edge a pool of addresses for routers). An external router counts against the project’s external IP quota. Administrators can also choose its Address and Gateway nodes.
  2. On the router’s row, Attach network… puts existing networks on it, and + network on <router> creates a new one there. Detach puts a network back on the edge.
  3. Delete removes a router once no network is attached.

There are no gxctl commands for routers. With the API:

  -d '{"name": "r1", "external": true}'
curl -H "$auth" -H 'Content-Type: application/json' -X PUT $api/projects/my-project/networks/lab/router \
  -d '{"router": "r1"}'                  # {} puts it back on the edge
curl -H "$auth" -X DELETE $api/projects/my-project/routers/r1

The console

Every VM has a serial console. You can type into it from the browser or from gxctl, as many clients at once as you like, and everything it prints is logged, so you can read what happened before you connected. Opening a console or reading its log needs the operator role in the VM’s project.

What the console shows depends on the guest: a cloud image booted through UEFI firmware prints the firmware, the boot loader and the kernel there, then a login prompt. Log in with the VM’s guest credential.

In the browser

On the VM’s page, click Open Console. The console opens in the page and connects at once; the Status at the top says connected, closed or error. Type into it as into a terminal: input goes straight to the VM’s serial port.

When you connect, the console first replays what the VM printed so far (its current log), then follows live output.

If the connection closes (the VM stopped, or the control plane restarted), click Reconnect. Back to VM leaves the console; closing the page detaches without affecting the VM.

With gxctl

gxctl> connect my-vm
Info: Connected to the VM console via ...
Tip: Press Ctrl+] to detach from console

console and attach are aliases of connect. Press Ctrl+] to detach; the VM keeps running. If the console closes from the other end (the VM stopped), gxctl says Console closed.

connect works over the local socket on the host and, after gxctl login, from another machine over HTTPS (see Logging in). On a cluster it reaches VMs on any node.

connect refuses when the VM has no running instance: start it first.

Several clients

Any number of clients can be connected to one VM at the same time: browser tabs, gxctl sessions, or both. They all see the same output, and what any of them types goes to the same serial port. A client that falls far behind (several MiB of output it hasn’t read) is disconnected; it can reconnect and replay the log.

The console log

Everything the guest prints on the console is written to a log on the VM’s host, from the first firmware output on, whether or not anyone is connected. Glidex adds a line when each run of the VM starts and ends, for example:

--- glidex: instance <id> started 2026-10-17T09:12:03Z ---
...
--- glidex: instance <id> exited: clean_exit ---

The log is kept across stops and starts, and when the control plane restarts. When it reaches its size limit (16 MiB by default; an administrator can change it), it is rotated: the previous log is kept, and older output is dropped.

Read the log without connecting:

gxctl> log my-vm              # the last 1 MiB of the current log

With the API, GET /vms/{id}/console/log returns the raw bytes: the last 1 MiB by default, ?tail_bytes=<n> for less, and ?previous=true for the rotated log. The web UI has no log view of its own; opening the console replays the current log.

After the guest exits

When the guest powers off or the hypervisor exits, the exit line is logged and live output stops. Until the control plane notices the exit, a client can still connect and replay the log; then the console closes, connect says the VM is not running, and the browser console reports an error. The log stays readable with log or the API until the VM is deleted.

API

The console is a WebSocket at GET /vms/{id}/console/ws: binary messages carry the console’s bytes in both directions. Browsers first get a single-use ticket (POST /vms/{id}/console/ticket, valid for 30 seconds) and pass it as ?ticket=; clients with an API token or on the local socket don’t need one. See Console WebSocket.

Usage

Glidex meters what VMs, disks, images and networks use: running time, CPU, memory, disk space, disk I/O and network traffic. It keeps the figures by the hour and reports them per project, VM, disk, NIC, network or node, by hour, day or billing month. You can also see a VM’s current rates and its last day of activity.

Who sees what:

  • Anyone with a role in a project (viewer and up) sees that project’s usage, and the usage of its VMs and disks.
  • The host roles auditor and system-admin see every project, including deleted ones, and host-wide figures such as stored images.

How it is measured

The control plane samples every running VM, every disk and every network every 30 seconds (an administrator can change the interval), and adds what it saw to hourly records. An hour is closed a couple of minutes after it ends; until then its figures are provisional. Reports say how far they are complete (Complete through in the web UI, complete through in gxctl).

Usage keeps accruing while the control plane restarts: the next sample covers the gap, spread over the time it lasted.

A billing month is a calendar month in the billing time zone, UTC unless an administrator set another (a fixed, whole-hour offset).

Hourly records are kept for 90 days, then as daily totals for 5 years; the 5-minute figures behind the percentiles are kept for 100 days. Administrators can change these.

Some meters are derived when you read them:

The per-VM and per-network views of traffic differ on purpose: a frame from one VM to another on the same network counts for both VMs, but once for the network. A VM or a project is charged by its own NICs (net.bytes).

Only NAT networks split external from internal traffic; on bridged and isolated networks the ext meters are absent, not zero.

A row can carry flags: provisional (its hour isn’t closed yet), revised (corrected after the hour closed), interpolated (spread over a gap between samples), reset (a counter went backwards), incomplete (usage was lost, for example at a host reboot), source_proc (CPU and memory read from /proc instead of the VM’s cgroup), ext_gap (external traffic may be short) and network_total_unavailable (a provider network has per-VM figures but no network total).

Rates and percentiles

For bandwidth, disk I/O, and CPU and memory, Glidex also keeps a 5-minute average per VM, NIC, disk and network, and reports per billing month:

  • the average;
  • the peak: the busiest sample interval (30 seconds by default);
  • the 95th percentile (p95) of the 5-minute averages, over the slots the subject was running.

Billable bandwidth is the larger of in and out; billable disk I/O is read + write. CPU is reported in cores and as a share of the VM’s vCPUs, memory in MiB and as a share of its size; both include the hypervisor’s own overhead, so they can pass 100 %. Disk latency isn’t available on Cloud Hypervisor.

Once a month is over, its percentiles are stored and no longer change.

Operator guide

This guide is for the people who install and run Glidex: they set up hosts, decide who may log in and what they may do, connect VMs to the network, join hosts into clusters, and keep it all running. Using VMs, disks and networks inside a project is in the User guide.

Components

On every host, the installer sets up these systemd units:

Installation

glidex-install installs Glidex and everything it needs on one host, and brings an existing install up to date. Run it again at any time: it only changes what is missing or outdated.

Requirements

  • Linux on x86_64 or aarch64, with KVM enabled (/dev/kvm). QEMU is installed on x86_64 only; on aarch64 VMs run on Cloud Hypervisor.
  • systemd, for the services. Without it the installer still builds and installs the binaries, and you start them by hand.
  • A package manager the installer knows: apt-get, dnf, yum or pacman.
  • sudo rights. Run the installer as your normal user; it asks for your sudo password when it first needs root.
  • git and a Rust toolchain (cargo) to build and run the installer itself. The installer keeps Rust up to date with rustup afterwards.
  • Internet access to the distribution’s package mirrors and to GitHub (Cloud Hypervisor, its firmware, Bun). Every download that isn’t a distribution package is checked against a pinned SHA-256 before use.

If /dev/kvm is missing, the installer says how to enable it (CPU virtualization in the firmware setup, then modprobe kvm_intel or kvm_amd) and carries on; no VM can start until it is there.

Install

git clone https://github.com/CMKL-APEX/glidex.git && cd glidex
cargo run -p glidex-install

The installer prints its plan, then:

  1. Installs or updates system packages: build tools, OpenSSL headers, the disk and cloud-init tools (qemu-img, sgdisk, growpart, mkdosfs, mtools), QEMU and OVMF, setcap, and OVN and conntrack for cluster networks.
  2. Installs Rust (if missing) and a pinned Bun release, then builds the Glidex binaries and the web UI.
  3. Creates the service users and groups (see Users and groups).
  4. Installs a pinned Cloud Hypervisor release and its UEFI firmware.
  5. Sets up VM networking: Open vSwitch and glidex-netd (see Host networking).
  6. Writes the systemd units and configuration files, then starts or restarts the services.

At the end it prints where the web UI and the API are, and the SHA-256 fingerprints of their certificates:

     web UI:  https://<host>:5173
     API:     /run/glidex-cp/api.sock (members of glidex-users), https://<host>:8841 (tokens)
     web UI certificate SHA-256: <fingerprint>
     API certificate SHA-256: <fingerprint>

Compare these with what your browser shows before you accept the certificate warning (see TLS certificates).

The installer added you to glidex-users and glidex-admin. Log out and back in so your session has the new groups, then check:

systemctl status glidex-control-plane glidex-ui glidex-authd.socket
gxctl whoami

The installer does not change the firewall. Open what remote clients need: TCP 5173 for the web UI, 8841 for the API (remote gxctl and API clients), and 8842 between the nodes of a cluster.

Updating

Pull the new source and run the installer again:

git pull
cargo run -p glidex-install

It updates system packages that came from its own list, Rust, Bun, Cloud Hypervisor, the binaries and the UI, and restarts the services whose binary or unit changed. Running VMs keep running across a control plane restart: each runs in its own glidex-vm@<id> unit. A running VM keeps the Cloud Hypervisor binary it started with until it is restarted.

If something else listens on port 8841 or 5173 (a control plane or UI you started by hand), the installer leaves the service stopped and tells you how to start it once the port is free.

Uninstall

See what would be removed, then remove it:

cargo run -p glidex-install -- uninstall --dry-run
cargo run -p glidex-install -- uninstall

The uninstaller stops every VM (each gets its power button and grace period), the services and glidex-netd; tears down Glidex host networking (uplinks give the host’s address back to its NIC, NAT, bridges and VM ports are removed); then removes the units, binaries, installer-written configuration, runtime directories, the users and the groups. Kernel settings the installer changed go back to their previous values.

By default it keeps your data and site configuration, and says so:

  • /var/lib/glidex-control-plane and ~/.glidex (VM database, credentials, images, disks, firmware);
  • your files in /etc/glidex (control-plane.json, netd.json, policies, certificates);
  • a locally edited /etc/pam.d/glidex;
  • Open vSwitch, its DPDK settings and the hugepages they need, and the cloud-hypervisor binary.

Configuration

The control plane reads /etc/glidex/control-plane.json at start. The file is optional: without it every setting has its default, and that is how the installer leaves a host. /etc/glidex/control-plane.json.example lists every top-level setting with its default; copy it to start:

sudo install -m 0640 -o root -g glidex \
  /etc/glidex/control-plane.json.example /etc/glidex/control-plane.json
sudoedit /etc/glidex/control-plane.json
sudo systemctl restart glidex-control-plane
  • Keep the file root:glidex, mode 0640: the control plane (user glidex) must be able to read it, nobody else needs to.
  • Changes take effect on restart. Restarting the control plane leaves running VMs running.
  • The file is checked strictly. An unknown key (a typo), a wrong type or a value out of range stops the control plane with a message naming the setting; it never falls back to defaults. Read it with journalctl -u glidex-control-plane -b.
  • Every key is optional. A section you leave out, or a key inside one, keeps its default.
  • The file holds no secrets. TLS keys, the OIDC client secret and the secrets key are given to the service as systemd credentials (see Secrets).

TLS certificates

The control plane API (port 8841) and the web UI (port 5173) serve HTTPS on every address of the host. Each uses a self-signed certificate unless you give it your own. Local gxctl users on the Unix socket don’t use TLS at all.

Self-signed certificates

On first start, the control plane and the web UI each generate a certificate (ECDSA P-256, valid for five years) for this host’s names and addresses: its fully qualified name, its host name, localhost, the loopback addresses and the addresses of its interfaces at that moment.

ServiceCertificateKey
Control plane/var/lib/glidex-control-plane/.glidex/tls/cp.crtcp.key next to it, mode 0600
Web UI/var/lib/glidex-ui/tls/ui.crtui.key next to it, mode 0600

A certificate is kept as long as it loads and is valid for more than 30 more days, so its fingerprint stays the same for the clients that trust it. It is regenerated when it is missing, unreadable or close to expiry.

Fingerprints

Browsers warn about a self-signed certificate. Before you accept it, compare the SHA-256 fingerprint the browser shows with the one the service printed:

  • the installer prints both at the end of every run;

  • the control plane logs it at every start (SHA-256: line):

    journalctl -u glidex-control-plane -b | grep SHA-256
journalctl -u glidex-ui -b | grep fingerprint

  • or compute it from the certificate:

    openssl x509 -in /run/glidex-cp/tls.crt -noout -fingerprint -sha256
sudo openssl x509 -in /var/lib/glidex-ui/tls/ui.crt -noout -fingerprint -sha256

/run/glidex-cp/tls.crt is a public copy of the API’s certificate (never the key) that the control plane writes at every start, for local clients to trust.

New names or addresses

A self-signed certificate only covers the names and addresses the host had when it was made. After you rename the host or give it a new address clients will use, generate new ones:

sudo systemctl stop glidex-ui glidex-control-plane
sudo rm /var/lib/glidex-control-plane/.glidex/tls/cp.{crt,key} \
        /var/lib/glidex-ui/tls/ui.{crt,key}
sudo systemctl start glidex-control-plane glidex-ui

The fingerprints change: tell your users, and update gxctl profiles that pinned the old one (see gxctl). Running VMs are not affected.

Your own certificate

Use a certificate from your CA for anything users reach over the network. Put the files somewhere outside /home, for example /etc/glidex/tls/; the certificate must be readable by the service’s user, the key only by root:

sudo install -d -m 0755 /etc/glidex/tls
sudo install -m 0644 glidex.crt /etc/glidex/tls/glidex.crt   # chain, leaf first
sudo install -m 0600 glidex.key /etc/glidex/tls/glidex.key

The certificate must name what users type: the host’s DNS name (and its address, if they use it).

API (control plane)

In /etc/glidex/control-plane.json:

{ "tls": { "cert": "/etc/glidex/tls/glidex.crt" } }

Give the key as the tls-key credential:

sudo systemctl edit glidex-control-plane

[Service]
LoadCredential=tls-key:/etc/glidex/tls/glidex.key

sudo systemctl restart glidex-control-plane

tls.key can name the key file instead, but then it must be readable by the glidex user; the credential keeps it root-only.

Web UI

sudo systemctl edit glidex-ui

[Service]
Environment=GLIDEX_UI_TLS_CERT=/etc/glidex/tls/glidex.crt
LoadCredential=ui-tls-key:/etc/glidex/tls/glidex.key

sudo systemctl restart glidex-ui

With a configured certificate the UI also sends Strict-Transport-Security.

If users reach the UI under a name that isn’t one of the host’s own, also set GLIDEX_UI_HOSTS and auth.allowed_origins (see Configuration).

Renewing

Neither service watches the files. Replace them, then restart the service; running VMs keep running:

sudo systemctl restart glidex-control-plane glidex-ui

Plain HTTP

"tls": "off" (API) and GLIDEX_UI_TLS=off (UI) serve plain HTTP, and are refused unless every listener is a loopback address:

{ "tls": "off", "listen": ["127.0.0.1:8841", "[::1]:8841"] }

Use this only behind something on the same host that terminates TLS. On its HTTPS port the web UI answers a plain-HTTP request with a redirect to https://.

Client trust

Browsers

With a CA-issued certificate, browsers need nothing. With the self-signed one, users compare the fingerprint once and accept it.

gxctl

On the host itself, gxctl uses the Unix socket and needs no certificate. Over TCP to a loopback address it trusts the published /run/glidex-cp/tls.crt automatically.

From another machine, gxctl trusts the system’s CA store. For a self-signed certificate, either:

  • copy the host’s /run/glidex-cp/tls.crt (it is public) and point GLIDEX_CA_CERT at it:

    export GLIDEX_CA_CERT=~/glidex-lab.crt
gxctl --url https://glidex.example.org:8841 login --oidc

  • or let a login profile pin the certificate. gxctl auth login shows the fingerprint of a certificate it doesn’t trust and asks whether to trust exactly that one; compare it with the one the control plane printed. Non-interactively, pass the fingerprint you checked:

    gxctl auth login --url https://glidex.example.org:8841 --profile lab \
  --pin sha256/<fingerprint> --oidc

    A pin trusts that one certificate; dates and the host name are still checked. When the certificate changes, gxctl refuses to connect rather than ask again. Once you have confirmed the new fingerprint through another channel:

    gxctl auth login --profile lab --pin sha256/<new-fingerprint> --rebind

    gxctl auth trust list shows a profile’s pins and CA, gxctl auth trust fetch compares the fingerprint the server reports with the certificate it presents.

Prefer a CA-issued certificate, or a pin, over any option that turns verification off. See the gxctl reference for login profiles.

API clients

Give clients the certificate to trust, for example with curl:

curl --cacert glidex-lab.crt -H "Authorization: Bearer $GLIDEX_TOKEN" \
  https://glidex.example.org:8841/auth/whoami

Clusters

Nodes of a cluster talk to each other on port 8842 with mutual TLS under the cluster’s own CA, which Glidex manages. That is separate from the certificates on this page; see Clusters.

Authentication

Every request to the control plane is authenticated, on every listener. How depends on where it comes from:

ClientHow it is identified
gxctl on the host, on /run/glidex-cp/api.sockThe caller’s Unix account, from the socket. No login.
Web UIA browser session, after a login with a local password or single sign-on.
gxctl from another machine, scripts, API clientsAn access token (Authorization: Bearer …).

What an authenticated user may then do is decided by roles and policies: see Access control.

The local socket

The control plane listens on /run/glidex-cp/api.sock. It reads the caller’s user id from the socket itself and looks up their groups on every request:

  • members of glidex-users (users_group) are let in as themselves;
  • root and members of glidex-admin (admin_group) are break-glass administrators: they may do anything, whatever the roles and site policies say;
  • everyone else is refused.

A local user gets a Glidex user the first time they use the socket. Their Unix groups count as teams named unix:<group> for requests on the socket, so a role can be given to a whole Unix group (see Access control).

Adding someone to a group takes effect on their next request:

sudo usermod -aG glidex-users alice

/run/glidex-cp/ui.sock is the web UI’s: only the glidex-ui user may use it, and it carries the browser’s session, never rights of its own.

Local accounts

People in glidex-users can log in to the web UI with their Unix user name and password. The control plane doesn’t read passwords itself: it asks glidex-authd, a small root helper that checks them with PAM.

  • glidex-authd.socket listens on /run/glidex-authd/auth.sock; systemd starts glidex-authd.service on the first login.
  • It answers only the glidex user (the control plane).
  • It uses the PAM service /etc/pam.d/glidex, which includes the system’s normal authentication and account checks (common-auth and common-account on Debian and Ubuntu, system-auth elsewhere).
  • Every failure is answered after a fixed delay, and repeated failures are rate-limited per user and overall.

The installer manages /etc/pam.d/glidex while it contains the line Managed by glidex-install. Delete that line to keep your own edits; later installs and the uninstaller then leave the file alone. PAM stacks that need network access from the helper itself (LDAP or RADIUS without sssd) or setuid helpers are not supported.

Who may log in

Two lists must both allow a user, and should match:

  • allowed_groups in /etc/glidex/authd.json (the helper’s own);
  • auth.pam.allowed_groups in /etc/glidex/control-plane.json.

Both default to ["glidex-users"]. To let a second group log in:

{ "service_user": "glidex", "allowed_groups": ["glidex-users", "lab"] }

{ "auth": { "pam": { "allowed_groups": ["glidex-users", "lab"] } } }

sudo systemctl restart glidex-authd.service glidex-control-plane

/etc/glidex/authd.json:

KeyDefaultMeaning
service_user"glidex"The only user allowed to ask.
allowed_groups["glidex-users"]A user must be in one of these groups.
failure_delay_ms1000Delay before every failure answer.
max_connections8Connections served at once.
allow_rootfalseAlso answer root. For debugging only; leave it off.

The rest of the PAM settings are in auth.pam (see Configuration): enabled turns password logins off, jit: false stops new users from being created at their first login, and group_teams maps Unix groups to Glidex teams, updated at every login.

A user’s local account and their password logins are the same Glidex user. In a cluster, local accounts are per node (alice on one node is not alice on another) unless cluster.shared_local_accounts is set.

Single sign-on (OIDC)

Glidex logs users in through any OpenID Connect provider, with the authorization code flow (PKCE) in the browser and the device authorization grant for gxctl.

  1. Register Glidex with the provider as a confidential web client:

    • redirect URI: https://<ui-host>:5173/api/auth/oidc/callback, with the name users type to reach the web UI;
    • grant types: authorization code, and device code if gxctl users should log in with it;
    • make the provider put the user’s groups in the ID token (a groups claim) if you use required_groups or group_teams.

  2. Put the client secret in a root-only file and hand it to the service as a credential:

    sudo install -m 0600 /dev/null /etc/glidex/oidc-client-secret
sudoedit /etc/glidex/oidc-client-secret       # paste the secret
sudo systemctl edit glidex-control-plane

    [Service]
LoadCredential=oidc-client-secret:/etc/glidex/oidc-client-secret

  3. Configure auth.oidc in /etc/glidex/control-plane.json:

    {
  "auth": {
    "allowed_origins": ["https://glidex.example.org:5173"],
    "oidc": {
      "enabled": true,
      "issuer": "https://idp.example.org",
      "client_id": "glidex",
      "redirect_uri": "https://glidex.example.org:5173/api/auth/oidc/callback",
      "required_groups": ["glidex-users"],
      "group_teams": { "lab-staff": "staff" }
    }
  }
}

  4. Restart: sudo systemctl restart glidex-control-plane. The login page now has a Sign in with Single sign-on button.

Set redirect_uri explicitly: by default it is built from the first of auth.allowed_origins, which, when that list is empty, is the host’s own name. The issuer must be an https:// URL; the control plane fetches its discovery document and keys from it, so it needs outbound HTTPS to the provider.

Who gets in:

  • required_groups: only members of one of these groups (from groups_claim). Empty lets in everyone the provider authenticates for this client, so set it, or restrict the client at the provider.
  • allowed_domains: only users whose email is in one of these domains.
  • jit: false: only people who already have a Glidex user.

group_teams maps provider groups to Glidex teams, which must exist (gxctl team create staff); memberships are updated at every login. Users are identified by the provider’s issuer and subject, never by email or name.

From another machine:

gxctl --url https://glidex.example.org:8841 login --oidc

gxctl prints a code and a URL to open in a browser, then saves a token valid for one day.

Login connectors

Each way to log in is a login connector. auth.pam and auth.oidc above appear as the connectors file-pam and file-oidc; they can only be changed in the file. Directory administrators can add more PAM and OIDC connectors, for example a second identity provider, from the web UI’s Connectors page or with gxctl connector:

gxctl connector add oidc corp --issuer https://login.example.com \
  --client-id glidex --name "Example Corp" --require-group glidex-users \
  --team lab-staff=staff
gxctl connector secret set corp                 # hidden prompt
gxctl connector secret set corp --from-file /path/to/secret
gxctl connector test corp
gxctl connector list
  • Each OIDC connector gets its own button on the login page, and its own redirect URI: https://<ui-host>:5173/api/auth/c/<id>/callback.
  • Secrets are read from a hidden prompt, standard input or a file, never the command line, and are never shown again. They are stored encrypted with the host’s secrets key (secrets.kek beside the database, or the secrets-kek credential); back that key up with the database.
  • --mfa admits only logins the provider reports as multi-factor (amr contains mfa, or acr is one of the --mfa-acr values).
  • --token-max-days N caps the tokens a login through the connector mints (default 30 days).
  • --jit / --no-jit, --require-group, --team GROUP=TEAM and --domain work as in the file settings.
  • --default-tenant <t> makes new users members of tenant <t>. If that is the admin tenant or another operator tenant, a connector that creates users must also have --require-group.
  • Changing a connector needs a recent login (see Sessions and re-authentication).

Run gxctl connector without arguments for every option.

Access tokens

Tokens are for gxctl on other machines, scripts and API clients. A token is shown once, when it is made; Glidex keeps only a hash of it.

  • A token lives auth.tokens.default_days (90) unless --days says otherwise, and at most auth.tokens.max_days (365).
  • gxctl login --oidc gets a token valid for one day; gxctl auth login --pam-user <user> one capped by its connector (30 days by default).
  • Clients send it as Authorization: Bearer <token>; gxctl reads it from GLIDEX_TOKEN or the file gxctl login --token saved (~/.config/glidex/token, mode 0600).

Sessions and re-authentication

A web UI login starts a session, kept in a cookie. It ends after auth.session.idle_minutes (30) without a request, or auth.session.absolute_hours (12) after login, whichever comes first, or when the user signs out.

Some actions need a login in the last 10 minutes:

  • writing site policies;
  • adding, changing or removing login connectors and their secrets;
  • managing admissions and deleting tenants;
  • host network changes that can cut the host off (installing Open vSwitch, DPDK, committing or removing uplinks, deleting bridges);
  • cluster membership and recovery (joining, join tokens, removing nodes, CA and secrets key rotation, OVN settings).

In the web UI, such an action opens a “This action needs a recent login” dialog; after signing in again the request goes through. On the local socket a request always counts as fresh. A personal token acting only as its owner never does: run those actions from the web UI, from the host’s socket, or with a token that has its own roles.

Who is logged in

gxctl whoami          # method, teams, roles
gxctl user list       # every user and their identities

The audit log records every login, write and denied request (see Access control).

Access control

Once a request is authenticated, Glidex decides whether it is allowed with Cedar policies. You rarely write policies yourself: you give people roles through bindings, and the shipped policies turn those into decisions. Site policies add rules on top when roles aren’t enough.

The pieces:
UsersPeople, from the local socket, a password login or single sign-on.
TeamsGroups of users. A role given to a team applies to its members.
TokensPersonal tokens act for their owner; service-account tokens have their own roles (see Access tokens).
ProjectsHold VMs, disks, credentials and project networks, with quotas.
TenantsOwn projects. A host has tenant admin, which operates the host, and tenant default, which holds the projects.
BindingsA role, given to a user, team or token, on a project, a tenant or the host.
PoliciesBase policies and role definitions shipped with Glidex, plus your site policies.

Concepts explains projects and tenants for users; Projects covers working inside one.

Safe defaults

Out of the box:

  • Nobody can do anything without a role, except read the image catalog and network names, and manage their own tokens.
  • Root and members of glidex-admin on the local socket are break-glass administrators: always allowed, whatever the bindings and site policies. Use it to recover, not for daily work.
  • A VM only uses disks and credentials of its own project, and only networks its project was granted. No role or site policy can change that.
  • A disabled user and an expired token are refused everything.
  • Changes that can cut a host off, and policy writes, need a recent login (see Sessions and re-authentication).

The first administrators

On its first start the control plane makes every member of glidex-admin (the installer adds you) a Glidex administrator:

  • system-admin on the host;
  • owner of the default project;
  • member of the admin tenant, tenant-admin of admin and default, and directory-admin of the host’s directory.

It does this only while nobody has system-admin, so adding people to glidex-admin later makes them break-glass users on the socket, but gives them no roles in the web UI. Give roles instead.

Giving roles

Bindings name a principal as user:<id>, team:<id> or token:<id>. Find ids with gxctl user list, gxctl team list and gxctl token list.

On a project (also on the project’s page in the web UI):

gxctl binding add web editor user:3f0c…
gxctl binding add web operator team:<team-id>
gxctl binding list web
gxctl binding remove web <binding-id>

On the host (the web UI’s Access page, System roles). The person must be in the admin tenant first:

gxctl tenant add-member admin user:3f0c…
gxctl system-binding add net-admin user:3f0c…
gxctl system-binding list
gxctl system-binding remove <binding-id>

On a tenant:

gxctl tenant bind default tenant-admin user:3f0c…
gxctl tenant bindings default

A binding takes effect at once, on every server of a cluster.

Teams

gxctl team create staff
gxctl team add-member staff <user-id>
gxctl team remove-member staff <user-id>

Teams can also be filled from outside:

  • group_teams of a login connector maps a Unix or identity provider group to a team; the user’s membership is updated at every login. Memberships you added by hand are left alone.
  • On the local socket, each of the caller’s Unix groups is a team unix:<group>. Bind it to give a whole Unix group a role for gxctl on the host: gxctl binding add web operator team:unix:lab. It applies only to requests on the socket.

Tenants and admissions

On one host the tenants are mostly bookkeeping: default holds the projects, admin operates the host. You can add tenants to keep groups of projects apart: a tenant’s members only reach its own projects, and a tenant only allocates on a host that admits it, within its cap.

gxctl tenant create research --name "Research group"
gxctl admission set research vms=20 memory_mib=131072
gxctl admission list
gxctl tenant list

The web UI has Tenants and Admissions pages for the same.

Quotas

Each project has quotas: vms, vcpus, memory_mib, disk_gib, running_vms, networks, plus routers and external_ips for cluster networks. New projects get quotas.default from control-plane.json (by default 2 networks, 1 router, 1 external address, the rest unlimited). Tenant administrators change them:

gxctl project quota web vms=10 vcpus=32 memory_mib=none
gxctl project show web

none means unlimited. A request that would go over a quota is refused, except from a system-admin, whose overruns are recorded in the audit log.

Site policies

Site policies are Cedar policies you add. They can:

  • forbid something roles would allow. A forbid always wins.
  • permit something no role covers.

They cannot relax the base policies: those are forbids too.

Writing one

Each site policy is one Cedar policy whose @id starts with site. followed by 1–64 of a-z, 0-9, ., _, -. It uses the Glidex namespace. For example, refuse consoles over the network unless the login was multi-factor:

@id("site.console-needs-mfa")
forbid (principal, action == Glidex::Action::"openConsole", resource)
when { context.auth.transport == "tcp" && !context.auth.mfa };

Or protect one project’s VMs from deletion:

@id("site.prod-no-delete")
forbid (principal, action == Glidex::Action::"deleteVm", resource)
when { resource.project == Glidex::Project::"<project-id>" };

What a policy can look at:

  • principal: a Glidex::User, Glidex::Team (via in) or Glidex::Token;
  • action: one action per API operation, such as openConsole, createVm, deleteVm, startVm, stopVm;
  • resource: the object, such as a Glidex::Vm (with .project) or a Glidex::Project;
  • context.auth: method (peer, pam, oidc, token), transport (unix, tcp), age_secs since login, mfa, and source_ip for TCP clients;
  • context.project, context.tenant where the action has one.

Every policy is validated against the schema before it is accepted; the validation errors name what is wrong. The Policies page in the web UI lists the base policies, role definitions and site policies with their full text, as a reference.

Applying it

Site policies need system-admin and a recent login. From the web UI’s Policies page: + New site policy, write it, Validate, then Simulate to compare decisions for sample requests under the current policies and with your draft, then Save. With gxctl:

gxctl policy validate site.console-needs-mfa console.cedar
gxctl policy put site.console-needs-mfa console.cedar --description "MFA for consoles"
gxctl policy list
gxctl policy show site.console-needs-mfa
gxctl policy put site.console-needs-mfa console.cedar --disable   # keep, but not in force
gxctl policy history site.console-needs-mfa
gxctl policy delete site.console-needs-mfa
  • A change applies at once, on every server of a cluster.
  • Each save is a new version; authz.policy_history (50) versions of each are kept.
  • There can be at most 200 site policies, each at most 64 KiB.

would_lock_out

Glidex refuses a policy change that would leave you unable to manage policies, with 409 would_lock_out (“after this change you could no longer manage policies”). Fix the policy so it doesn’t forbid you, for example by excluding a team of administrators, and try again.

If you do lock yourself, or everyone, out, a break-glass administrator on the host’s socket can still undo it; site policies don’t apply to them:

sudo gxctl policy delete site.too-broad

Policy files

Site policies can also be files, for sites that manage configuration with their own tools. Put *.cedar files in authz.policy_files_dir (/etc/glidex/policies, root:glidex, mode 0750). A file may hold several policies; each needs its own @id("site.…"), and an id can’t be used by a file and the API at the same time. File policies show in gxctl policy list and the web UI as read-only.

The control plane reads the files at start. Check a policy before you put it there (validate takes one policy at a time), then reload after changing the directory:

gxctl policy validate site.lab-rules lab-rules.cedar
sudo install -m 0640 -o root -g glidex lab-rules.cedar /etc/glidex/policies/
gxctl policy reload

If a file doesn’t parse or validate, reload fails and the policies in force stay as they were; at start, the control plane stops with the error.

Audit log

Glidex records every write, every login and every denied request: who, from where, the action, the target, the result and the policies that decided it. Read it from the web UI’s Audit page or:

gxctl audit --limit 50
gxctl audit --project web
gxctl audit --user <user-id> --since 1767225600000   # Unix milliseconds

auditor and system-admin read all of it; a project’s owners read their project’s. Entries older than audit.retention_days (90) are deleted. Each entry is also written to the control plane’s journal:

journalctl -u glidex-control-plane | grep glidex_audit

Ship the journal to your log system if you need the trail kept longer or out of the host’s reach.

Host networking

VM networking on a Glidex host runs on Open vSwitch (OVS). The control plane never touches the host’s network itself: it asks glidex-netd, a small root helper, to create bridges, NAT, uplinks and VM ports. This page covers the host side: installing OVS, choosing a datapath, bridges, uplinks, NAT networks, and the host’s part in cluster networks on OVN. Creating networks for VMs is in Networks.

Host networking needs the net-admin role (or system-admin). On the local socket, members of glidex-admin have it.

Everything here acts on the host that serves the request: the one whose socket gxctl uses, or whose web UI you opened. A cluster agent has no local API for gxctl; manage its host networking from the web UI it serves (https://<agent>:5173), which runs these requests on the agent.

Pieces

PieceWhat it does
glidex-netd.serviceRoot helper. Owns glidex’s bridges, NAT (address, nftables, dnsmasq), uplinks and VM ports. State in /var/lib/glidex/netd.db, sockets in /run/glidex/.
Open vSwitchThe switch. Distribution packages, or a pinned source build for DPDK.
dnsmasqDHCP (and DNS) for NAT networks, one instance per network.
OVN (clusters)Cluster networks that span nodes. Installed by default, off until the host is in a cluster.

glidex-netd starts before the control plane. At start it re-creates glidex’s bridges, re-binds DPDK NICs to vfio-pci, re-applies uplinks that carry the host’s address, and restores NAT, then reports ready.

The control plane talks to netd’s full socket as the glidex group. If it can’t, its startup line says Checking networking... LIMITED or UNAVAILABLE, and the web UI’s Networking page shows a warning instead of the OVS status.

Install Open vSwitch

The installer sets up OVS, glidex-netd and the host settings NAT needs (IP forwarding) unless you pass --no-networking. Pick the profile at install time; it is remembered for later runs:

cargo run -p glidex-install                        # kernel datapath (default)
cargo run -p glidex-install -- --ovs-profile dpdk  # DPDK: reserves hugepages and PMD cores

With --ovs-profile dpdk, --pmd-cpu-mask MASK sets the OVS-DPDK PMD CPU mask (hex; auto clears it). If OVS already has bridges, the installer won’t restart ovs-vswitchd unless you pass --allow-ovs-restart. See Installation for the other options.

You can also install or switch the profile on a running host, from the web UI (Networking → Install Open vSwitch or Install / switch profile) or gxctl:

gxctl ovs status                           # netd access, OVS version, what this host can do
gxctl ovs install --profile dpdk           # --force if it must restart a running OVS
gxctl ovs install --profile dpdk --source  # the pinned source build instead of packages
gxctl ovs dpdk-init --socket-mem 1024 --pmd-cpu-mask 0x6   # enable DPDK in ovs-vswitchd (restarts it)

OVS 3.0 or newer is required. Restarting OVS interrupts traffic on its bridges, so both the UI and gxctl ask for confirmation first (--force in gxctl).

Datapaths and NIC types

OVS forwards packets either in the kernel (system datapath) or in userspace (netdev, with DPDK or AF_XDP). A VM’s NIC is either a tap device or a vhost-user socket. Not every mix works; gxctl ovs status and the Networking page list the combinations and what each is missing on this host:

IdCombinationNeeds
Akernel datapath, tap VM ports (NAT or kernel uplink)OVS running; cap_net_admin on cloud-hypervisor (the installer sets it)
Buserspace datapath, DPDK uplink, vhost-user VM portsthe dpdk profile, DPDK initialized, IOMMU, hugepages
Cuserspace datapath, AF_XDP uplink, vhost-user VM portsas B, plus OVS with AF_XDP support
Duserspace datapath, AF_XDP uplink, tap VM portsOVS with AF_XDP support

In short:

  • tap is the default and works everywhere. Use it unless you need DPDK.
  • vhost-user needs the dpdk profile. Guest memory is shared with OVS automatically. Choose it per network (--vhost-user, or VM port: vhost-user (DPDK) in the network form).

The dpdk profile needs the IOMMU on (intel_iommu=on or amd_iommu=on on the kernel command line, and VT-d / AMD-Vi in the firmware). The installer reports a missing IOMMU but doesn’t change the kernel command line.

Bridges

A NAT or isolated network gets its own bridge, named gxbr-<first 8 characters of the network id> unless you name it. A bridged network, and an uplink, use a bridge you create first.

Create a bridge in the web UI: Networking → glidex bridges → + New bridge, with a name and a datapath:

  • kernel (system): for kernel uplinks, and for an OVN gateway’s physical network.
  • userspace (netdev, DPDK): for AF_XDP and DPDK uplinks.

Over the API:

api -X POST https://localhost:8841/ovs/bridges \
  -H 'Content-Type: application/json' \
  -d '{"name": "gxbr-up", "datapath": "DATAPATH_SYSTEM"}'

(api is the curl wrapper from the REST API page.)

gxctl bridges lists glidex’s bridges with their datapath and port count; one marked MISSING on host exists in netd’s records but not in OVS. Glidex only touches bridges it owns, never ones you made with ovs-vsctl yourself.

Uplinks

An uplink connects a glidex bridge to the physical network through one of the host’s NICs. There are three kinds:

KindBridge datapathNIC
Kernelkernel (system)stays a kernel interface (eno1)
AF_XDPuserspace (netdev)stays a kernel interface; OVS reads it through AF_XDP
DPDKuserspace (netdev)leaves the kernel: bound to vfio-pci, named by PCI address

Add one from the web UI (Networking → a bridge → Add uplink…) or gxctl:

gxctl uplink-add gxbr-up --kernel eno2
gxctl uplink-add gxbr-fast --afxdp enp65s0f0 --xdp-mode native --rxq 4
gxctl uplink-add gxbr-fast --dpdk 0000:41:00.0 --name up0 --rxq 2
gxctl uplinks gxbr-up                # list a bridge's uplinks
gxctl uplink-rm gxbr-up eno2         # remove it; the NIC is restored

--xdp-mode is best_effort (default), native, native_with_zerocopy or generic. --rxq is 1–64. A NIC used by a DPDK uplink can’t also be passed through to a VM.

Moving the host’s address onto the bridge

If the host itself uses the NIC (it carries the host’s address or default route), adding it as a plain uplink would cut the host off, so it is refused with host_interface_in_use. Move the NIC’s addresses and routes to the bridge instead:

gxctl uplink-add gxbr-up --kernel eno1 --migrate-ip --force

In the web UI, tick The host uses this NIC: move its address and routes to the bridge.

The move is checked twice before it sticks:

  1. glidex-netd snapshots the NIC’s addresses and routes, moves them to the bridge, and waits up to 20 seconds for the default gateway to answer through the bridge. If it doesn’t, the NIC gets its exact configuration back.
  2. The uplink is then pending_commit. The client (gxctl or the page) checks it can still reach the API and commits. Without a commit within 60 seconds, netd rolls the change back by itself.

So a mistake costs about a minute of connectivity, not the host. Run it from a session that can survive a short interruption all the same.

An address from DHCP is refused, because the DHCP client stays on the NIC and the address may be lost when its lease ends. Give the NIC a static address first, or pass --accept-dhcp (If the address comes from DHCP, move it anyway.) knowingly. DPDK uplinks can’t take the host’s address: the NIC leaves the kernel.

At boot: re-apply or roll back

The host’s own network configuration puts the address back on the NIC at boot. glidex-netd then moves it to the bridge again, with the same gateway check. If moving fails or the gateway doesn’t answer, it gives the NIC its own configuration back and holds the uplink off the bridge, so the host stays reachable.

A held uplink shows held off the bridge on the Networking page, with when and why. gxctl uplinks <bridge> shows its phase and the netd log says IP migration rolled back at start. Fix the cause (a cable, a switch port, the gateway), then re-apply it:

gxctl uplink-reapply gxbr-up eno1

or Re-apply on the page. It goes through the same check and commit as a new uplink.

gxctl uplink-rm on an uplink that carries the host’s address moves the address back to the NIC. Networks on that bridge lose their way out.

NAT networks

A NAT network is a private subnet on its own bridge. glidex-netd puts a gateway address on the bridge, runs dnsmasq for DHCP (and DNS), and masquerades traffic out through whatever route the host already uses. It needs no uplink.

gxctl network-add lab                          # NAT, first free /24 in 10.88.0.0/16
gxctl network-add lab2 --nat --subnet 192.168.50.0/24
gxctl network-add lab-fast --vhost-user        # vhost-user NICs (needs the dpdk profile)
  • The gateway is the subnet’s first address; DHCP hands out the rest. The subnet must be a /29 or larger.
  • A VM keeps its address across restarts (a reservation per MAC).
  • Node NAT networks come from 10.88.0.0/16 by default. To use another range, set nat_supernet in /etc/glidex/netd.json (see Configuration).
  • An isolated network (--isolated) has no way out: its VMs reach only each other.
  • In a cluster with OVN on, network-add makes a cluster network unless you pass --node (a bridge on this host only).

If ufw or firewalld is active, the Networking page warns that it may drop forwarded NAT traffic. glidex-netd adds its own nftables table (glidex) and, where the iptables FORWARD or INPUT policy would drop guest traffic, its own chains (GLIDEX-FORWARD, GLIDEX-INPUT). If guests still get no address or can’t get out, allow the NAT subnets in your firewall.

Bridged networks

A bridged network puts VMs straight on a glidex bridge that has an uplink, so they appear on the physical LAN:

gxctl network-add lan --bridged gxbr-up            # optionally --vlan 20

The bridge must be a glidex bridge. Glidex doesn’t hand out addresses on a bridged network: the LAN’s DHCP server, or a static address in the guest, does.

Clusters: OVN on the host

In a cluster with OVN on, cluster networks span every node: each node is an OVN chassis, VMs on different nodes reach each other through Geneve tunnels, and NAT cluster networks leave through a shared edge on gateway nodes. Turning OVN on and setting the edge is in Clusters. Each node also has host-level settings, on the node’s page (Cluster → a node):

Physical networks

A physical network is a name (for example uplink) for a LAN that some nodes reach. On each node, map the name to the glidex bridge that has the uplink to that LAN. Provider networks (bridged cluster networks) and the shared edge use these names.

On the node’s page, Physical networks → Change…, add rows of physical network → bridge. It applies within half a minute, without a restart. You can also set them in the host’s /etc/glidex/control-plane.json (read when the control plane starts); a mapping set in the UI wins over the file’s:

{
  "cluster": {
    "ovn": {
      "bridge_mappings": { "uplink": "gxbr-up" }
    }
  }
}

The scheduler places a VM on a provider network only on nodes that map its physical network.

The br-int datapath

OVN’s integration bridge, br-int, carries every VM port on cluster networks. On the node’s page, br-int datapath → Change…:

SettingUse
AutomaticUserspace (DPDK) where OVS runs DPDK, else the kernel datapath.
Kernel (system)What a gateway node needs. VMs here get tap NICs on cluster networks.
Userspace (netdev, DPDK)For vhost-user NICs on cluster networks. Needs DPDK; can’t carry a gateway.

The node switches within half a minute, but only while no VM port is on br-int: stop or move the node’s VMs on cluster networks first. A VM with a vhost-user NIC on a cluster network is placed only on nodes whose br-int is userspace.

Gateway (edge) nodes

The shared edge, and each project router with its own outside address, run on gateway nodes. A gateway node must:

  • map the edge’s physical network to a bridge with an uplink to that LAN, and
  • have br-int on the kernel datapath.

Use a kernel (system) bridge for that physical network. Glidex refuses to name a node a gateway that doesn’t meet these.

Removing networking

cargo run -p glidex-install -- uninstall tears down glidex’s host networking with netd’s own code: uplinks put the host’s address back on the NIC and restore NIC drivers, and NAT, bridges and VM ports go. OVS itself stays unless you pass --remove-ovs. See Maintenance.

PCI passthrough

A VM can take a host PCI device (a GPU, a NIC, an NVMe drive) through VFIO. Both hypervisors support it: Cloud Hypervisor with --device, QEMU with -device vfio-pci. Glidex lists the host’s devices, records which VM claims which device, checks who may use it, and hot-plugs it into a running guest.

Glidex does not prepare the host: enabling the IOMMU, binding the device to vfio-pci and giving the glidex user access to it are up to you.

Host prerequisites

IOMMU

Turn on VT-d (Intel) or AMD-Vi (AMD) in the firmware, then on the kernel command line:

intel_iommu=on iommu=pt     # Intel
amd_iommu=on iommu=pt       # AMD (often on by default)

After a reboot, the IOMMU groups exist:

ls /sys/kernel/iommu_groups/

A device can only be passed through with every other device in its IOMMU group (except PCI bridges). gxctl pci shows each device’s group.

Bind the device to vfio-pci

Load the module, and bind the device to it instead of its usual driver. For a device at 0000:41:00.0:

sudo modprobe vfio-pci
echo vfio-pci | sudo tee /sys/bus/pci/devices/0000:41:00.0/driver_override
echo 0000:41:00.0 | sudo tee /sys/bus/pci/devices/0000:41:00.0/driver/unbind
echo 0000:41:00.0 | sudo tee /sys/bus/pci/drivers_probe

This doesn’t survive a reboot. To make it permanent, use your distribution’s way (for example options vfio-pci ids=10de:2204 in /etc/modprobe.d/, with the vendor and device ids from gxctl pci, and vfio-pci in /etc/modules-load.d/). For a GPU, also keep the host’s own driver from claiming it first.

The installer loads vfio-pci at boot only for the dpdk OVS profile (for DPDK NICs); for passthrough, load it yourself.

Let the glidex user open it

VMs run in glidex-vm@<id>.service units as the glidex user. The unit allows the VFIO devices (/dev/vfio/vfio and the per-group /dev/vfio/<group>), but the group device must also be readable and writable by glidex. By default it belongs to root. A udev rule fixes that for every group:

# /etc/udev/rules.d/90-glidex-vfio.rules
SUBSYSTEM=="vfio", GROUP="glidex", MODE="0660"

sudo udevadm control --reload && sudo udevadm trigger --subsystem-match=vfio
ls -l /dev/vfio/

Find devices

gxctl pci                    # every host PCI device: address, ids, class, driver, IOMMU group
gxctl pci 0000:41:00.0       # one device, with its sysfs path

A device ready for passthrough shows the driver vfio-pci and an IOMMU group. Over the API it is GET /pci-devices; listing needs a host role (auditor, net-admin or system-admin). The list is what this host has; in a cluster, a node’s page (Cluster → a node) shows how many PCI devices it reports.

Glidex names a device by its sysfs path, /sys/bus/pci/devices/0000:41:00.0. The API also accepts the bare address 0000:41:00.0 where it checks permissions, but use the full path: it is what Glidex stores and compares.

Who may use a device

Passing a device through needs the usePciDevice permission on it. By default:

  • net-admin and system-admin may use any device.
  • A project may use the devices granted to it in /etc/glidex/control-plane.json, by project or by tenant:
{
  "pci": {
    "allow": [
      { "bdf": "0000:41:00.0", "projects": ["ml-team"] },
      { "bdf": "0000:42:00.0", "tenants": ["research"] }
    ]
  }
}

projects takes project ids or names, tenants tenant ids or slugs. Restart the control plane after changing the file. Site policies can widen or narrow this; see Access control.

Adding a device to an existing VM also needs attachDevice on the VM, and removing one detachDevice (both part of the editor role).

Attach a device

At creation, in the web UI’s VM form, VFIO PCI Devices (optional) takes comma-separated sysfs paths. Over the API, vfio_devices:

api -X POST https://localhost:8841/vms -H 'Content-Type: application/json' -d '{
  "name": "gpu-vm", "vcpu_count": 8, "mem_size_mib": 16384,
  "image": "ubuntu-26.04", "root_disk_size_gib": 40, "credential": "alice",
  "vfio_devices": ["/sys/bus/pci/devices/0000:41:00.0"]
}'

On an existing VM, stopped or running:

gxctl attach-device gpu-vm /sys/bus/pci/devices/0000:41:00.0
gxctl detach-device gpu-vm /sys/bus/pci/devices/0000:41:00.0

Over the API these are POST and DELETE /vms/{id}/devices, or a PATCH of vfio_devices. The VM’s page lists its VFIO PCI Devices.

What happens:

  • A stopped VM gets the device at its next start.
  • A running VM gets it hot-plugged (Cloud Hypervisor’s API, QEMU’s device_add), and hot-unplugged on detach. While the guest is paused, the change waits (the VM shows DevicesPending with reason GuestPaused) and is applied once it runs. If the hypervisor refuses, the VM shows DevicesPending with reason HotplugFailed and the error; stop and start the VM to apply the change at boot.
  • One device belongs to one VM. A second VM asking for it is refused (PCI device … is used by VM …), and the claim lasts until the instance that holds it is gone, not just until the spec drops it.
  • A NIC that is a DPDK uplink of a glidex bridge can’t be passed through.

The guest sees the device on its PCI bus; install the guest driver there as on bare metal.

In a cluster

Devices are per host. The scheduler places a VM with vfio_devices only on a node that reports every one of those devices (otherwise: no PCI device …). If several nodes have a device at the same address, pin the VM to the one you prepared: Placement in the VM form, or node (a node name or id) in the API request. Prepare each host (IOMMU, vfio-pci, the udev rule) the same way.

gxctl pci lists the devices of the host it is connected to. A cluster agent has no local API for gxctl; to list an agent’s devices, use the web UI that agent serves, which runs the request on the agent.

Clusters

Several Glidex hosts can run as one cluster: one API, one set of projects, users and images, and a scheduler that places VMs on the nodes. This page covers forming a cluster, adding and removing nodes, recovery, upgrades, and turning on cluster networks (OVN).

Cluster operations need the system-admin role. On the local socket, members of glidex-admin have it. Most of them (init, join tokens, removals, snapshots, CA rotation, OVN settings) also need a recent login: over TCP or in the web UI, you may be asked to log in again.

Roles and quorum

Every node runs the same software and runs VMs. A node is one of:

  • Server: keeps a copy of the cluster’s database, replicated with Raft, and serves the API. Servers sign node certificates and run OVN’s databases when OVN is on.
  • Agent: only runs VMs. It has no API of its own: gxctl on an agent says so and points you to a server. Its web UI still works; it relays every request to a server, which authenticates it, so you log in there with the servers’ users.

The servers that vote in Raft are voters. A cluster keeps working while a majority of voters is up, so run 1, 3 or 5 servers: 3 survive one lost server, 5 survive two. Glidex refuses changes that leave an even number of voters or no majority, unless you --force the even case.

Nodes talk to each other on TCP 8842 (the node API), with mutual TLS under the cluster’s own certificate authority. The installer doesn’t open firewall ports; see the port list.

Before you start

Install Glidex on every host as in Installation. OVN is installed too unless you pass --no-ovn; its services stay off until the host is in a cluster. Give each host a stable address that the others can reach.

Create a cluster

On the first host, which becomes the first server:

gxctl cluster init --force

--force is required: init re-keys every record for clustering and can’t be undone from Glidex. It keeps a copy of the database first (glidex.db.pre-cluster-<time> in the data directory) and prints the cluster id and the CA’s SHA-256 fingerprint. VMs keep running.

The node advertises its first non-loopback address on port 8842. To choose, pass --advertise 192.0.2.11:8842; --tunnel-ip sets the address for Geneve tunnels (default: the advertised address).

In the web UI: Cluster → Make this host a cluster → Initialize cluster…, with the same two fields.

Check it:

gxctl cluster status
gxctl nodes

Join tokens

A host joins with a one-time token issued by a server. The token is a secret: it is shown once, works once, and expires (1 hour by default, up to 7 days). Write it straight to a private file:

umask 077
gxctl cluster join-token --role agent > join.token           # an agent
gxctl cluster join-token --role server --ttl 24h > join.token
gxctl cluster join-token --role agent --allow-import > join.token

--role is agent (default) or server, and the joining host must ask for the same role. --allow-import lets the host bring its existing VMs along (see Import). The command prints the servers to join through on standard error.

In the web UI: Cluster → + Add node, pick the Role, how long the Token valid for, and whether the host has VMs to bring along. The dialog shows the token once with the commands to run.

Copy the token to the new host over a secure channel (for example scp), keep it mode 0600, and delete it after use. The token also pins the cluster’s CA: the joining host refuses a server whose CA doesn’t match it.

Join a host

On the new host, from your Glidex checkout, with the token file:

cargo run -p glidex-install -- --join 192.0.2.11:8842 --role agent --token-file join.token

The installer installs or updates Glidex as usual, then joins. The token is read from the file (which must not be readable by others) or from standard input, never from the command line. Options:

  • --role server for a server (the token must be a server token).
  • --advertise IP:PORT: the address other nodes use for this one.
  • --node-name NAME: default is the host name.

A host that already runs Glidex can join with gxctl instead:

gxctl cluster join --server 192.0.2.11:8842 --role agent --token-file join.token

gxctl cluster join defaults to --role server, so pass the role the token was made for.

A host that has VMs, disks, networks or credentials can’t do a plain join: that would abandon them. Remove them, or join with --import.

Add servers

A new server joins as a Raft learner, then becomes a voter. To keep the voter count odd, learners are promoted in pairs: join two servers to go from 1 to 3 voters, two more to reach 5. A single extra server stays a learner until the next one joins, or until you promote it:

gxctl cluster promote node2 node3        # learners to voters; --force for an even count

gxctl cluster status lists voters and learners; the Raft card on the Cluster page shows the same.

An agent can’t become a server in place. To turn an agent into a server, take it out of the cluster and join it again with a server token.

Import an existing host’s VMs

A standalone host can join with its VMs, disks, networks and credentials:

  1. On a server: gxctl cluster join-token --role agent --allow-import > join.token (or tick The host already has VMs to bring along in + Add node).
  2. On the host: cargo run -p glidex-install -- --join 192.0.2.11:8842 --import --token-file join.token. Nothing changes yet: the host sends a plan and waits.
  3. An administrator reviews and approves the plan. On the Cluster page, Pending imports lists it; its page shows what the host brings, lets you map its projects, node networks and credentials to names in the cluster, and reports problems. Check, then Approve (or Reject). From the CLI:
gxctl node import list
gxctl node import show <plan>
gxctl node import approve <plan> --project lab=new:lab-imported --dry-run
gxctl node import approve <plan> --project lab=new:lab-imported --network default=lab-net
gxctl node import reject <plan>

--project src=existing puts a project’s resources into an existing project, src=new:name into a new one. --network a=b and --credential project/user=new rename networks and credentials whose name is taken. --over-quota accepts an import that takes a project over its quota. A plan expires after a day.

On approval the host joins and its resources become the cluster’s in one step. Its VMs keep running.

Placement

The scheduler picks a node when a VM is created. A node is a candidate only if it is Active, ready, not draining, has room, and has what the VM needs: the hypervisor, the image’s architecture, hugepages if asked, its PCI devices, the physical networks of its provider networks, a userspace br-int for vhost-user NICs on cluster networks, an OVN version as new as the cluster’s, and the node of any disk or node network it uses. Among candidates it picks the least allocated (the larger of CPU and memory share after placing), then the one with fewest VMs.

Room is each node’s CPUs and memory minus a reserve, times an overcommit ratio. The defaults, in /etc/glidex/control-plane.json:

{
  "cluster": {
    "scheduler": { "cpu_overcommit": 4.0, "memory_overcommit": 1.0 },
    "node_reserved": { "cpus": 1, "memory_mib": 2048 }
  }
}

The VM form’s Placement shows the scheduler’s choice (Automatic (now: …)) and each node’s free vCPUs and memory, or why it can’t take the VM. Pick a node to pin the VM there (node in the API). A VM no node can take is still created and waits, with each node’s reason in its status.

A VM stays on its node once placed. Glidex doesn’t move running VMs.

Node lifecycle

Each node has a phase: Active, Draining, Departing (a detach in progress), or one of the end states Departed, Removed, Forgotten. The Cluster page’s Nodes card shows phase and readiness; a node’s page has an Operations… menu for everything below.

A node is down for a while

Nothing to do. A node that stops reporting for 40 seconds (cluster.node_grace_secs) becomes not ready, and so do its VMs (NodeUnreachable). Nothing is restarted elsewhere. The node comes back by itself with its identity.

Drain

gxctl node drain node3
gxctl node undrain node3

A draining node gets no new VMs. VMs already there keep running; the command prints what is still on the node. Stop, delete or move them before removing it.

Remove an empty node

  1. gxctl node drain node3, then delete its VMs, disks and node networks (or detach it with them).
  2. gxctl node remove node3. Refused while the node holds a VM, disk or node network, if it is the only gateway of the shared edge or of a project router, or if the Raft voters left would have no majority or an even count (--force for the even case only).
  3. On that host, from your checkout: cargo run -p glidex-install -- --leave. It refuses until the removal has committed, then makes the host standalone again. (On a removed server whose control plane still runs, gxctl cluster leave does the same; an agent has no local API for it.)

Removing a server rotates the CA afterwards: it held the CA key.

Detach a node with its VMs

gxctl node detach node3 --map-network lab=lab-standalone
gxctl node detach node3 --abort         # before the node acknowledged

The node leaves with its VMs, disks and node networks and becomes a standalone host that owns them. --with-access also carries the projects’ users, teams and role bindings (never sessions or tokens). The node is frozen while the handover runs. The Cluster page shows it under Detaches.

If no server can be reached at all, a node can leave on its own:

cargo run -p glidex-install -- --leave --keep-resources --offline

It asks for confirmation: changes made in the cluster since the node last synced are lost. Then, on a server, run gxctl node detach node3 --departed so the cluster lets go of it.

A node is gone for good

  1. Make sure it is powered off or fenced. Then: gxctl node forget node3 --fenced (add --force if that leaves an even number of voters). Its VMs stay recorded, marked lost; its certificate is refused from now on; a forgotten server is rotated out of the CA.
  2. When you no longer want its records: gxctl node purge node3. This deletes the records of its VMs, disks and networks, not any files.

A repaired host comes back as itself

A forgotten node, or one whose certificate expired, can rejoin with the same identity, disks and VMs:

umask 077
gxctl node rejoin-token node3 > rejoin.token
gxctl node rejoin-token node3 --raft-lost > rejoin.token   # a server whose Raft state is gone

Use --raft-lost for a server whose cluster/raft directory is gone or older than its last vote: it then returns as a learner with fresh Raft state. On the host:

cargo run -p glidex-install -- --rejoin 192.0.2.11:8842 --token-file rejoin.token

Add --node-id <id> if the host lost its cluster files. A removed or departed node’s id is retired; it joins as a new node instead.

End the cluster

On the last node, after every other node has left:

gxctl cluster dissolve --force

The host becomes standalone with every VM, disk, network and user, and keeps a final snapshot. Restart the control plane afterwards. The Cluster page’s Danger zone has Leave (for a removed node) and Dissolve.

Certificates and the CA

The cluster CA is valid for 10 years, node certificates for one. Nodes renew their certificates by themselves 30 days before they expire. The CA rotates by itself after a server leaves and a year before it expires. To rotate on demand:

gxctl cluster rotate-ca                  # old CA retires after 7 days, or once every node renewed
gxctl cluster rotate-ca --grace 0        # retire at once

--grace is in seconds (default 604800, cluster.ca_rotation_grace_secs). Every node trusts both CAs, renews its certificate under the new one, and the old one retires. A node that was unreachable the whole time needs a rejoin token. The Certificate authority card on the Cluster page shows the signing CA, its expiry, a rotation in progress, and nodes not yet renewed; Rotate starts one (grace in days there).

Join tokens pin the CA. A token issued before a rotation fails with “the server’s CA … is not the one the token names”: issue a new one.

The secrets key

Connector secrets are sealed with a key every server holds. Rotate it with:

gxctl cluster rotate-secrets-key

If a server can’t be reached, it stops before re-wrapping anything; run it again.

Rolling upgrades

Upgrade one node at a time: agents first, then servers. On each host, update the checkout and re-run the installer (see Maintenance). VMs keep running while the control plane restarts.

gxctl cluster status shows each node’s version and feature level. The cluster runs at the lowest feature level any server reports, and uses new formats only once every server has them. Keep servers within one release of each other while you upgrade, and finish the round before starting the next.

The installer also brings a node’s OVN up to the version the cluster’s ovn-northd runs. A node whose OVN is older gets no VMs on cluster networks; the Cluster page names it.

Backups and lost quorum

On a server, take a snapshot of the replicated database regularly:

gxctl cluster snapshot glidex-$(date +%F).gxsnap

The file is written 0600: it holds credential and token hashes. Store it like the database itself. The Cluster page’s Certificate authority card also offers Download a cluster snapshot.

If a majority of servers is destroyed, the cluster can’t elect a leader. Recover from one surviving server:

  1. On that server, stop the control plane (VMs keep running): sudo systemctl stop glidex-control-plane.

  2. Start a single-voter cluster from its own database, or from a snapshot. Copy the snapshot where the glidex user can read it (sudo install -o glidex -g glidex -m 0600 glidex-….gxsnap /var/lib/glidex-control-plane/latest.gxsnap), then:

    sudo -u glidex env HOME=/var/lib/glidex-control-plane \
  /usr/local/bin/glidex-control-plane --force-new-cluster --from /var/lib/glidex-control-plane/latest.gxsnap

    Leave out --from to use its local database. Then sudo systemctl start glidex-control-plane.

  3. Re-join the other servers with --rejoin and tokens made with gxctl node rejoin-token <node> --raft-lost.

  4. With OVN on, OVN’s own databases need the same: on a surviving server, convert its northbound and southbound database files to standalone (ovsdb-tool cluster-to-standalone), then re-cluster the servers.

Cluster networks on OVN

With OVN off, every network lives on one node. With OVN on, cluster networks span every node: VMs on different nodes share them over Geneve tunnels, and NAT cluster networks leave through a shared edge. Node networks and their VMs are not affected either way.

Turn OVN on

Every node needs OVN installed (the default). If the Cluster page’s OVN card lists a node as missing it, re-run the installer there with --ovn. Then Enable OVN… on that card. Every node follows within a minute, without a restart: servers start OVN’s databases, every node becomes a chassis.

You can instead set it in a server’s /etc/glidex/control-plane.json ("cluster": {"ovn": {"enabled": true}}) and restart the control plane; saving in the UI makes the setting the cluster’s.

With OVN on, the OVN card shows tunnels between nodes, and nodes whose OVN is out of date. OVN settings… holds the rest. Disable OVN… is there too, once no cluster network is left.

Maintenance

Day-to-day care of a Glidex host: updates, what keeps running when the services restart, backups, logs, and removing Glidex.

Updating

Pull the new source and re-run the installer, from your checkout:

git pull
cargo run -p glidex-install

It reuses the choices saved in /etc/glidex/install.conf, updates what is outdated, and restarts only the services whose binary or unit changed. Running VMs keep running. Details are in Installation.

In a cluster, update one node at a time, agents first, then servers; see Rolling upgrades.

What survives a restart

Each running VM lives in its own systemd unit, glidex-vm@<vm-id>.service, in the glidex-vms.slice. The unit runs glidex-vm-shim, which supervises the hypervisor. These units are not part of the control plane’s service, so:

EventVMs
glidex-control-plane stops, restarts or is upgradedKeep running. At start the control plane finds each running instance and adopts it; nothing is relaunched.
glidex-ui restartsNot affected.
glidex-netd restartsKeep running. netd restores bridges, NAT and uplinks at start; vhost-user sockets survive in /run/glidex/vhost.
Host shutdownEach VM gets its power button and host_shutdown_grace_secs (default 60, at most 300) to shut down, then is stopped. VMs stop before netd and Open vSwitch.
Host bootThe control plane relaunches the VMs that were meant to be running (reconcile.on_host_boot: resume, the default) or leaves them stopped (stop).

To see the VM units:

systemctl list-units 'glidex-vm@*'
systemctl status glidex-vm@<vm-id>

Don’t start or stop these units yourself: the control plane does, through polkit, and restarting a VM is its decision, never systemd’s. Use gxctl start / stop or the web UI.

gxctl events <vm> shows what happened to a VM: starts, exits, restarts and adoptions.

Backups

What to keep, on every host:

  • /var/lib/glidex-control-plane/.glidex/glidex.db and secrets.kek, together;
  • tls/ (or your own certificates), and cluster/ on a cluster node;
  • /etc/glidex/;
  • /var/lib/glidex/netd.db;
  • images/ and disks/ if you can’t re-create them.

These files hold password hashes, token hashes and private keys. Keep backups encrypted, readable only by administrators, and in your approved backup system.

A standalone host

The database is written while the control plane runs, so stop it for a consistent copy. VMs keep running:

sudo systemctl stop glidex-ui glidex-control-plane
sudo tar -C /var/lib/glidex-control-plane -czf /root/glidex-$(date +%F).tar.gz \
  --exclude=.glidex/images --exclude=.glidex/disks .glidex
sudo tar -czf /root/glidex-etc-$(date +%F).tar.gz /etc/glidex /var/lib/glidex/netd.db
sudo systemctl start glidex-control-plane glidex-ui

Disks of running VMs change while you copy them. Copy a VM’s disk while the VM is stopped, or back up from inside the guest.

To restore, install Glidex, stop the two services, put the files back (owned by glidex:glidex, mode 0600 for files, 0700 for directories), and start them again.

A cluster

The cluster’s database is replicated on every server. Take snapshots from a server:

gxctl cluster snapshot glidex-$(date +%F).gxsnap

The file is written 0600 and holds credential and token hashes. A snapshot is what you recover from if a majority of servers is lost; see Clusters. VM disks stay on their nodes: back them up per node as above.

Certificate fingerprints

Both the API (port 8841) and the web UI (port 5173) use a self-signed certificate unless you configured one. Before trusting it from another machine, compare its SHA-256 fingerprint with the one on the host:

sudo openssl x509 -in /run/glidex-cp/tls.crt -noout -fingerprint -sha256              # API
sudo openssl x509 -in /var/lib/glidex-ui/tls/ui.crt -noout -fingerprint -sha256       # web UI

The installer also prints both at the end.

  • The browser’s fingerprint differs. Something between you and the host presents another certificate (a proxy, or the wrong host). Don’t accept it until you know why.

  • gxctl says the certificate is not among the profile’s pins. The host’s certificate changed. Glidex regenerates it only in narrow cases (a configured certificate replaced, cluster rotate-ca, a re-init). Confirm the new fingerprint on the host through another channel, then:

    gxctl auth login --profile <name> --pin sha256/<new fingerprint> --rebind

    gxctl auth trust list shows a profile’s pins; gxctl auth trust fetch shows what a server presents.

  • A join says the server’s CA is not the one the token names. The cluster CA rotated after the token was issued (for example a server left). Issue a new token.

See TLS certificates to use your own certificates.

Paths the glidex user can’t read

The control plane and every VM run as the glidex system user, in a sandbox. Paths you give the API (disk images, kernels, cloud-init files) are opened by that user, so:

  • They must be readable by glidex. Your home directory usually isn’t, and /home, /root and /run/user are hidden from the services entirely.
  • They must not be under /tmp or /var/tmp: VMs have a private /tmp. The API refuses such paths (… is under /tmp, which VMs cannot see).
  • Passing host paths at all needs the host.paths permission (system-admin).

Put such files somewhere like /srv/glidex/ with sudo chgrp -R glidex /srv/glidex && sudo chmod -R g+rX /srv/glidex. Better still, import them as images, which Glidex stores itself.

KVM

ls -l /dev/kvm
lsmod | grep kvm
  • No /dev/kvm. Turn on virtualization (VT-x / AMD-V) in the firmware settings, then sudo modprobe kvm_intel or sudo modprobe kvm_amd. In a VM, nested virtualization must be on in the outer hypervisor.
  • /dev/kvm exists but VMs fail with permission denied. The glidex user must be in the kvm group: id glidex. The installer adds it when the group exists; re-run it, then restart the control plane.

Getting help

When you report a problem, include the Glidex version (gxctl cluster status in a cluster, or the control plane’s startup banner), what you ran, the error code and message, and the relevant journal lines. Remove host names, addresses, user names and anything secret from them first, and never include tokens, passwords or private keys.

gxctl

gxctl is the Glidex command-line client. It runs as an interactive shell, or runs one command and exits:

gxctl                                   # interactive shell: gxctl> …
gxctl list                              # one command, then exit
gxctl --project lab disk list
gxctl --url https://host.example.org:8841 auth login --oidc

In the shell, help (or ?) lists the commands, Tab completes command names, subcommands and file paths, and exit (quit, q) leaves. Words can be quoted: project create lab --description "Lab VMs". Noun commands also answer to their plural (images, projects, tenants, …), and many subcommands to short forms (ls, rm).

gxctl --help shows the global options. Commands have no --help of their own: run one without its arguments to see its usage line, or gxctl help for the full list. Both are authoritative over this page.

API overview

Glidex has one API with two transports:

  • REST: JSON over HTTPS, for curl, scripts and anything that doesn’t want generated code. See REST API.
  • RPC: gRPC and the Connect protocol, with typed clients generated from the protos. See RPC API.

Both run the same operation, with the same authorization, quotas and audit entry. Most operations exist on both. Some are REST only: the console WebSocket, the /watch event stream, browser and OIDC login redirects, CSV exports, cluster and node management, and /health. The gRPC health service has no REST twin. The web UI and gxctl use this same API.

Which one to use

You wantUse
A quick call from a shell, or a script in any languageREST
A typed client (Go, TypeScript, Python, Rust, …) with compatibility checksRPC
The serial console, or live change eventsREST (WebSocket, server-sent events)
Cluster and node managementREST, or gxctl

Where an operation exists on both, its request and response are the same message: the REST body is the proto3 JSON form of the RPC message, with snake_case field names.

REST API

Conventions

  • Base URL: https://host.example.org:8841, with no path prefix (https://host.example.org:8841/vms). Locally, the same paths over the Unix socket /run/glidex-cp/api.sock.
  • JSON in and out (Content-Type: application/json), except the console WebSocket, CSV exports and the cluster snapshot.
  • Ids and names: VM paths take the VM’s id. Disks, images, networks, projects and nodes take an id or a name, tenants an id or a slug; a name that several visible resources share is 409 ambiguous. gxctl resolves VM names for you.
  • Projects: VMs, disks, guest credentials and project networks belong to a project. Creates take project (id or name) and default to your default project; lists take ?project=.
  • Status codes: 200 OK, 201 created, 202 accepted (the controller is still working on it), 204 no content (gone).

Waiting for the controller

VM and disk writes, and image and network deletes, record what you want and return; controllers carry it out. By default such a write answers at once: 202 with the resource (201 for a create, 204 for a delete with nothing left to do). Add ?wait=<secs> (at most 300) to hold the answer until the controller has acted:

OutcomeAnswer
Done in time200 (201 for a create) with "settled": true
The time ran out202 with "settled": false
The controller failedThe error it hit, e.g. 500 hypervisor_error, with the VM in details.vm
The resource is gone (a delete)204

?wait applies to VM create, start, stop, pause, PATCH, delete, device and disk attach/detach; disk create, resize and extend-root; image delete; network delete. gxctl waits 60 s by default.

A VM’s state is what the controller last saw and desired_state what you asked for. Wait for its Ready condition to be True, not for a state.

Start, stop, pause and PATCH of a VM take If-Match: <resource_version>: the write is refused with 412 precondition_failed if the VM changed since you read it.

Lists and paging

Lists return everything you may see in one answer, except:

  • GET /tenants: page_size, page_token; the answer has next_page_token.
  • GET /audit: since, limit (default 500, at most 5000), project, user.

Live changes: GET /watch

A stream of server-sent events (text/event-stream) with the VMs, disks, images and networks you may list:

  • ?kinds=vms,disks,images,networks (the default); also nodes, imports, cluster, policy.
  • ?project=<p> limits VMs and disks to one project.

The stream starts with an added event per object, then synced; after that added, modified and deleted as things change. Each event’s data is {"kind": "vm", "id": "…", "object": {…}} (no object on deleted). Authorization is re-checked for every event. The server ends a stream after 5 minutes with expired; reconnect for a fresh snapshot (a browser EventSource does this by itself). Too many open streams on a host give 503 too_many_watchers: poll instead.

Console WebSocket

  1. GET /vms/{id}/console says whether the console is available and gives the WebSocket path.
  2. Browsers with a session cookie first get a single-use ticket, POST /vms/{id}/console/ticket, and pass it as ?ticket=. Token and Unix-socket clients don’t need one.
  3. GET /vms/{id}/console/ws upgrades to a WebSocket. Output arrives as binary frames of raw serial bytes; send keystrokes as binary or text frames. Any number of clients can share a console.

GET /vms/{id}/console/log?tail_bytes=N returns the end of the console log (at most 1 MiB); previous=true reads the rotated one. See Console.

Cluster reads

In a cluster any server answers reads after catching up with the leader. Send x-glidex-consistency: local to skip that wait and accept a possibly stale answer. Writes sent to a follower are forwarded to the leader.

RPC API

Every operation in the REST API that has a proto message is also an RPC. Same port, same credentials, same authorization and audit: the RPC and its REST twin run the same code.

Protocols

ProtocolWhereNotes
gRPC:8841 (HTTP/2 over TLS), api.sock (HTTP/2 without TLS)Binary protobuf
Connect:8841, api.sockUnary calls are plain POSTs over HTTP/1.1 or HTTP/2, with application/proto or application/json bodies; easy to call with curl
gRPC-WebThe web UI onlyRefused on :8841 and api.sock (PERMISSION_DENIED, reason protocol_not_allowed)

All three are answered by the same server on the same port as REST; there is no separate RPC port. Procedures live at /glidex.<area>.v1.<Service>/<Method>, for example /glidex.vm.v1.VmService/ListVms.

Every method is unary for now. Live events (/watch) and the console stay on REST until their streaming RPCs exist.

Limits: 4 MiB per message; a client deadline (grpc-timeout, connect-timeout-ms) is honored up to 5 minutes.

Authentication

ListenerMetadata
:8841authorization: Bearer <token>
api.sockNone: you are the Unix user you connect as

Session cookies are refused on RPCs outside the web UI (UNAUTHENTICATED, reason cookie_not_accepted): use a token. Public methods (SystemService.GetServerInfo and the LoginService methods) need no credential. See API overview.

Optional metadata:

  • x-glidex-consistency: local: in a cluster, read from the server you reached without waiting for it to catch up with the leader.

Responses carry x-request-id.

Errors

Errors carry a gRPC status and, as an error detail, a google.rpc.ErrorInfo with domain: "glidex" and reason set to the same stable code the REST API returns in error (codes). When the REST error has details, a glidex.api.v1.ErrorDetails detail holds them as JSON text in json. Branch on reason, not on the message.

StatusReasons
UNAUTHENTICATEDunauthenticated, login_failed, reauth_required, cookie_not_accepted
PERMISSION_DENIEDforbidden, login_not_allowed, tls_required, ticket_required, tenant_suspended, origin_not_allowed, csrf_failed, protocol_not_allowed, not_admitted, …
RESOURCE_EXHAUSTEDquota_exceeded, tenant_quota_exceeded, too_large, rate_limited, slow_down
NOT_FOUNDnot_found, oidc_disabled
ABORTEDconflict (a name taken, a concurrent change): read again and retry
FAILED_PRECONDITIONOther 409 codes (ambiguous, would_lock_out, confirmation_required, …), authorization_pending, unsupported_on_host
INVALID_ARGUMENT400 and 422 codes: bad_request, invalid, invalid_*

Health

grpc.health.v1.Health/Check is served on every listener without a credential, like GET /health. It is answered by the server you reach.

Getting the protos

The protos are in the repository: crates/glidex-api/proto. The server doesn’t offer reflection, so clients and tools need these files. Packages are versioned (v1); a breaking change would come as a v2 package served next to v1. Field names and numbers are the compatibility contract, and JSON names are the snake_case field names.

Generate clients with buf. A buf.gen.yaml for TypeScript (Connect-ES), next to a checkout of the repository:

version: v2
inputs:
  - directory: glidex/crates/glidex-api/proto
plugins:
  - remote: buf.build/bufbuild/es
    out: src/gen
    opt:
      - target=ts

git clone https://github.com/CMKL-APEX/glidex.git
buf generate

Other languages work the same way with their protobuf and gRPC or Connect plugins (managed mode can set package options such as go_package, which the protos don’t declare).

Examples

Connect with curl, JSON in and out:

curl --cacert tls.crt \
  -H "Authorization: Bearer <token>" \
  -H 'Content-Type: application/json' \
  -d '{}' \
  https://host.example.org:8841/glidex.system.v1.SystemService/WhoAmI

curl --cacert tls.crt \
  -H "Authorization: Bearer <token>" \
  -H 'Content-Type: application/json' \
  -d '{"project": "lab"}' \
  https://host.example.org:8841/glidex.vm.v1.VmService/ListVms

buf curl, with the protos as the schema:

buf curl --schema glidex/crates/glidex-api/proto \
  --cacert tls.crt \
  -H "Authorization: Bearer <token>" \
  -d '{"id": "<vm-id>", "wait_secs": 60}' \
  https://host.example.org:8841/glidex.vm.v1.VmService/StartVm

grpcurl over gRPC, remotely and on the host’s socket:

grpcurl -cacert tls.crt \
  -import-path glidex/crates/glidex-api/proto -proto glidex/vm/v1/vm.proto \
  -H 'authorization: Bearer <token>' \
  -d '{}' \
  host.example.org:8841 glidex.vm.v1.VmService/ListVms

grpcurl -plaintext -unix \
  -import-path glidex/crates/glidex-api/proto -proto glidex/system/v1/system.proto \
  -d '{}' \
  /run/glidex-cp/api.sock glidex.system.v1.SystemService/WhoAmI

Write requests take the same fields as the REST body; the REST query parameters become fields too (?wait=60 is wait_secs: 60, If-Match is expected_resource_version).
