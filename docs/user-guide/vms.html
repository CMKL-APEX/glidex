Glidex

Virtual machines

A VM belongs to one project. You create it stopped (or ask for it to start at once), then start, pause, stop and delete it. Each of these changes the VM’s desired state; the control plane then works until the VM gets there. See Concepts for the model.

In the web UI, the VMs page lists the VMs of the selected project. Click a VM for its details, actions, usage and events.

In gxctl, commands take a VM’s name or id. Names are unique within a project; use --project <p> (or project use <p>) when the same name exists in two projects you can see.

gxctl> list                       # the VMs: id, name, project, state, node, vCPUs, memory, hypervisor
gxctl> get my-vm                  # one VM: state, last exit, NICs and their addresses

Before you start

A VM that boots a cloud image needs:

  • an image (or an existing disk made from one), and a firmware image for the hypervisor. See Images and disks;
  • a guest credential, or the VM has no way to log in. See Guest credentials;
  • a network your project may use, or the VM has no NIC. See Networks.

You need the editor role in the project to create, change and delete VMs, and operator to start, stop and pause them and to open their consoles. See Projects.

API

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/vms -d '{
    "name": "web-1", "vcpu_count": 2, "mem_size_mib": 2048,
    "image": "ubuntu-26.04", "root_disk_size_gib": 20,
    "credential": "alice", "networks": [{"network": "lab"}],
    "power": "running"
  }'

name, vcpu_count and mem_size_mib are required. See REST API for every field.

Boot disk

Give exactly one of:

  • image: Glidex creates a linked root disk from the image for this VM (named <vm>-root), grows it to root_disk_size_gib, and extends the guest’s root partition at first boot. The disk belongs to the VM and is deleted with it, unless you delete with --keep-disk.
  • root_disk: an existing, unattached disk of the project (name or id). It is not deleted with the VM.
  • rootfs_path: a disk image file on the host, used as is.

The image (or the root disk’s image) and the firmware must be for the same CPU architecture.

Firmware or kernel boot

A VM with an image or root_disk boots through UEFI firmware: the newest firmware image for its hypervisor (and architecture), unless you name one with firmware. If there is none, the create fails and tells you which one to pull (cloudhv-edk2 for Cloud Hypervisor, ovmf for QEMU).

For a direct kernel boot, give kernel_image_path (and a root filesystem in rootfs_path) instead. The default kernel arguments are console=hvc0 root=/dev/vda reboot=k panic=1 on Cloud Hypervisor and console=ttyS0 root=/dev/vda reboot=k panic=1 on QEMU.

Host paths

rootfs_path, kernel_image_path, cloud_init_path and firmware_path name files on the host. Using them needs the system-admin role, and the files must be readable by the service user the control plane runs as. Most users should use images, disks and firmware images instead. A path under /tmp or /var/tmp is refused: VMs have a private /tmp.

Credential and cloud-init

With firmware boot and no cloud_init_path, Glidex generates a cloud-init seed for the VM: its hostname, the root partition grow, and, if you name a credential, that user with its password and SSH keys. cloud-init applies it on the VM’s first boot. Without a credential the guest has no login. See Guest credentials.

cloud_init_path replaces the generated seed with your own (a host path, see above); a credential can’t be combined with it.

Networks

Each entry of networks adds one NIC, in order (at most 8):

"networks": [
  {"network": "lab"},
  {"network": "storage", "mac": "02:00:00:00:10:01", "queue_pairs": 2}
]

network is a network’s name or id that your project may use. mac is optional: by default each NIC gets a stable MAC derived from the VM’s id. queue_pairs (1 to 8) is optional. The address each NIC got shows in the VM’s details. See Networks.

Data disks

data_disks lists disks of the project (names or ids), attached in order after the boot disk. A disk is attached to one VM at a time.

To attach or detach a disk later:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/vms/<id>/disks -d '{"disk": "data-1"}'
curl -H "Authorization: Bearer $GLIDEX_TOKEN" \
  -X DELETE https://host.example.org:8841/vms/<id>/disks/data-1

On a running VM the change applies at the next start. See Images and disks.

PCI devices

vfio_devices passes host PCI devices (a GPU, a NIC) through to the guest. Give each as /sys/bus/pci/devices/0000:41:00.0 or the bare address 0000:41:00.0. A device is used by one VM at a time, and using one needs a grant from an administrator. See PCI passthrough.

gxctl> pci                                          # host PCI devices
gxctl> attach-device my-vm /sys/bus/pci/devices/0000:41:00.0
gxctl> detach-device my-vm /sys/bus/pci/devices/0000:41:00.0

On a running VM, devices are hot-plugged. On a paused VM, the change waits until it runs again.

gxctl waits up to 60 seconds for the VM to get there (longer for a graceful stop) and prints the state it reached; --no-wait returns at once. If the VM isn’t there yet, it says what it is waiting for. The web UI follows the VM and shows In progress until it gets there. The API returns at once (202), or, with ?wait=<secs> (at most 300), once the VM got there. See Waiting for the controller.

Starting a stopped VM counts against the project’s running-VM quota.

Stop

A graceful stop presses the guest’s power button, waits for the guest to shut down, and stops the VM hard if it is still running after the timeout:

gxctl> stop my-vm --graceful          # wait up to 60 s
gxctl> stop my-vm --graceful 120      # wait up to 120 s (at most 300)

The web UI’s Shut down waits 60 seconds. Stop and stop without --graceful stop the VM like pulling the plug.

The timeout you give is kept as the VM’s stop grace (stop_grace_secs) and used again by later stops that don’t give one, including stops from the web UI’s Stop button. Pass --graceful 0 (or graceful_timeout_secs=0) for an immediate stop after a graceful one.

Pause and resume

A paused VM keeps its memory but gets no CPU time. Resume in the web UI, or start in gxctl, runs it again.

Restart

There is no restart action: stop the VM, then start it. A reboot from inside the guest restarts the guest and the VM stays running.

When the VM stops on its own

  • The guest powers off (for example poweroff inside it): the desired state becomes stopped, and the VM stays stopped whatever its restart policy.
  • The hypervisor crashes: with the restart policy on_failure, the VM is started again after 10 seconds, doubling with each crash in a row up to 5 minutes; after 10 minutes of running the count starts over. With never, the desired state becomes stopped.
  • It fails to launch: the VM is failed and Glidex retries with a growing delay. Its details and events say why.
  • The host reboots: with on_host_boot resume, a VM that was running is started again; with stop, it stays stopped.

Change these policies with the API:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X PATCH https://host.example.org:8841/vms/<id> \
  -d '{"change": {"restart_policy": "never"}, "update_mask": "restart_policy"}'

Change a VM

Change vCPUs, memory, networks, data disks, PCI devices, kernel arguments, the credential, hugepages and the policies with PATCH /vms/{id}. change holds the new values, update_mask lists the fields to change (comma-separated):

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X PATCH https://host.example.org:8841/vms/<id> \
  -d '{"change": {"vcpu_count": 4, "mem_size_mib": 8192}, "update_mask": "vcpu_count,mem_size_mib"}'

networks and data_disks replace the whole list. The hypervisor, the boot disk, the firmware and host paths can’t be changed.

The web UI and gxctl have no edit form; gxctl changes PCI devices only (attach-device, detach-device).

A change to vCPUs, memory, kernel arguments, the credential, hugepages, networks or data disks of a running VM takes effect at the next start: the web UI says Configuration changes take effect at the next start, and the API sets restart_required. Stop and start the VM to apply it. A new credential doesn’t change logins in a guest that already booted (cloud-init runs once).

Pass the VM’s resource_version in an If-Match header to refuse the change (409) if someone else changed the VM since you read it.

Delete

gxctl> delete my-vm                 # asks for confirmation
gxctl> delete my-vm --keep-disk     # keep the root disk created for it

Deleting stops the VM if it runs, releases its NICs and their addresses, and detaches its disks. A root disk created for the VM from an image is deleted with it, unless you keep it (--keep-disk, ?keep_disk=true). Other disks are only detached.

States and events

The state shows where the VM is; while it is on its way to its desired state, gxctl and the web UI show both, for example stopped → running.

StateMeaning
createdNever started.
startingBeing provisioned or launched.
runningThe guest runs.
pausedThe guest is paused.
stoppingA stop is in progress.
stoppedNot running.
failedIt failed to launch, or crashed and waits to be restarted.
unknownThe control plane can’t tell, for example because the VM’s node stopped reporting.

In the API, states are VM_STATE_RUNNING and so on, and the desired state is desired_state. The VM’s conditions say what is in the way (the Ready condition), and last_exit says how the last run ended: stopped on request, stopped by the host, guest powered off, crashed (with its exit code or signal), failed to launch, host rebooted, or lost.

Each VM keeps a list of events: created, spec changes, launches, exits, restarts, warnings such as a lost network port.

gxctl> events my-vm           # time, who, reason, message

In the web UI they are under Events on the VM’s page. With the API, GET /vms/{id}/events.

To follow every VM, disk, image and network of your projects as they change:

gxctl> watch                  # Ctrl-C stops
gxctl> watch vms

Placement on a cluster

On a cluster, the scheduler picks the node for a new VM when it is created. It considers only nodes that are active, ready and not draining, that have the hypervisor, enough vCPUs and memory left, the PCI devices, hugepages and physical networks the VM needs, and that hold its disks and node networks. Of those, it prefers the least loaded.

A VM stays on its node for its whole life: Glidex doesn’t move it, and doesn’t restart it elsewhere if the node fails. If no node can take the VM, it is still created and waits for one; its page says Waiting for a node with each node’s reason.

In the web UI’s create form, Placement shows Automatic (now: <node>) and each node with its free vCPUs and memory, or why it can’t take the VM. Pick a node to pin the VM there. With the API, set node when you create the VM. To ask the scheduler without creating anything:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/scheduler/preview \
  -d '{"vcpu_count": 2, "mem_size_mib": 2048, "hypervisor": "qemu"}'

The answer has the node it would pick (pick) and every node’s fit (nodes, with refused when it can’t take the VM).

The VM’s node shows in gxctl list and on its page. If the node stops reporting, the page shows the VM’s last known state; the VM may still be running there.

See Clusters for nodes and draining.
