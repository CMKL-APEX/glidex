Glidex

Kernel boot

A VM boots in one of two ways:

  • Firmware boot (the default): the hypervisor runs UEFI firmware, and the firmware runs the boot loader on the VM’s disk, which picks the kernel. See Virtual machines.
  • Kernel boot (direct kernel boot): the hypervisor loads a kernel, an optional initramfs and a kernel command line that Glidex hands it. There is no firmware and no boot loader.

A distro cloud image boots either way: the same root disk, the same cloud-init seed and credential, and the same console.

When to use it

Use kernel boot when you want to choose the kernel from outside the guest:

  • to set the kernel command line yourself, for example to debug a guest that doesn’t boot;
  • to boot a kernel the guest doesn’t have, or keep a VM on a known kernel build;
  • to boot a bare root filesystem with no partition table or boot loader.

Stay with firmware boot when the guest should manage its own kernel through its boot loader, as on a physical machine. With kernel boot, a kernel the guest installs (apt upgrade, say) doesn’t boot unless you turn on following the guest’s kernel.

A VM’s boot mode is fixed when it is created: you can’t switch a VM between firmware and kernel boot.

Kernel images

A kernel image is an entry in the shared image library holding a kernel, an optional initramfs and a default command line. VMs name it with kernel, as they name firmware with firmware. Like other images, kernel images are visible to everyone, and adding and deleting them needs the image-admin role. See Images and disks.

A kernel image is never replaced: a newer kernel is a new image, and each VM keeps the one it names until you change it.

From a cloud image

Pulling a catalog image also takes the kernel out of it: a second image, <image>-kernel (for example ubuntu-26.04-kernel), appears in state extracting and becomes ready a few seconds after the image. It is the kernel, initramfs and command line the image’s own boot loader would boot, with console= replaced by the serial console: console=ttyS0, or console=ttyAMA0 for an aarch64 image. So the kernel always matches the modules on the image’s disk.

  • A pull with a name names the kernel image <name>-kernel.

  • gxctl image pull <key> --no-kernel ("with_kernel": false) skips the extraction; "with_kernel": true extracts from a URL pull too (off by default for URLs). gxctl image pull waits through extracting and prints the kernel’s release and command line.

  • To take the kernel out of an image you already have, including one pulled from a URL: Extract kernel on the image under Images, gxctl image extract-kernel my-image, or

    curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/images -d '{"kernel_from": "my-image"}'

    The answer is 202 with the new kernel image (200 with the one already extracting from that image).

Glidex reads the image inside a small VM without network, never on the host. It builds that VM the first time it extracts, from pinned Debian packages for the image’s architecture (a one-time download of about 35 MB on x86_64, 30 MB on aarch64).

That VM runs under KVM, so an image’s kernel is extracted only on a host of the image’s architecture:

ImageExtracted on
x86_64an x86_64 host with Cloud Hypervisor or QEMU
aarch64an aarch64 host with Cloud Hypervisor

An administrator can also turn extraction off (for a host without internet access, say). Where it can’t run, kernel_from is refused with 400 invalid_image and the reason, for example kernels can’t be extracted here: aarch64 kernels are extracted on a aarch64 host; this one is x86_64, and catalog pulls bring only the disk image.

If extraction fails, only the kernel image fails, with the reason; the disk image stays ready and firmware boot is unaffected. Retry in the web UI or gxctl image retry <name> runs it again.

From a URL

gxctl> image pull https://images.example.org/vmlinuz-6.8.0-147-generic --kernel --sha256 <sha256> \
         --initrd-url https://images.example.org/initrd.img-6.8.0-147-generic --initrd-sha256 <sha256> \
         --cmdline "root=LABEL=cloudimg-rootfs ro console=ttyS0"

or over the API:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/images -d '{
    "url": "https://images.example.org/vmlinuz-6.8.0-147-generic", "sha256": "<sha256>",
    "kind": "IMAGE_KIND_KERNEL",
    "initrd_url": "https://images.example.org/initrd.img-6.8.0-147-generic", "initrd_sha256": "<sha256>",
    "cmdline": "root=LABEL=cloudimg-rootfs ro console=ttyS0"
  }'

The URL rules are those of any image pull: https://, and listed as unverified unless every file had a sha256. Use the kernel the cloud image was built with: the guest loads the kernel’s modules from its own disk. Ubuntu publishes each build’s kernel and initramfs next to the image, in unpacked/.

From host files

An administrator who may use host paths can copy a kernel from files on the host into the library:

gxctl> image pull --kernel-path /srv/kernels/vmlinuz-custom --initrd-path /srv/kernels/initrd-custom \
         --cmdline "root=/dev/vda1 ro console=ttyS0"

or over the API:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/images -d '{
    "kernel_path": "/srv/kernels/vmlinuz-custom", "initrd_path": "/srv/kernels/initrd-custom",
    "cmdline": "root=/dev/vda1 ro console=ttyS0", "name": "custom-kernel"
  }'

VMs then boot it like any kernel image; their users need no access to host paths.

What a kernel image may hold

  • An x86_64 bzImage (64-bit), an ELF vmlinux for x86_64 or aarch64, or an arm64 Image. Anything else fails the image.
  • An aarch64 kernel as distributions ship it is unwrapped to the plain Image Cloud Hypervisor boots: Ubuntu’s vmlinuz (an EFI stub holding the kernel), the kernel’s own compressed EFI image (gzip or zstd), or a gzip file. This applies to extracted, downloaded and host-file kernels; a host file is unwrapped into the copy and never changed. The kernel image’s size and sha256 are the unwrapped file’s.
  • At most 128 MiB for the kernel and 1 GiB for the initramfs, unless an administrator changed the limits.
  • A cmdline of at most 2047 bytes, without control characters.

The kernel’s release (7.0.0-34-generic) is read from its header when the format carries one (a bzImage does).

Listing and deleting

Web UI: Images, Kernels (shown once there is one): each kernel image with its release, whether it has an initramfs, its command line, its status (Extracting…, Ready), its source and the VMs that boot it.

gxctl:

gxctl> image list            # kernel images show as "kernel <release>"
gxctl> image rm ubuntu-26.04-kernel

The source column says where a kernel came from: its URL, the host file, or extracted: <partition>:<path> (extracting until done).

A kernel image can’t be deleted while a VM boots it, or keeps it to go back to (see Kernel versions): the delete is refused with 409 conflict, naming the VMs. The image’s used_by_vms lists them.

Create a VM with kernel boot

Name a kernel image with kernel and the root disk as for firmware boot (image or root_disk):

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X POST https://host.example.org:8841/vms -d '{
    "name": "web-1", "vcpu_count": 2, "mem_size_mib": 2048,
    "image": "ubuntu-26.04", "kernel": "ubuntu-26.04-kernel",
    "credential": "alice", "networks": [{"network": "lab"}]
  }'
  • The VM needs no firmware image. Giving both a kernel and a firmware (firmware or firmware_path) is refused with 400 invalid_config.
  • The kernel image must be ready and of the root image’s architecture. Using it needs read access to the image, as for firmware.
  • The VM gets the kernel image’s command line as its kernel_args, unless you give them.
  • Glidex generates the cloud-init seed as for firmware boot (the hostname, the root partition growth and the credential), so credential works the same. See Guest credentials.
  • On a cluster, the VM’s node gets its own copy of the kernel image. Until it has one, the VM waits with the condition DisksReady False (kernel <name> has not been copied to this node yet).

Web UI: Create VM, Boot Mode Direct kernel boot. The Kernel choice replaces UEFI Firmware: pick a kernel image. Only the chosen image’s own kernel is preselected; when it has none, the choice stays empty and Extract it from the image makes one. Other kernels are listed as — from <image>, and picking one shows a warning: another distribution’s initramfs usually can’t find this image’s root. Kernel Arguments show and default to the kernel image’s command line. Follow the guest’s kernel turns on following. The boot disk and login credential work as with firmware.

gxctl: in gxctl create, answer kernel at UEFI firmware, then pick the kernel image at Kernel (the default is only the boot image’s own kernel; another image’s kernel prints a warning), and answer Follow the guest’s kernel. Kernel arguments default to the kernel image’s command line.

Host paths

An administrator who may use host paths can boot files on the host directly instead of a kernel image:

FieldWhat it is
kernel_image_pathThe kernel.
initrd_pathIts initramfs, optional; distro kernels need one. Only with kernel_image_path.
rootfs_pathA root filesystem or disk image, used as is. Over the API, image and root_disk work too.

In the web UI: Direct kernel boot, then Kernel Kernel files on the host, with the kernel and initramfs paths; a root filesystem file is the boot disk’s path source. In gxctl create, answer kernel at UEFI firmware, give a host path at Kernel, then the Initramfs path (optional).

Host paths can’t be changed after create. A VM with a host-path kernel and a host-path root filesystem gets no generated seed, so it can’t have a credential; one with image or root_disk gets the seed. generate_seed (true or false) overrides this at create, and can’t be combined with cloud_init_path.

The kernel command line

kernel_args is the kernel command line:

  • Default: the kernel image’s command line; with host paths, or a kernel image without one, console=ttyS0 root=/dev/vda reboot=k panic=1 (console=ttyAMA0 … on aarch64). The architecture is the kernel image’s, else that of the node the VM is pinned to, else the host’s.
  • Limits: at most 2047 bytes, no control characters (400 invalid_config).
  • The root: a cloud image’s root is on a partition, so root=/dev/vda doesn’t find it. A cloud image needs its own root, for example root=LABEL=cloudimg-rootfs ro for Ubuntu; an extracted kernel’s command line has it. A VM with a managed root disk whose arguments have no root= is created with the warning kernel_args has no root=; the kernel may not find the root disk.

Change them with PATCH /vms/{id} (kernel_args); they apply at the next start. Changing the kernel doesn’t change them.

The console

With kernel boot, the last console= in kernel_args picks the device Glidex connects the console to:

Last console=Guest deviceCloud HypervisorQEMU
hvc… (for example hvc0)the virtio consolevirtio console, no serial portvirtio console, no serial port
anything else (ttyS0, ttyAMA0), or nonethe serial portserial portserial port

Both hypervisors behave the same. Firmware boot always uses the serial port. The default arguments and extracted kernels name the serial port, console=ttyS0 (console=ttyAMA0 on aarch64, where ttyS0 would leave the console silent), so the console shows the kernel from its first line, and a panic is visible. The virtio console only starts once the kernel’s virtio driver is up: put console=hvc0 last only if you want it.

A Cloud Hypervisor VM created by an earlier version of Glidex keeps the console=hvc0 it was created with, and so the virtio console.

Following the guest’s kernel

A kernel-booted VM boots the kernel Glidex hands the hypervisor, so a kernel the guest installs doesn’t boot by itself. To boot it anyway, turn on kernel_from_disk: Follow the guest’s kernel on the VM’s Kernel panel or in the create form, gxctl kernel my-vm --follow on, or:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X PATCH https://host.example.org:8841/vms/<id> \
  -d '{"change": {"kernel_from_disk": true}, "update_mask": "kernel_from_disk"}'

It is also a field of POST /vms, and needs a kernel image (kernel) and a managed root disk (image or root_disk): 400 invalid_config otherwise. It applies at the next start.

Before each start, Glidex then takes the kernel out of the VM’s root disk again if the disk changed since the last time (its size or modification time), the same way it extracts from a cloud image. A VM that was only stopped and started pays nothing.

  • The VM shows booted_kernel, the kernel image it boots, and previous_kernel, the one before. Its kernel stays what you chose: the kernel it starts from, and its fallback.
  • A new kernel logs the event KernelUpdated (old → new release).
  • If extraction fails, the VM boots the kernel it has. Its condition KernelExtracted is False with the reason, the event KernelExtractFailed is logged, and the next start tries again. Only a VM with no kernel at all fails to start (KernelNotExtracted).
  • The VM keeps its kernel_args; the new kernel’s command line from the disk isn’t applied.
  • Extraction takes a few seconds on each start after a change, during which the disk is busy.

To go back to an earlier kernel, set kernel, for example to the previous_kernel:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X PATCH https://host.example.org:8841/vms/<id> \
  -d '{"change": {"kernel": "<previous_kernel>"}, "update_mask": "kernel"}'

Changing kernel without kernel_from_disk in the mask turns following off, so the VM stays on the kernel you set. Put both in the mask to keep following on.

Extract once

To take the guest’s kernel without following it, extract it once from a stopped VM: Extract from its disk now on the VM’s page, or

gxctl> kernel my-vm --extract

which waits until the new kernel image is ready and prints how to use it (kernel my-vm --set <kernel-image>). Over the API, POST /vms/<id>/extract-kernel answers 202 with the new kernel image, extracting; wait for it to be ready (GET /images/<image-id>), then set it as the VM’s kernel with PATCH.

  • It needs the editor role in the VM’s project.
  • The VM must be stopped (409 conflict otherwise), boot a kernel image, and have a managed root disk (400 invalid_config otherwise).
  • On a cluster, send it to a server on a node that reaches the VM’s root disk; otherwise it is refused with 409, naming the disk. A disk being moved to another datastore is 409 too.

Kernel versions

Kernels taken from a VM’s own disk are kernel images the VM owns: their owner is the VM’s id, they are named <vm>-kernel-<id prefix>, and they are never marked verified (the guest writes that disk).

  • A launch-time extraction that finds a kernel and initramfs already stored (the same files) uses that image instead of keeping a copy. A VM following an unchanged guest boots the cloud image’s own kernel image. extract-kernel always keeps its new image.
  • A VM uses a kernel image while its kernel names it, or it boots it or keeps it as previous_kernel. Such an image can’t be deleted, and on a cluster it is copied to the VM’s node.
  • A VM-owned kernel image is deleted by itself once no VM uses it (at least five minutes after it was made).

So VMs of the same image can run different kernels side by side, each kept while a VM needs it.

Change a VM’s kernel

kernel can be changed on a stopped or running VM that boots a kernel image; it applies at the next start. On the VM’s page, Kernel shows the kernel image (and, when following the guest, the one it boots and the one before); pick another and Use from the next start. With gxctl:

gxctl> kernel my-vm                              # the kernel, booted and previous
gxctl> kernel my-vm --set ubuntu-26.04-kernel
gxctl> kernel my-vm --follow on                  # or off

Over the API:

curl -H "Authorization: Bearer $GLIDEX_TOKEN" -H 'Content-Type: application/json' \
  -X PATCH https://host.example.org:8841/vms/<id> \
  -d '{"change": {"kernel": "ubuntu-26.04-kernel"}, "update_mask": "kernel"}'

The new kernel must be a ready kernel image of the same architecture. A firmware VM can’t change to a kernel (400 invalid_config), and kernel_image_path, initrd_path and generate_seed can’t be changed.

Limits

  • Kernel boot has no UEFI firmware, so no Secure Boot and no UEFI variables.
  • Kernel extraction runs only on a host of the image’s architecture (x86_64 or aarch64), and on aarch64 only with Cloud Hypervisor. Elsewhere, add kernel images from a URL or host files.
  • With a host-path kernel, the file must exist on the VM’s node; Glidex doesn’t copy it.
