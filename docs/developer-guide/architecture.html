Glidex

Architecture

This page is a map of Glidex for contributors: which processes run, how a request travels through them, where state lives and how it turns into running VMs. Each section names the crates and modules involved and links to the design spec with the details. For why things are built this way, see Design decisions and trade-offs; for the algorithms (scheduling, reconciliation, Raft write sets, metering), see Algorithms; for the repository layout, see Repository and code organization.

Source paths below are relative to the repository root and link to main. The design specs live in spec/.

The big picture

Glidex is a set of ordinary Linux processes. Nothing is containerized. The work is split by privilege: the control plane runs as an unprivileged user, and each thing that needs root is a small helper daemon with a narrow protocol on a Unix socket.

Socket and port numbers are configurable; these are the defaults. The helpers’ protocols are newline-delimited JSON; the clients live in the helper crates (glidex_netd::client, glidex_stord::client, glidex_authd::client) so the control plane and the daemon share one definition. The clients block; a call can take seconds (netd up to 30 s, LVM commands, hyperstor’s API), so the control plane makes them through glidex_raftstore::wait::blocking, which on a Tokio worker waits in block_in_place and leaves the runtime free to drive I/O.

Why VMs survive control-plane restarts

The control plane never spawns a hypervisor and never holds a PTY. For each VM it starts a glidex-vm@<id> unit through systemd. The unit runs glidex-vm-shim, which starts the hypervisor as its child, in the unit’s own cgroup. The control plane reaches a running VM only through files and sockets in the VM’s runtime directory, /run/glidex-cp/vms/<id>/:

FileWritten byContent
launch.jsoncontrol planeEverything the shim needs: the hypervisor command line (the whole VM config, built by the hypervisor driver), paths, grace periods
instance.jsonshimWhat the shim reports: phase, pids with start times, boot id, exit record
shim.sockshimstatus, stop, kill, release
api.sockhypervisorCloud Hypervisor’s HTTP API or QEMU’s QMP, reached with glidex-hv-client
console.sock, console.logshimThe serial console and its log

So stopping, crashing or upgrading the control plane (or netd, whose VM ports and vhost-user sockets also outlive it) leaves guests running. On the next start it observes every VM and adopts the live instances before acting on any (see Reconciliation). The runtime directory survives because the unit sets RuntimeDirectoryPreserve=yes. With the detached runner (development and tests) the shim runs in its own session instead of a unit; the picture is otherwise the same.

Cluster forwarding and consistent reads

In a cluster every server answers the API. The gate decides per request:

  • Writes (a non-safe HTTP method, or an operation of kind WRITE) on a follower are forwarded whole to the leader over :8842, with the already-authenticated principal in X-Glidex-Principal. The leader trusts that header only on a connection with a server certificate, and runs authorization itself.
  • Reads wait for a ReadIndex barrier (batched round trip to the leader), so a read on any server sees every write committed before it arrived. Without quorum they fail with 503 cluster_unavailable, unless the client asks for a stale read with X-Glidex-Consistency: local (gxctl --stale). Answers carry X-Glidex-Revision, the Raft index of the last applied entry.
  • Host-only routes (/ovs, /pci-devices, /system/…, the glidex.host.v1 services, cluster init/join/leave) act on the host that receives them and are never forwarded. With X-Glidex-Target-Node, a server authorizes the route’s action on that node’s Host and runs it there over :8842 (api/relay.rs).

The data model

Spec and status

Managed objects (VMs, disks, images, networks, nodes, routers) are envelopes of meta, spec and status, the Kubernetes pattern:

PartHoldsWritten by
metaid, name, project, generation (+1 on every spec change), resource_version (+1 on every write), deletion request, finalizersAPI
specDesired state: what the user asked for (power: running, vCPUs, disks, networks)API, inside admission
statusObserved state: phase, conditions (Ready, Scheduled, DisksReady, …), observed_generation, placement, the live instance, NICs, last exitControllers only (and the scheduler for placement)

The API records the spec before it answers, then returns 202, or, with wait, once the controller has acted. An object has converged when observed_generation == generation and Ready=True. Controllers write observed_generation as the generation they read, so a spec change made during a reconcile is never undone and is picked up next round. Types are in models.rs.

The store

All control-plane state is one redb database, glidex.db under the service user’s home (/var/lib/glidex-control-plane/.glidex/). Every change goes through Db::write: a transaction that records each put and delete as a write set. The store and its Raft integration are the glidex-raftstore crate; glidex’s schema (the TableId list, each table’s scope, and the write Origins) is store/db.rs. TableId is append-only: a table can be retired, its id never reused.

Writes take one write lane, a mutex, and in a cluster hold it until Raft has committed the write. Raft’s round trip needs the Tokio runtime’s I/O, so no worker may block outright on the lane, or on any other lock held across a store write (the network store’s write mutex, the image cache, the directory key lock): if the worker that blocked was the one driving I/O, the lane’s holder never hears back and every later request queues behind it. Those waits go through glidex_raftstore::wait: a free lock is taken at once, a held one is waited for in block_in_place.

VmManager (state.rs) keeps an in-memory cache of every VM. Admission (validation, quotas, disk and device claims, name uniqueness) runs under that cache’s write lock and ends in one store commit with the spec, the claims and an event. It never touches the host.

What’s replicated and what stays on a host. Every table of glidex.db is replicated except raft_meta (each replica’s own last_applied and membership). Each table also has a scope: directory tables (users, teams, projects, credentials, connectors, tokens, …) follow the organization; cluster tables (VMs, disks, images, networks, nodes, datastores, metering, …) follow the hardware. Auth tables replicate to servers only. These stay on each host and are never replicated:

  • the Raft log and the cluster identity (node certificate and key, CA) in the control plane’s state directory;
  • configuration files in /etc/glidex/;
  • netd’s own state database and stord’s configuration;
  • VM runtime directories, console logs, and disk and image files on node-local datastores;
  • on agents, the outbox of status writes not yet acknowledged.

Reconciliation

Controllers are level-triggered loops: each round observes the host, records what it saw in status, and takes the smallest step toward the spec. Every step is idempotent and safe to interrupt, so a crash at any point is finished or undone by the next round.

 API spec write ──┐
 exit watch (pidfd per shim and hypervisor) ──┤

 resync every reconcile.resync_secs ──┤      (dedup by     (reconcile.     observe → act → write status

One deduplicating queue (controller/queue.rs) feeds the workers: a key is processed by one worker at a time, failures back off per key, and the periodic resync means a missed event only delays convergence.

VmManager::start_controllers (controller/mod.rs) starts the node role tasks (workers, resync, datastore probe, device pool preparation, self-report, OVN chassis) and, on servers, the server role tasks (scheduler pass, cluster network controller). The leader-only loops do nothing on a follower.

Startup and adoption

main.rs loads the configuration, opens the store, and calls VmManager::initialize (controller/startup.rs) before any controller acts or any listener opens:

  1. Observe every VM. A live instance that matches status.instance is adopted as it is (event Adopted); one only instance.json knows of is adopted from it (AdoptedUnrecorded).
  2. List units and runtime directories with no VM record as orphans. They are reported (GET /system/reconcile), never touched.
  3. Only then tell netd which VMs own ports, so it never drops a port of a VM that is still running.
  4. Start the controllers, then the listeners.

Invariant: at most one hypervisor instance per VM. Before a launch, the controller must positively establish that no instance is live (unit state, recorded pids with their start times, sockets). If it can’t tell, the VM is Unknown and nothing is launched.

Host boot

glidex-vm@ units are never enabled: relaunching VMs after a reboot is the control plane’s decision. The shim records the host’s boot id; a recorded instance from an earlier boot is an exit with cause HostReboot. The VM’s on_host_boot policy (resume by default, or stop, with a site default in reconcile.on_host_boot) then decides whether the controller launches it again or sets its desired power to stopped. At host shutdown, systemd stops each unit: the shim presses the guest’s power button, waits the grace period, then stops the hypervisor.

Where the scheduler fits

The scheduler is called inside VM admission: in a cluster, create_vm_with asks scheduler::pick_node for a node and writes the placement in the same commit as the VM. If no node fits, the VM is created with Scheduled=False/Unschedulable and the reason for each node, and the leader’s placement pass (place_pending, every few seconds) tries again as nodes and capacity change. Placement is decided once and then sticks; an administrator can place a stopped or lost VM again. Filters (capacity, hugepages, NUMA and CPU policy, hypervisor, devices, disks’ datastores, networks, architecture) and scoring are described in Algorithms.

Agents, the UI and host pages

An agent serves no API: auth tables replicate to servers only, so an agent has no users, sessions or tokens. It removes its api.sock (gxctl logs in to a server instead) and its ui.sock answers API requests with 421 use_a_server. Its glidex-ui reports itself to the control plane (PUT /ui/self) and learns which server’s UI to send browsers to: a GET is redirected (307) to that server, / to the agent’s own Host page (/hosts/<node>). Servers publish their UI address in their node record (cluster.ui_url, else what their glidex-ui reports). Host pages work from any server for any node by sending host-only calls with X-Glidex-Target-Node (see the request path). Code: glidex-ui/src/home.rs, api/relay.rs.

A datastore is where disks live. Its record is cluster-wide; each node reports what it finds at it. Disks are reached through a driver that hands back a volume binding: a file (qcow2 or raw) or a raw block device.

Each VM has one serial console on a PTY whose master the shim holds. A proxy thread in the shim owns the PTY, the console socket and the log: it fans output out to any number of clients and is the log’s only writer. New clients get the log replayed first (minus the terminal queries a guest leaves in it), and the listener outlives the PTY, so a dead guest’s last output is still visible. The browser gets a short-lived single-use ticket (CreateConsoleTicket), then opens /vms/{id}/console/ws; api/vms.rs::console_ws and the RPC share service::vm::console_target/console_connect. In a cluster tickets live in the leader’s memory: a follower forwards ticket requests to the leader, and the server that takes the WebSocket redeems the ticket there (POST /cluster/v1/console-ticket), so the two requests may reach different servers. For a VM on another node, the server that authorized the request relays to that node.

Code: glidex-vm-shim/src/proxy.rs, api/vms.rs. Design: 02-console.md. Using it: Console.

Images, firmware and kernel extraction

  • Cloud images come from a built-in catalog or a URL. The download pipeline streams to a temporary file while hashing, verifies the digest and image header, converts raw to qcow2, makes the file read-only and renames it into place (images/download.rs).
  • Firmware (EDK2 for Cloud Hypervisor, OVMF for QEMU) is pinned and imported as firmware images (images/firmware.rs).
  • Kernel images (kernel, initramfs, command line) for direct kernel boot can be extracted from a cloud image. The image’s filesystems are only ever read inside a short-lived extractor VM: a pinned kernel with an initramfs glidex builds boots with the image attached read-only and writes the boot files to a raw disk, which the host parses as a checked stream. The run goes through the same runner and unit sandbox as a VM (images/extractor.rs, controller/extract.rs).
  • Firmware-booted guests get a NoCloud seed built per launch (cloud_init.rs) with the VM’s guest credential (credentials.rs).

Design: 10-images.md, 23-kernel-boot.md, 08-credentials.md. Using it: Kernel boot.

Hypervisors

Hypervisor drivers (hypervisor/: cloud_hypervisor.rs, qemu.rs, pylon.rs) are stateless. A driver turns a VM’s config into the full command line the shim runs, and performs runtime operations (observe, pause/resume, VFIO hot-plug) over the hypervisor’s socket with glidex-hv-client. Because everything is a path, a restarted control plane manages instances exactly as before. Pylon is a Cloud Hypervisor fork with fast CPU core elasticity: its driver reuses Cloud Hypervisor’s arguments and API client, adds --pylon with a shared memory page and pylond’s socket, and sends pylond policy updates (minimum and maximum cores, weight) for a running VM. A node reports whether pylond runs. Design: 04-hypervisors.md, 30-pylon.md.

Devices

  • PCI and VFIO: the control plane scans sysfs read-only (pci.rs); binding a device to vfio-pci (and SR-IOV VFs) is netd’s job, at boot through glidex-vfio-boot.service or on demand. VM units may open only the device nodes VMs use.
  • Topology: each node’s NUMA nodes, CPUs, per-node memory and hugepages, and the NUMA node of each device, as a small summary in the node’s replicated status (topology.rs); the full PCIe tree on request. The scheduler uses it for NUMA and dedicated-CPU policies.
  • Pools: pci.pools in the configuration groups devices (GPUs, NICs) that VMs ask for by count; tenants get shares of them (tenant_device_pools). Pools marked prepare are bound to vfio-pci on each node at start.

Design: 22-host-topology.md, 27-gpu-vms.md. Operating it: PCI passthrough, Host resources.

Metering

Each node samples its VMs and disks every metering.sample_secs: CPU and memory from each VM unit’s cgroup (the unit turns on accounting), disk I/O from the hypervisor’s counters, network traffic from OVS bridge ports, external traffic from NAT counters (conntrack accounting on OVN gateways), stored size from the volumes. A ledger turns readings into hourly usage rows exactly once: deltas and the cursors that produced them commit in one transaction. In a cluster each node accumulates locally and ships closed hours to the leader (/cluster/v1/ledger), which merges them and rolls up daily totals, 5-minute rate series and billing-month percentiles. Usage is read through UsageService and MetricsService (/usage, /vms/{id}/stats).

Code: metering/ (sampler.rs, sources.rs, net.rs, ledger.rs, rates.rs, retention.rs, query.rs). Design: 13-metering.md. Using it: Usage.

Life of a VM create

A user creates a VM from an image and starts it. Below, a three-server cluster with the VM placed on an agent; on a standalone host the forwarding, Raft and watch steps fall away and everything happens in one process.

 UI / gxctl        server A          leader B             agent C               shim / hypervisor
 (follower)
   │ CreateVm ────▶ authenticate
   │                gate: write ───▶ authenticate (fwd principal)
   │                                 service::vm::create_vm: Cedar checks
   │                                 VmManager::create_vm_with: admission,
   │                                 scheduler::pick_node → C
   │                                 Db::write: VM + disk + event + IPAM
   │                                 ── Raft ──▶ A, others apply

   │                                                       make root disk

   │                                                       start glidex-vm@<id> ──▶ shim: instance.json,
   │                                                                                 spawn hypervisor,
   │                                                                                 READY
   │                                                       observe: Running ◀───────
   │                                    ◀─ status-write ── 
   │ ◀── watch event / wait answers ── (leader writes status; replicated)
  1. Client. The web UI calls VmService.CreateVm over gRPC-Web (createVm in crates/glidex-ui/ui/src/api.ts); glidex-ui proxies /api/* to the control plane’s ui.sock. gxctl’s create command calls the same RPC through its generated client (src/bin/gxctl/vm.rs) over api.sock or HTTPS :8841. A REST client would POST /vms with the same message as JSON.
  2. Listener and authentication. serve.rs tags the request with its listener and peer; api::authenticate resolves the principal (the session cookie, the peer uid, or a token).
  3. Cluster gate. CreateVm is a WRITE in the operation table, so on a follower gate::cluster_gate forwards it to the leader over :8842 with the principal attached. The leader runs the rest.
  4. RPC adapter. api/rpc/mod.rs finds the operation (action createVm) and builds the Call; api/rpc/vm.rs calls service::vm::create_vm.
  5. Service. create_vm checks Cedar for the compound request: createVm on the project, then useDisk, useCredential, attachNetwork/useNetwork, readImage, useHostPath and device pools for everything the request names, and that the project’s tenant is admitted here. It builds the VmConfig and calls VmManager::create_vm_with.
  6. Admission and placement. Under the VM cache’s write lock, state.rs validates, checks quotas and claims, plans the root disk on the default datastore, and places the VM: on a standalone host on local, in a cluster with scheduler::pick_node. Disks bind to the chosen node (unless shared). One Commit writes the VM (spec.power as requested, stopped by default), its disks, the Created event and IPAM reservations.
  7. Store. Db::write commits locally on a standalone host; in a cluster the leader proposes the write set to Raft and returns once it is committed and applied. The audit entry is written; the call answers at once, or with wait once the VM converges (service::vm::respond → wait_converged).
  8. Reaching the node. Servers see the change through the store’s subscription (VmManager::cache_sync); the agent through its watch (cluster/agent.rs), which applies it to its cache. Both queue the disk and the VM on the local work queue; only the node the VM is placed on acts (VmManager::is_local).
  9. Disk. The disk controller makes sure the node has a verified copy of the image (controller/image_cache.rs), then has the datastore driver create the root disk (a qcow2 overlay, or an LVM-thin snapshot through stord). Its status write goes to the leader (/cluster/v1/status-write).
  10. Start. Once the spec says running (in the request, or after a later StartVm), controller/vm.rs waits for DisksReady and NetworkReady, establishes that no instance is live, then: regenerates the cloud-init seed; for each NIC records it in status.nics and asks netd to attach the port; writes launch.json with the driver’s command line; records the intent in status.instance (instance id, boot id, generation); and asks the runner (instance/runner.rs) to start glidex-vm@<id> over D-Bus.
  11. Shim. glidex-vm-shim validates launch.json, writes instance.json, starts the console proxy, spawns the hypervisor on a fresh PTY, waits for its API socket, binds shim.sock and tells systemd it is ready (supervisor.rs). The control plane opens a pidfd exit watch on the shim and the hypervisor.
  12. Status back. The next round observes the guest through the hypervisor socket (Cloud Hypervisor vm.info, QEMU query-status), sets phase Running, Ready=True and observed_generation, and sends the status to the leader, which checks and commits it. The change replicates; watchers (WatchService.Watch, used by the UI’s live.tsx, and GET /watch) get a modified event, and a waiting call answers 200 with the VM.
