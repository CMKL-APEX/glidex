Glidex

Performance and benchmarks

This page collects the figures a contributor should know: what has been measured, where, when and how, and how to measure it again. Glidex has no benchmark suite yet (see Gaps), so most figures come from host acceptance runs recorded in the specs and in pull requests, from CI timings, and from a few read-only measurements on a development host.

How to read the numbers

  • Every figure was taken once, on one date, on one machine. It is a data point, not a guarantee or a service level.
  • The hardware is stated where it was recorded. Many host runs in the specs say only “this host” (the project’s development host); for those the hardware is given as not recorded.
  • Some figures are design estimates, not measurements. They are marked as such. The cluster scale envelope is the main one.
  • Test durations (for example “the kernel-boot test passed in 68 s”) are the wall time of a whole test: pulling or building artifacts, booting, logging in, checks and teardown. They are not boot times.
  • Fixed rates in the metering runs (iperf -b 100M, fio at 500 IOPS) check that metering counts correctly. They say nothing about the maximum throughput of the data path.
  • Defaults and limits (timeouts, retry intervals, size caps) are configuration, not measurements. Where they help read a figure they are listed separately and labelled as defaults.

Cluster scale and Raft

The scale envelope in 14-clustering.md §4.1 is a design estimate, built from the measured metering sizes and typical NVMe and LAN latencies. The scale run that would measure it (a synthetic 2,000 VMs on 50 simulated nodes) is listed as not done in 14-clustering.md §20.

Sustained writesabout 5–20 per second at 2,000 VMsabout 150–300 per secondone write lane; each write about 3–8 ms on NVMe in a LAN (estimate)
Burst500 VM creates take 20–40 s of write lanesame lane

Raft defaults (configuration): heartbeat 250 ms, election timeout 1–2 s, node heartbeat every 5 s.

Measured in tests rather than at scale:

  • The slowest single cluster test took about 16.5 s on CI (#43, 2026-10-17).
  • cluster_tests (42 tests) took 265 s in the CI run of 2026-10-22, the longest test binary in the workspace.
  • Write-set replay checking (GLIDEX_CHECK_WRITE_SETS=1) costs little: the control plane’s tests took 461.9 s plain and 469.2 s with it, on CI (#43).

Metering

From 13-metering.md §15.6–§15.7 and #13 (2026-10-07). The load test is metering/bench.rs: 200 VMs in 10 projects, 2 NICs and 2 disks each, 10 networks, a month of history with every 5-minute slot filled. Hardware not recorded.

First buildCurrent (per-project key ranges)
One sampling round41 ms39 ms (budget 15 s)
Usage query, one project, one month, by VM972 ms146 ms (target 200 ms)
Bandwidth p95, one project, one month, by VM1.65 s254 ms

With 2 days of history and CPU and memory slots (M4): a round takes 49 ms and the CPU and memory p95 query 20 ms; VM slot rows add about 20 % to the slot table.

Size: one day for this fleet is 23k hourly rows (387 B each) and 19k slot rows (669 B each). The database file grows to about 3× the live data (copy-on-write pages). At the default retention that is about 2.5 GB for 200 VMs, roughly 12 MB per VM.

Accuracy on a host (2026-10-05, two Debian 13 guests): metered CPU was within +0.03 % (Cloud Hypervisor) and +0.13 % (QEMU) of the cgroup’s own counter over 300 s of load, and within +0.21 % across a control-plane restart.

Measure it yourself

All of these read only, except where a test says it creates VMs; run those on a host you can use for testing.

API latency

On a host running Glidex, as a user who can use the API socket:

for p in /health /vms /images; do
  for i in $(seq 100); do
    curl -s -o /dev/null -w '%{time_total}\n' \
      --unix-socket /run/glidex-cp/api.sock "http://x$p"
  done | sort -n | awk -v p=$p '{a[NR]=$1*1000}
    END {printf "%s p50 %.1f ms p95 %.1f ms\n", p, a[int(NR*0.5)], a[int(NR*0.95)]}'
done

Note the number of objects each list returns, the node’s Raft role and the host’s load with the figures.

Real-boot and host tests

The ignored tests in crates/glidex-control-plane/tests/functional_tests.rs boot real guests and print their progress. They need /dev/kvm, Cloud Hypervisor or QEMU, and a UEFI-bootable image; see the file’s header for the variables (GLIDEX_TEST_IMAGE, GLIDEX_TEST_KERNEL, GLIDEX_TEST_INITRD, GLIDEX_TEST_CATALOG, GLIDEX_TEST_FIRMWARE, GLIDEX_TEST_GPUS). Time them with --nocapture and the shell:

GLIDEX_TEST_IMAGE=~/images/resolute-server-cloudimg-amd64.raw \
  cargo test -p glidex-control-plane --test functional_tests -- --ignored --nocapture
# one test
time cargo test -p glidex-control-plane --test functional_tests \
  extracted_kernel_boots_its_image -- --ignored --nocapture

They include firmware_boot_with_generated_cloud_init, kernel_boot_with_initrd, kernel_image_boot_with_generated_cloud_init, extracted_kernel_boots_its_image, guest_kernel_updates_are_followed, vm_survives_control_plane_restart, catalog_image_boots_and_root_grows, nat_network_e2e, bridged_uplink_e2e, afxdp_uplink_e2e, vhost_user_e2e, numa_placement_e2e and lvm_root_disk_boots, most with a qemu_ twin.

Gaps

Not benchmarked yet, stated plainly:

  • No cargo bench or Criterion suites. The only load test is the ignored metering/bench.rs.
  • No cluster scale run. The §4.1 envelope is an estimate; Raft write latency, leader CPU, database growth and snapshot install time have not been measured.
  • No API write latency or throughput figures, and no figures for the RPC API, TLS, or requests forwarded from followers.
  • No VM boot, stop or start-to-network times separate from test wall time.
  • No storage throughput (IOPS or MB/s ceilings) for dir, shared-dir or lvm datastores, and no timings for disk moves or image copies.
  • No network throughput for tap, AF_XDP or vhost-user with OVS-DPDK, and none across a Geneve tunnel.
  • Hardware is missing from most recorded host runs.
  • No regression tracking: nothing is measured on every change.

Suggested next benchmarks:

  1. The §4.1 scale run: 2,000 VMs on 50 simulated nodes with a fake netd and real Raft on three hosts; record write rate, write latency per entry, leader CPU, database size and snapshot install time.
  2. An API latency script in the repository (reads and writes, Unix socket and TLS, on the leader and on a follower), with object counts.
  3. Time from POST /vms/{id}/start to Running and to the first console line, per backend and boot mode, from the ignored tests’ own timestamps.
  4. fio and iperf3 at full rate per datastore driver and per port type, with the hardware recorded.
  5. A Criterion suite for hot paths: scheduler filtering and scoring at 50 nodes, OVN NB diff per round, metering queries.
  6. Record the hardware with every host run in the specs and pull requests.
