Glidex

Repository and code organization

This page maps the repository: what each crate is, which process runs where, how the control plane is split into modules, and where the protos, the web UI, the packaging and the docs live. For how these pieces work together at run time, see Architecture.

Links to source files point at main on GitHub.

glidex-api: protos and generated code

The proto files are the source of truth for every API type (spec/18-grpc.md G-D3).

crates/glidex-api/
├── build.rs        protox → checks → operations.rs, fields.rs → connectrpc-build
├── buf.yaml        buf lint (STANDARD) and breaking (FILE) rules
├── buf.gen.yaml    TypeScript for the UI → ../glidex-ui/ui/src/gen
├── proto/glidex/<area>/v1/<area>.proto
│                   access, auth, cluster, common, directory, host,
│                   network, storage, system, tenancy, usage, vm, watch
├── proto/glidex/api/v1/options.proto   (glidex.api.v1.op), (glidex.api.v1.secret)
├── proto/glidex/api/v1/errors.proto, types.proto
├── proto/google/rpc/error_details.proto   vendored ErrorInfo
└── src/lib.rs      generated modules, OPERATIONS, operation(), unknown_field()

What build.rs does on every cargo build, with no protoc or buf needed:

  1. Compiles every .proto under proto/ with protox.
  2. Fails the build if a rule is broken:
    • every RPC has a (glidex.api.v1.op) option with an action, a kind (KIND_READ or KIND_WRITE) and, if any, a REST twin in the form "<METHOD> /path";
    • every field’s JSON name equals its proto name (json_name, G-D11), so REST stays snake_case;
    • no response message reaches a field marked [(glidex.api.v1.secret) = true].
  3. Writes operations.rs (glidex_api::OPERATIONS: procedure, service, method, Cedar action, kind, REST twin, streaming) and fields.rs (every message’s JSON field names, which the server uses to refuse unknown fields).
  4. Writes a descriptor set (glidex_api::DESCRIPTOR_SET, for server reflection) and runs connectrpc-build for messages (buffa types), service traits and clients, included as glidex_api::proto.

The TypeScript for the UI is not generated by cargo: run buf generate in crates/glidex-api (after bun install in crates/glidex-ui/ui). Its output in crates/glidex-ui/ui/src/gen/ is committed, and CI fails when it is stale.

glidex-control-plane

The control plane is one library (src/lib.rs) with two binaries: src/main.rs (the server) and src/bin/gxctl/ (the CLI). Its tests are in tests/; the Cedar schema and shipped policies in policies/.

gxctl

src/bin/gxctl/main.rs holds the interactive shell (rustyline) and the dispatch; each area has its own file (vm.rs, storage.rs, network.rs, access.rs, cluster.rs, host.rs, directory.rs, tenancy.rs, usage.rs, admin.rs; dirlogin.rs for logging in at a directory). client.rs has the REST client and the Connect transport that carries the generated RPC clients over gxctl’s own connection; config.rs the login profiles; console.rs the console attach loop. Only the global options are clap; commands are parsed by hand.

Tests

tests/ holds one integration test binary per area (vm_tests.rs, storage_tests.rs, datastore_tests.rs, cluster_tests.rs, rpc_tests.rs, tenancy_tests.rs, …) with shared helpers in tests/common/. functional_tests.rs boots real guests; most of it is #[ignore]d. See Contributing.

Web UI

crates/glidex-ui/
├── src/main.rs        serve ui/dist (or GLIDEX_UI_DIR), proxy /api, TLS, Host allowlist; --dev
├── ui/                Vite + React + TypeScript + Tailwind
│   ├── src/App.tsx    routes → pages
│   ├── src/pages/     one file per page: Dashboard, VmDetail, Disks, Datastores, Cluster, …
│   ├── src/components/  forms, dialogs, cards (CreateVmForm, VmActions, PlacementPicker, …)
│   ├── src/api.ts     every API call; rpc() for RPCs, REST for the rest
│   ├── src/session.tsx  the kit's session layer with Glidex's adapter; capability checks (useCan)
│   ├── src/live.tsx   WatchService stream: live updates
│   └── src/gen/       generated by buf generate (committed; don't edit)
├── kit/               @glidex/ui-kit: Modal, TokenReveal, password form, SSO buttons,
│                      step-up dialog, session provider; takes an AuthApi adapter
└── e2e/               Playwright suite, run with bun

api.ts sends RPCs over gRPC-Web (createGrpcWebTransport, base /api) with JSON messages, through rpc(Service.method.x, req), which returns the proto JSON the REST twin would answer. REST stays for what has no RPC (health, login and logout, OIDC redirects, CSV exports, the console WebSocket, GET /auth/whoami). The browser reaches the control plane through glidex-ui, which forwards /api to ui.sock; that is the only listener that takes gRPC-Web with a session cookie.

The UI is built with bun (bun install, bun run build), never npm. ui/ is the bun workspace root and lists ../kit as a workspace, so bun install in ui/ covers both. The kit holds the login and session pieces that aren’t Glidex-specific, for reuse by other management UIs: it never imports api.ts or types.ts; the app hands it an AuthApi adapter (methods, whoami, login, startSso, logout). Passkeys, accounts, roles and capability checks stay in ui/. See kit/README.md.
