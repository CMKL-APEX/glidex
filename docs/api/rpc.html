Glidex

RPC API

Every operation in the REST API that has a proto message is also an RPC. Same port, same credentials, same authorization and audit: the RPC and its REST twin run the same code.

Protocols

ProtocolWhereNotes
gRPC:8841 (HTTP/2 over TLS), api.sock (HTTP/2 without TLS)Binary protobuf
Connect:8841, api.sockUnary calls are plain POSTs over HTTP/1.1 or HTTP/2, with application/proto or application/json bodies; easy to call with curl. Server streams work over HTTP/1.1 too; the console’s bidirectional stream needs HTTP/2
gRPC-WebThe web UI onlyRefused on :8841 and api.sock (PERMISSION_DENIED, reason protocol_not_allowed)

All three are answered by the same server on the same port as REST; there is no separate RPC port. Procedures live at /glidex.<area>.v1.<Service>/<Method>, for example /glidex.vm.v1.VmService/ListVms.

Methods are unary except three streams, below. Limits: 4 MiB per message; a client deadline (grpc-timeout, connect-timeout-ms) on a unary call is honored up to 5 minutes.

Authentication

ListenerMetadata
:8841authorization: Bearer <token>
api.sockNone: you are the Unix user you connect as

Session cookies are refused on RPCs outside the web UI (UNAUTHENTICATED, reason cookie_not_accepted): use a token. Public methods (SystemService.GetServerInfo and the LoginService methods) need no credential. See API overview.

A token from a workload federation’s exchange is sent the same way. The exchange itself, POST /auth/exchange, is REST only: it has no RPC (Token exchange).

Optional metadata:

  • x-glidex-consistency: local: in a cluster, read from the server you reached without waiting for it to catch up with the leader.
  • x-glidex-target-node: <node id>: on a cluster server, run a glidex.host.v1 method (or ClusterService.LeaveCluster) on that node instead, authorized on its host. On other methods it is bad_target_node (Host networking and PCI).

Responses carry x-request-id.

Errors

Errors carry a gRPC status and, as an error detail, a google.rpc.ErrorInfo with domain: "glidex", reason set to the same stable code the REST API returns in error (codes), and metadata.http_status set to the status REST would have answered ("422", say). When the REST error has details, a glidex.api.v1.ErrorDetails detail holds them as JSON text in json. Branch on reason, not on the message.

A Connect error with a JSON body looks like this (the detail’s value is the encoded ErrorInfo):

{
  "code": "not_found",
  "message": "VM not found: <vm-id>",
  "details": [{"type": "google.rpc.ErrorInfo", "value": "<base64>"}]
}
StatusReasons
UNAUTHENTICATEDunauthenticated, login_failed, reauth_required, cookie_not_accepted
PERMISSION_DENIEDforbidden, login_not_allowed, tls_required, ticket_required, tenant_suspended, origin_not_allowed, csrf_failed, protocol_not_allowed, agent_no_local_api, not_admitted, …
RESOURCE_EXHAUSTEDquota_exceeded, tenant_quota_exceeded, insufficient_storage, too_large, rate_limited, slow_down
NOT_FOUNDnot_found, oidc_disabled
ABORTEDconflict (a name taken, a concurrent change): read again and retry
FAILED_PRECONDITIONOther 409 codes (ambiguous, would_lock_out, confirmation_required, managed_by_connector, not_provisioned, not_pulled, no_source, sync_running, …), unsupported_on_host
INVALID_ARGUMENT400 and 422 codes: bad_request, invalid, invalid_*, bad_target_node, issuer_unreachable
UNAVAILABLEnot_leader, use_a_server, leader_changed, cluster_unavailable, and 502/503 codes (netd_unavailable, node_unreachable, too_many_watchers, console_unavailable, …)
INTERNALinternal, persistence_error and other 500 codes. The message is generic and names the request id; the details are in the server log
UNIMPLEMENTEDA method this server doesn’t have (an older version during an upgrade)

precondition_failed (a VM changed since you read it: a stale expected_resource_version) has no status of its own yet and arrives as INTERNAL, with a generic message. Its ErrorInfo still has the reason, http_status "412" and, in ErrorDetails, the current resource_version: check the reason before treating INTERNAL as a server fault.

Streams

MethodKindREST twin
WatchService.WatchServer streamGET /watch
WatchService.WatchEventsServer streamNone
VmService.ConsoleBidirectional streamThe console WebSocket

Opening a stream is authorized and audited like a unary call: a refusal is the call’s error, before any message. Over native gRPC that error arrives with its status but without its ErrorInfo; use the Connect protocol for streams if you need the reason. Streams are served by the server you reach and are not forwarded to the leader.

Watch sends the same events as GET /watch (Live changes). The request takes kinds (WATCH_KIND_VM, …_DISK, …_IMAGE, …_NETWORK by default; also …_NODE, …_IMPORT, …_CLUSTER, …_POLICY, …_DATASTORE) and project. Each WatchResponse has a type (WATCH_EVENT_TYPE_ADDED, …_MODIFIED, …_DELETED, …_SYNCED, …_EXPIRED), kind, id and the object in a oneof (vm, disk, image, network, node, import_plan, cluster, policy, datastore). After 15 s without an event the server sends WATCH_EVENT_TYPE_KEEPALIVE, so proxies keep a quiet stream open; ignore it. The stream ends after 5 minutes with …_EXPIRED: open a new one for a fresh snapshot.

WatchEvents follows one VM, disk, image or network (kind, id): the events it has (as its events list answers them), …_SYNCED, then each new event as it happens, with keep-alives and expiry as on Watch. It needs read access to the object.

Console is the VM’s serial console both ways. The first request must be {open: {id}}, within 30 s; then send keystrokes as {input: <bytes>}. Responses are {output: <bytes>}: the replayed console log, then the guest’s output. Closing your side of the stream ends the call. A browser session would need open.ticket (CreateConsoleTicket), but browsers use the WebSocket: gRPC-Web can’t stream both ways. gxctl uses this RPC over the Connect protocol.

Health

grpc.health.v1.Health/Check is served on every listener without a credential, like GET /health. It is answered by the server you reach.

Getting the protos

On the host, server reflection (grpc.reflection.v1 and v1alpha) on api.sock lets tools such as grpcurl and buf curl list and call methods without the proto files. It is offered on api.sock only: :8841 answers 404.

Elsewhere, take the protos from the repository: crates/glidex-api/proto. Packages are versioned (v1); a breaking change would come as a v2 package served next to v1. Field names and numbers are the compatibility contract, and JSON names are the snake_case field names.

Generate clients with buf. A buf.gen.yaml for TypeScript (Connect-ES), next to a checkout of the repository:

version: v2
inputs:
  - directory: glidex/crates/glidex-api/proto
plugins:
  - remote: buf.build/bufbuild/es
    out: src/gen
    opt:
      - target=ts

git clone https://github.com/CMKL-APEX/glidex.git
buf generate

Other languages work the same way with their protobuf and gRPC or Connect plugins (managed mode can set package options such as go_package, which the protos don’t declare).

Examples

Connect with curl, JSON in and out:

curl --cacert tls.crt \
  -H "Authorization: Bearer <token>" \
  -H 'Content-Type: application/json' \
  -d '{}' \
  https://host.example.org:8841/glidex.system.v1.SystemService/WhoAmI

curl --cacert tls.crt \
  -H "Authorization: Bearer <token>" \
  -H 'Content-Type: application/json' \
  -d '{"project": "lab"}' \
  https://host.example.org:8841/glidex.vm.v1.VmService/ListVms

On the host, through the socket:

curl --unix-socket /run/glidex-cp/api.sock \
  -H 'Content-Type: application/json' -d '{}' \
  http://localhost/glidex.system.v1.SystemService/WhoAmI

grpcurl on the host’s socket, with reflection:

grpcurl -plaintext -unix /run/glidex-cp/api.sock list
grpcurl -plaintext -unix /run/glidex-cp/api.sock describe glidex.vm.v1.VmService
grpcurl -plaintext -unix -d '{}' \
  /run/glidex-cp/api.sock glidex.system.v1.SystemService/WhoAmI

Remotely, give the tools the protos. buf curl:

buf curl --schema glidex/crates/glidex-api/proto \
  --cacert tls.crt \
  -H "Authorization: Bearer <token>" \
  -d '{"id": "<vm-id>", "wait_secs": 60}' \
  https://host.example.org:8841/glidex.vm.v1.VmService/StartVm

grpcurl:

grpcurl -cacert tls.crt \
  -import-path glidex/crates/glidex-api/proto -proto glidex/vm/v1/vm.proto \
  -H 'authorization: Bearer <token>' \
  -d '{}' \
  host.example.org:8841 glidex.vm.v1.VmService/ListVms

Write requests take the same fields as the REST body; the REST query parameters become fields too (?wait=60 is wait_secs: 60, If-Match is expected_resource_version).
