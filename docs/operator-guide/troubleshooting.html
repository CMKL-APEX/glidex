Glidex

Troubleshooting

Start with the services and their logs, then look up the error code the API returned. Most problems are a stopped service, a missing group membership, a path the glidex user can’t read, or the host network.

Check the services

systemctl status glidex-control-plane glidex-netd glidex-ui glidex-authd.socket
journalctl -u glidex-control-plane -b

At start, the control plane logs one line per check. Each should end in OK:

  Checking disk tools... OK
  Loading configuration... OK
  Opening database... OK
  Checking KVM access... OK (VMs open it in their glidex-vm units)
  Loading VMs... OK (2 VMs, 1 running, VM runner: systemd)
  Checking UEFI firmware (Cloud-Hypervisor)... OK (image cloudhv-edk2)
  Checking UEFI firmware (QEMU)... OK (image ovmf)
  Checking networking... OK
  Loading authorization policies... OK
LineMeansDo
Checking disk tools... MISSING (...)qemu-img, sgdisk or another disk tool is missing; image and disk operations fail.Re-run the installer.
Loading configuration... FAILED/etc/glidex/control-plane.json has an error or an unknown key. The control plane doesn’t fall back to defaults.Fix the file; the message names the field.
Checking KVM access... MISSINGNo /dev/kvm.See KVM.
Checking KVM access... NO ACCESSThe glidex user isn’t in the kvm group.Re-run the installer, which adds it.
Checking networking... LIMITEDThe control plane can only read netd’s status: it isn’t running as the glidex group.Use the installed unit; don’t run the control plane by hand as yourself.
Checking networking... UNAVAILABLEglidex-netd isn’t running or not installed.systemctl status glidex-netd; re-run the installer without --no-networking.
Loading authorization policies... FAILEDA policy file in /etc/glidex/policies is invalid or unreadable.Fix it; the directory must be root:glidex, mode 0750.

Logs of one VM: journalctl -u glidex-vm@<vm-id>, and gxctl events <vm> for what Glidex did with it. For log locations and more detail, see Maintenance.

Error codes

API errors come back as JSON with a code, a message and sometimes details:

{"error": "quota_exceeded", "message": "…", "details": {"quota": "…"}}

gxctl and the web UI show the code and message. The common ones:

CodeMeansDo
unauthenticatedNo valid login or token.Log in again; check the token’s expiry.
reauth_requiredThe action needs a recent login (cluster changes, installing OVS, uplink and bridge changes, policies).Log in again and retry.
forbiddenYour roles or the site policies don’t allow it.Check gxctl whoami; ask for a role. See Access control.
not_foundNo such VM, network, image… in the project you’re using.Check --project / your default project (gxctl project use).
conflictA name is taken, or the resource is in use or busy (a disk claimed by a VM, a PCI device used by another VM, a DPDK NIC).Read the message: it names what holds it.

quota_exceeded, tenant_quota_exceededThe project or tenant would go over a quota.Raise it (gxctl project quota) or free resources.

Certificate fingerprints

Both the API (port 8841) and the web UI (port 5173) use a self-signed certificate unless you configured one. Before trusting it from another machine, compare its SHA-256 fingerprint with the one on the host:

sudo openssl x509 -in /run/glidex-cp/tls.crt -noout -fingerprint -sha256              # API
sudo openssl x509 -in /var/lib/glidex-ui/tls/ui.crt -noout -fingerprint -sha256       # web UI

The installer also prints both at the end.

  • The browser’s fingerprint differs. Something between you and the host presents another certificate (a proxy, or the wrong host). Don’t accept it until you know why.

  • gxctl says the certificate is not among the profile’s pins. The host’s certificate changed. Glidex regenerates it only in narrow cases (a configured certificate replaced, cluster rotate-ca, a re-init). Confirm the new fingerprint on the host through another channel, then:

    gxctl auth login --profile <name> --pin sha256/<new fingerprint> --rebind

    gxctl auth trust list shows a profile’s pins; gxctl auth trust fetch shows what a server presents.

  • A join says the server’s CA is not the one the token names. The cluster CA rotated after the token was issued (for example a server left). Issue a new token.

See TLS certificates to use your own certificates.

Paths the glidex user can’t read

The control plane and every VM run as the glidex system user, in a sandbox. Paths you give the API (disk images, kernels, cloud-init files) are opened by that user, so:

  • They must be readable by glidex. Your home directory usually isn’t, and /home, /root and /run/user are hidden from the services entirely.
  • They must not be under /tmp or /var/tmp: VMs have a private /tmp. The API refuses such paths (… is under /tmp, which VMs cannot see).
  • Passing host paths at all needs the host.paths permission (system-admin).

Put such files somewhere like /srv/glidex/ with sudo chgrp -R glidex /srv/glidex && sudo chmod -R g+rX /srv/glidex. Better still, import them as images, which Glidex stores itself.

KVM

ls -l /dev/kvm
lsmod | grep kvm
  • No /dev/kvm. Turn on virtualization (VT-x / AMD-V) in the firmware settings, then sudo modprobe kvm_intel or sudo modprobe kvm_amd. In a VM, nested virtualization must be on in the outer hypervisor.
  • /dev/kvm exists but VMs fail with permission denied. The glidex user must be in the kvm group: id glidex. The installer adds it when the group exists; re-run it, then restart the control plane.

Networking

Start with what the host can do:

gxctl ovs status            # netd access, OVS version and state, what is missing
gxctl networks              # networks and their status
gxctl bridges
sudo ovs-vsctl show
SymptomCheck
The Networking page says glidex-netd is not reachablesystemctl status glidex-netd, journalctl -u glidex-netd.
A network stays not readygxctl networks and the network’s status in the UI give the reason.
A VM on a NAT network gets no addressdnsmasq is installed (gxctl ovs status); a host firewall (ufw, firewalld) may drop DHCP or forwarded traffic: allow the NAT subnet.
A VM has an address but no internetIP forwarding (sysctl net.ipv4.ip_forward is 1), the host’s own route out, and the firewall’s FORWARD policy.
A bridged VM gets no addressThe bridge has an uplink (gxctl uplinks <bridge>), the link is up, and the LAN has a DHCP server (Glidex doesn’t run one there).
An uplink is held off the bridge after a rebootThe gateway didn’t answer at boot. Fix it, then gxctl uplink-reapply <bridge> <uplink>.
vhost-user NICs failThe host needs the dpdk profile, DPDK initialized and hugepages: gxctl ovs status.
Cluster VMs on different nodes can’t reach each otherUDP 6081 (Geneve) between the nodes’ tunnel addresses; the OVN card on the Cluster page shows the tunnels.
gxctl cluster status lists ports that don’t answerOpen them; see Ports between nodes.

If the host lost its own connectivity after an uplink change, wait a minute: an uncommitted address move is rolled back by itself. If you need to act at the console, gxctl uplink-rm <bridge> <uplink> puts the address back on the NIC.

Getting help

When you report a problem, include the Glidex version (gxctl cluster status in a cluster, or the control plane’s startup banner), what you ran, the error code and message, and the relevant journal lines. Remove host names, addresses, user names and anything secret from them first, and never include tokens, passwords or private keys.
