Glidex

Troubleshooting

Start with the services and their logs, then look up the error code the API returned. Most problems are a stopped service, a missing group membership, a path the glidex user can’t read, or the host network.

Check the services

systemctl status glidex-control-plane glidex-netd glidex-ui glidex-authd.socket
journalctl -u glidex-control-plane -b

At start, the control plane logs one line per check. Each should end in OK:

  Checking disk tools... OK
  Loading configuration... OK
  Opening database... OK
  Checking KVM access... OK (VMs open it in their glidex-vm units)
  Loading VMs... OK (2 VMs, 1 running, VM runner: systemd)
  Checking UEFI firmware (Cloud-Hypervisor)... OK (image cloudhv-edk2)
  Checking UEFI firmware (QEMU)... OK (image ovmf)
  Checking networking... OK
  Loading authorization policies... OK
LineMeansDo
Checking disk tools... MISSING (...)qemu-img, sgdisk or another disk tool is missing; image and disk operations fail.Re-run the installer.
Loading configuration... FAILED/etc/glidex/control-plane.json has an error or an unknown key. The control plane doesn’t fall back to defaults.Fix the file; the message names the field.
Checking KVM access... MISSINGNo /dev/kvm.See KVM.
Checking KVM access... NO ACCESSThe VMs, which run as glidex, can’t open /dev/kvm: glidex isn’t in its group (usually kvm), or its mode doesn’t let that group read and write it.ls -l /dev/kvm; re-run the installer, which adds glidex to the group.
Checking networking... LIMITEDThe control plane can only read netd’s status: it isn’t running as the glidex group.Use the installed unit; don’t run the control plane by hand as yourself.
Checking networking... UNAVAILABLEglidex-netd isn’t running or not installed.systemctl status glidex-netd; re-run the installer without --no-networking.
Loading authorization policies... FAILEDA policy file in /etc/glidex/policies is invalid or unreadable.Fix it; the directory must be root:glidex, mode 0750.

Logs of one VM: journalctl -u glidex-vm@<vm-id>, and gxctl events <vm> for what Glidex did with it. For log locations and more detail, see Maintenance.

Error codes

API errors come back as JSON with a code, a message and sometimes details:

{"error": "quota_exceeded", "message": "…", "details": {"quota": "…"}}

gxctl and the web UI show the code and message. The common ones:

CodeMeansDo
unauthenticatedNo valid login or token.Log in again; check the token’s expiry.
reauth_requiredThe action needs a recent login (cluster changes, installing OVS, uplink and bridge changes, policies).Log in again and retry.
forbiddenYour roles or the site policies don’t allow it.Check gxctl whoami; ask for a role. See Access control.
not_foundNo such VM, network, image… in the project you’re using.Check --project / your default project (gxctl project use).
conflictA name is taken, or the resource is in use or busy (a disk claimed by a VM or being moved, a PCI device used by another VM on the same host or sharing its IOMMU group, a DPDK NIC, a kernel image a VM boots, a datastore that still has disks or, for LVM-thin, image volumes).Read the message: it names what holds it.
ambiguousA name matches more than one thing.Use the id.
invalid_stateThe VM can’t do that now (start a running VM, attach what’s already attached).Check its state with gxctl get <vm>.
invalid_config, invalid, invalid_network, invalid_image, invalid_diskA bad request: wrong path, out-of-range value, unknown network.The message says which field.
invalid_datastoreA datastore name or path that isn’t allowed: the path must be a directory under /srv/glidex; an LVM-thin datastore takes a volume group and thin pool, not a path.See Datastores and LVM-thin.

SCIM provisioning

When an IdP can’t provision a SCIM connector, its test or logs show the endpoint’s answer:

AnswerCause and fix
401A wrong, expired or revoked token, or another connector’s. Check gxctl connector scim-token list <id>, make a new token, and enter it in the IdP.
403The connector is disabled, or isn’t --provisioning scim.
400 invalidFilterThe IdP filters on an attribute Glidex doesn’t: users by userName, externalId, emails, displayName; groups by displayName, externalId.
409 uniquenessA user with that userName, or a group with that name, already exists for the connector.

429Over 20 requests a second for the connector. IdPs retry after Retry-After.

Every SCIM write is in the audit log as system:scim:<connector-id>: gxctl audit --limit 50.

Certificate fingerprints

Both the API (port 8841) and the web UI (port 5173) use a self-signed certificate unless you configured one. Before trusting it from another machine, compare its SHA-256 fingerprint with the one on the host:

sudo openssl x509 -in /run/glidex-cp/tls.crt -noout -fingerprint -sha256              # API
sudo openssl x509 -in /var/lib/glidex-ui/tls/ui.crt -noout -fingerprint -sha256       # web UI

The installer also prints both at the end.

  • The browser’s fingerprint differs. Something between you and the host presents another certificate (a proxy, or the wrong host). Don’t accept it until you know why.

  • gxctl says the certificate is not among the profile’s pins. The host’s certificate changed. Glidex regenerates it only in narrow cases (a configured certificate replaced, which is served within a minute without a restart; cluster rotate-ca; a re-init). Confirm the new fingerprint on the host through another channel, then:

    gxctl auth login --profile <name> --pin sha256/<new fingerprint> --rebind

    gxctl auth trust list shows a profile’s pins; gxctl auth trust fetch shows what a server presents.

  • The ts.net name still gets a certificate warning with --tailscale-cert on. The UI serves its usual certificate until tailscaled hands it one: journalctl -u glidex-ui says why (HTTPS certificates not enabled for the tailnet, TS_PERMIT_CERT_UID not glidex-ui, the first certificate still being issued). See Tailscale certificates.

  • A join says the server’s CA is not the one the token names. The cluster CA rotated after the token was issued (for example a server left). Issue a new token.

See TLS certificates to use your own certificates.

Paths the glidex user can’t read

The control plane and every VM run as the glidex system user, in a sandbox. Paths you give the API (disk images, kernels, cloud-init files) are opened by that user, so:

  • They must be readable by glidex. Your home directory usually isn’t, and /home, /root and /run/user are hidden from the services entirely.
  • They must not be under /tmp or /var/tmp: VMs have a private /tmp. The API refuses such paths (… is under /tmp, which VMs cannot see).
  • Passing host paths at all needs the host.paths permission (system-admin).

Put such files in a directory of their own, such as /srv/vm-files: sudo chgrp -R glidex /srv/vm-files && sudo chmod -R g+rX /srv/vm-files. Not under /srv/glidex: that is where datastores are mounted and registered, and the installer offers what is mounted there as datastores. Better still, import them as images (a kernel as a kernel image), which Glidex stores itself.

KVM

ls -l /dev/kvm
lsmod | grep kvm
  • No /dev/kvm. Turn on virtualization (VT-x / AMD-V) in the firmware settings, then sudo modprobe kvm_intel or sudo modprobe kvm_amd. In a VM, nested virtualization must be on in the outer hypervisor.
  • /dev/kvm exists but VMs fail with permission denied. The glidex user must be in the kvm group: id glidex. The installer adds it when the group exists; re-run it, then restart the control plane.

PCI devices

  • PCI device … is used by VM … or … shares IOMMU group … with …. Another VM on that host holds the device or a device of its IOMMU group. Claims are per host: in a cluster, an unpinned VM goes to a node where the device is free.

  • A VM with PCI devices waits for a node. Its page lists each node’s reason: no PCI device … (the node doesn’t report it), or the VM holding it on every node that has it.

  • A VM’s DeviceHealthy condition is False. One of its devices fell off the bus or had new uncorrectable PCIe errors (event DeviceError). Glidex leaves the VM running; check gxctl node topology <node> --devices and the host’s dmesg, and cordon the device if you don’t trust it.

  • A VM’s NumaAligned condition is False. A NUMA_POLICY_PREFERRED VM didn’t fit on one NUMA node and spans the host.

  • A device on vfio-pci is not ready: in use by <process> (pid …), or release and VF counts are refused with IOMMU group … is in use by …. A VM, Glidex’s or another hypervisor’s, has the group open. Stop it; see Devices another hypervisor holds.

  • After a reboot, devices are back on their host drivers, or VFs are gone. Keep them with the installer’s --vfio-devices and --sriov; journalctl -u glidex-vfio-boot shows what was bound, skipped or failed. See Keep it across reboots.

  • A GPU request is refused: PCI device … has no NUMA node. The firmware reports no NUMA node for the device (-1), common on one-socket hosts; gpus aligns to NUMA nodes. Send numa_policy: NUMA_POLICY_PREFERRED with gpus. See GPU requests.

See PCI passthrough for host setup problems (IOMMU, vfio-pci, /dev/vfio permissions), and Host resources for hugepages, NUMA, dedicated CPUs, device pools and cordoned devices.

Getting help

When you report a problem, include the Glidex version (gxctl cluster status in a cluster, or the control plane’s startup banner), what you ran, the error code and message, and the relevant journal lines. Remove host names, addresses, user names and anything secret from them first, and never include tokens, passwords or private keys.
