Glidex

Maintenance

Day-to-day care of a Glidex host: updates, what keeps running when the services restart, backups, logs, and removing Glidex.

Updating

Pull the new source and re-run the installer, from your checkout:

git pull
cargo run -p glidex-install

It reuses the choices saved in /etc/glidex/install.conf, updates what is outdated, and restarts only the services whose binary or unit changed. Running VMs keep running. Details are in Installation.

With the kernel OVS profile saved (the default), a re-run turns off DPDK it finds on in Open vSwitch, which restarts ovs-vswitchd; with bridges it waits for --allow-ovs-restart. If you turned DPDK on with gxctl or the web UI and want to keep it, pass --ovs-profile dpdk once. See Back to the kernel profile.

Browsers check for a new web UI every time they load a page, so a reload is enough to get it. A tab left open from before the update keeps the old UI, and may fail to open pages it hadn’t loaded yet: reload it.

In a cluster, update one node at a time, agents first, then servers; see Rolling upgrades.

What survives a restart

Each running VM lives in its own systemd unit, glidex-vm@<vm-id>.service, in the glidex-vms.slice. The unit runs glidex-vm-shim, which supervises the hypervisor. These units are not part of the control plane’s service, so:

EventVMs
glidex-control-plane stops, restarts or is upgradedKeep running. At start the control plane finds each running instance and adopts it; nothing is relaunched.
glidex-ui restartsNot affected.
glidex-stord restartsKeep running: they hold their volumes open. stord keeps no state.
glidex-netd restartsKeep running. netd restores bridges, NAT and uplinks at start; vhost-user sockets survive in /run/glidex/vhost.
Host shutdownEach VM gets its power button and host_shutdown_grace_secs (default 60, at most 300) to shut down, then is stopped. VMs stop before netd and Open vSwitch.
Host bootThe control plane relaunches the VMs that were meant to be running (reconcile.on_host_boot: resume, the default) or leaves them stopped (stop). A VM on LVM-thin volumes has them activated and allowed again as it starts.

To see the VM units:

systemctl list-units 'glidex-vm@*'
systemctl status glidex-vm@<vm-id>

Don’t start or stop these units yourself: the control plane does, through polkit, and restarting a VM is its decision, never systemd’s. Use gxctl start / stop or the web UI.

gxctl events <vm> shows what happened to a VM: starts, exits, restarts and adoptions.

Backups

What to keep, on every host:

  • /var/lib/glidex-control-plane/.glidex/glidex.db and secrets.kek, together;
  • tls/ (or your own certificates), and cluster/ on a cluster node;
  • /etc/glidex/;
  • /var/lib/glidex/netd.db;
  • images/ and disks/ if you can’t re-create them, the disks/ of each datastore under /srv/glidex, and the gx-d-… volumes of LVM-thin datastores.

These files hold password hashes, token hashes and private keys. Keep backups encrypted, readable only by administrators, and in your approved backup system.

A standalone host

The database is written while the control plane runs, so stop it for a consistent copy. VMs keep running:

sudo systemctl stop glidex-ui glidex-control-plane
sudo tar -C /var/lib/glidex-control-plane -czf /root/glidex-$(date +%F).tar.gz \
  --exclude=.glidex/images --exclude=.glidex/disks .glidex
sudo tar -czf /root/glidex-etc-$(date +%F).tar.gz /etc/glidex /var/lib/glidex/netd.db
sudo systemctl start glidex-control-plane glidex-ui

Disks of running VMs change while you copy them. Copy a VM’s disk while the VM is stopped, or back up from inside the guest. gxctl disk show gives a disk’s datastore and the path of its file.

A disk on an LVM-thin datastore is the raw volume /dev/<vg>/gx-d-<disk-id> on its node. Copy it while its VM is stopped, with your usual LVM or block-device tools (activate it first with sudo lvchange -ay -K <vg>/gx-d-<disk-id> if it has no device node). Image volumes (gx-i-…) need no backup: Glidex makes them again from the image.

A disk file on a datastore is named by the disk’s id. A linked disk names its image by a relative path (../images/<image-id>.qcow2 on a shared datastore), so copy a shared datastore’s images/ along with its disks/, or restore into the same layout.

To restore, install Glidex, stop the two services, put the files back (owned by glidex:glidex, mode 0600 for files, 0700 for directories), and start them again.

A cluster

The cluster’s database is replicated on every server. Take snapshots from a server:

gxctl cluster snapshot glidex-$(date +%F).gxsnap

The file is written 0600 and holds credential and token hashes. A snapshot is what you recover from if a majority of servers is lost; see Clusters. The snapshot holds records, not disk files. Disks on local and other node-local datastores, LVM-thin included, stay on their nodes: back them up per node as above. Disks on a shared datastore are on the shared filesystem: back that up with the storage system’s own tools, or per disk while its VM is stopped.

If a node is lost for good, VMs whose disks are all on shared datastores can run on another node once it is forgotten; see A node is gone for good. VMs with disks on the lost node’s own storage need those disks restored from a backup.

Logs

Each service logs to the journal:

journalctl -u glidex-control-plane -f
journalctl -u glidex-netd
journalctl -u glidex-ui
journalctl -u glidex-authd
journalctl -u glidex-stord               # LVM-thin volumes, device access
journalctl -u glidex-vm@<vm-id>          # one VM's shim and hypervisor
journalctl -u 'glidex-vm@*' --since today

More detail: set RUST_LOG in a drop-in, for example for the control plane:

sudo systemctl edit glidex-control-plane
# [Service]
# Environment=RUST_LOG=debug
sudo systemctl restart glidex-control-plane

glidex-netd, glidex-stord and glidex-ui read RUST_LOG the same way. Remove it when you are done: debug logs are large.

Other records:

  • A VM’s serial console log: gxctl log <vm>, or the console page. It is kept in the VM’s runtime directory and rotated past 16 MiB (console.log_max_bytes); one older generation is kept.
  • The audit log: gxctl audit, or the Audit page. Kept 90 days (audit.retention_days).

Uninstall

From your checkout:

cargo run -p glidex-install -- uninstall --dry-run
cargo run -p glidex-install -- uninstall

It stops every VM (each gets its power button and grace period), the services and glidex-netd, tears down host networking (uplinks give the host’s address back to its NIC), and removes units, binaries and installer-written configuration. Your data in /var/lib/glidex-control-plane, your files in /etc/glidex, Open vSwitch and cloud-hypervisor stay unless you ask:

OptionAlso removes
--remove-ovsOpen vSwitch (packages or the source build in /opt/glidex).
--reset-dpdkDPDK settings Glidex put in OVS.
--remove-cloud-hypervisorThe cloud-hypervisor binary.
--purge-user-data/var/lib/glidex-control-plane (VMs, credentials, images, disks), ~/.glidex, and control-plane.json, netd.json and policies/ in /etc/glidex.

-y / --yes skips the confirmation. Back up first if you might want the data back.

/srv/glidex and the datastores under it always stay, with their disks, and so do LVM-thin volume groups and their volumes (remove gx-d-… and gx-i-… with lvremove); unmount and remove them yourself. /etc/glidex/stord.json stays with your other files there, unless --purge-user-data.

On a cluster node, take the node out of the cluster first (Remove an empty node or Detach), then uninstall.
