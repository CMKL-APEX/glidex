# Design decisions and trade-offs

This page explains why Glidex is built the way it is. It covers the
choices a contributor is most likely to question, says what each one
costs, and says when it should be looked at again. For what the parts
are and how they talk to each other, see [Architecture](architecture.md).
For how specific mechanisms work (the write lane, placement, the
metering ledger), see [Algorithms](algorithms.md). For how Glidex
compares with other products, see [Glidex compared](comparison.md).

book. Each spec has a decision table near the top, with a number, the

The numbers are scoped to their spec, so "D8" alone is ambiguous. The
specs write `reconciliation.md D8`, and so does this page. Where the
reason for a single rule doesn't fit a table, the spec carries a `Why:`
or `Invariant:` note next to it. Settled open questions are kept, marked
**Settled**, with the answer. Specs also record what they *rejected*, in
"Settled questions" or "Why not" sections (for example
[storage.md §12.1](https://github.com/CMKL-APEX/glidex/blob/main/spec/storage.md#121-why-not-first-s1)).

**To change a decision:**

1. Open a pull request that edits the spec first: change the decision's
   row (keep its number) or add a new row with the next free number, and
   give the reason. If a decision is replaced, say so in the row rather
   than deleting it silently.
2. List the other specs the change touches. Larger designs do this in a
   section of their own (for example clustering.md §16).
3. Land the code in the PR of the milestone that changes the behaviour,
   and update the spec's status table there.

Many past changes were reviewed this way: a "Spec: …" pull request, then
one PR per milestone. See [Contributing](contributing.md) for the rest
of the workflow.

The "Why" and "Alternatives considered" below come from the specs and
from pull request descriptions. Where the project has not written a
reason down, this page says so.

## Platform

### Rust, and one control-plane binary

**Decision.** Glidex is written in Rust. One binary,
`glidex-control-plane`, runs on every host. It always runs the **node**
role (VM, disk and image controllers, metering sampler, netd sync). On
server hosts it also runs the **server** role (API, Raft, scheduler,
cluster controllers, ledger). A standalone host runs both roles in one
process
([clustering.md D4](https://github.com/CMKL-APEX/glidex/blob/main/spec/clustering.md#3-decisions)).
Small companion binaries exist only where a separate process is needed:
the per-VM shim, the root helpers, `glidex-ui` and `gxctl`.

**Why.** The maintainers chose Rust for two reasons. **Safety:** memory
and thread safety without a garbage collector, for a long-running
service that holds root-adjacent privileges and talks to hypervisors,
OVS and the store. **AI-friendly code generation:** much of Glidex is
written with AI assistance, and Rust's strict types and compiler checks
catch generated mistakes at build time instead of in production. The
specs also show a steady preference for pure-Rust dependencies over C
ones. ReDB was
"chosen over SQLite to avoid a C dependency"
([data-model.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/data-model.md#storage)).
Protobuf code is generated by `protox` so that `cargo` alone builds the
workspace (G-D9). WebAuthn is checked in "pure Rust, no OpenSSL"
(passkeys.md §7). Cloud Hypervisor, the default hypervisor, is also
Rust.
For one binary, the reason is recorded: the node role is the host-facing
code, unchanged in substance, so a cluster adds the server role around
it rather than a second program. README goal 4 asks for minimal host
dependencies, and clustering.md D1 adds "no new service to install,
secure or upgrade".

**Alternatives considered.** Separate binaries per role (an API server
plus a node agent, as many orchestrators do). The specs don't argue
against this directly. D4's reason is that the node role is the same
code a standalone host already runs.

**Consequences.** Upgrades are one binary per host, and a standalone
host carries no cluster cost (clustering.md D5). The binary is large and
every host builds or receives all of it, including server-only code.
Mixed versions during rolling upgrades are handled by versioned API
packages (G-D7) and by write sets that replicate bytes, not logic (see
[below](#leader-computed-write-sets)).

## Hypervisors

### Cloud Hypervisor and QEMU, with one feature set, driven directly

**Decision.** Glidex supports two hypervisors, Cloud Hypervisor (the
default) and QEMU, behind one stateless driver trait
(`HypervisorDriver`,
[hypervisors.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/hypervisors.md)).
Callers see the same features on both (README goal 1). Glidex builds the
hypervisor command line itself and talks to the hypervisor's own API
socket (Cloud Hypervisor's HTTP API, QEMU's QMP). There is no libvirt.

**Why.** Goal 1 of
[spec/README.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/README.md#goals)
is "uniform microVM control across hypervisors … including VFIO PCI
passthrough and interactive console I/O". The parity work was done
explicitly: PR #2 ("Bring QEMU to parity with Cloud Hypervisor") gave
QEMU tap and vhost-user NICs, UEFI boot of cloud images, the generated
cloud-init seed and graceful stop, and added the `qemu_*` end-to-end
tests. The driver is stateless (everything it needs is a socket path),
so a restarted control plane manages a VM exactly as the one that
launched it did. "Launch = configured" (reconciliation.md D9): both
hypervisors get their whole configuration on the command line, so
there is no half-configured instance and no crash window between
"launched" and "booted".

Why not libvirt is not recorded. What the design needs from a VM
runtime is recorded, and it is specific: a supervisor per VM that owns
the console PTY and the exit record (reconciliation.md D1), restart
policy in one place (D6), and everything needed to adopt an instance
persisted in its runtime directory (D7). Glidex runs alongside libvirt
on the same host, and treats devices a libvirt-managed QEMU holds as
not ready (host-topology.md §5, PR #133).

**Alternatives considered.**

- **Firecracker** was supported early on and removed (commit "Drop
  Firecracker support"). The reason isn't recorded. Firecracker publicly
  has no PCI passthrough and no UEFI firmware boot, which goals 1 and 4
  require (VFIO, and booting stock distro cloud images through EDK2).
  Old Firecracker records are skipped at load, not treated as fatal
  ([data-model.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/data-model.md)).
- **One hypervisor only (Cloud Hypervisor).** QEMU is kept because it
  can also *emulate*: run a VM of another architecture on a host, or run
  VMs on a host without KVM, in software (TCG). Cloud Hypervisor needs
  KVM and the host's own architecture. This is the maintainers' reason
  for keeping QEMU; emulation isn't wired up yet. Today the QEMU driver
  runs `qemu-system-x86_64` with `-enable-kvm`, and the scheduler places
  a VM only on nodes of its architecture.

**Consequences.** Every feature is built and tested twice. The specs
are full of per-backend details: Cloud Hypervisor needs `CAP_NET_ADMIN`
for taps (networking.md decision 9), QEMU needs a per-VM UEFI variable
store, vCPU pinning differs (host-topology.md H9), and Cloud Hypervisor
reports no usable disk latency (metering.md D17). Features that only one
backend can offer have to wait or be refused. Revisit if one backend
falls behind on a feature users need, or if maintaining parity starts
to block features.

## VM lifecycle

### A shim per VM, in its own systemd unit

**Decision.** Each running VM is supervised by its own
`glidex-vm-shim`. The shim is the hypervisor's parent, owns the PTY
master, the console socket and log, and records the exit
(reconciliation.md D1). Under systemd the shim runs as
`glidex-vm@<vm-id>.service`, started by the control plane over systemd's
D-Bus API (`zbus`) and allowed by a polkit rule (D2). systemd never
restarts a VM (`Restart=no`); restart policy belongs to the VM
controller (D6).

**Why.**

- Whatever holds the PTY master and reaps the hypervisor must not be the
  control plane, or the guest dies, or loses console output, with it
  (D1). This makes "VMs survive control-plane restarts" (README goal 2)
  true: stopping, crashing or upgrading the control plane leaves guests
  running, and it adopts them on startup.
- Only a separate unit escapes the control plane's cgroup. A unit per VM
  gives per-VM accounting, journal and shutdown ordering (D2). Metering
  reads CPU and memory from that cgroup (metering.md D3).
- Two supervisors with restart policies fight, and only the controller
  knows why a VM exited (D6).
- D-Bus rather than `systemctl`, for typed errors and unit signals.
  Polkit rather than netd, so netd stays networking-only (D2).

**Alternatives considered.**

- **Hypervisors as children of the control plane**, which is what Glidex
  did before PR #4. A control-plane restart killed or deafened every VM.
- **`KillMode=process` on the control plane's unit**: it leaves VMs in a
  cgroup systemd believes is stopped, without accounting (D2).
- The same split exists elsewhere: containerd-shim and conmon (D1).

**Consequences.** The control plane never holds a process handle. It
reaches a VM only through files and sockets in the VM's runtime
directory, and everything needed to talk to an instance is persisted
(D7). Adoption after a restart is therefore the normal code path, not a
recovery path. Before any launch the controller must positively
establish that no instance is live, and reports `Unknown` when it can't
(D8). The price is one more process and one systemd unit per VM, a
polkit rule the installer must install, and a second runner (a
double-forked shim in its own session) for development and tests.

### Desired state and level-triggered controllers

**Decision.** Every persisted resource is `{meta, spec, status}`. The
API writes `spec`; only controllers write `status` (D3). Controllers are
level-triggered, fed by a deduplicating work queue and a periodic resync
(D4). Admission (validation, authorization, quotas, exclusive claims)
stays synchronous; host actions are asynchronous and report in `status`
(D5).

**Why.** "The user wants it running" survives "it isn't running right
now" (D3). Missed events are harmless, and the global lock that used to
be held across hypervisor I/O is gone (D4). Invariants that protect data
(exclusive disk use, quotas) must hold at commit time, not eventually
(D5).

**Alternatives considered.** The earlier synchronous design, where a
request did the host action under a global write lock (PR #4 describes
the change).

**Consequences.** API writes answer `202` unless the caller passes
`?wait`. `?wait` returns the same errors the synchronous calls used to
return, so clients kept their behaviour (D20). Clients have to wait on
`Ready`, which means "converged to the spec", including for a VM that
should be stopped (D13).

## Privilege separation

### An unprivileged control plane with small root helpers

**Decision.** The control plane runs as the unprivileged user `glidex`,
under a tight systemd sandbox, and runs no hypervisor itself. Work that
needs root goes to small helpers, each over a Unix socket with
peer-credential checks and a per-operation allow-list:

| Helper | Does | Spec |
|---|---|---|
| `glidex-netd` | OVS, bridges, uplinks, NAT, DHCP, VM ports, `vfio-pci` binding | networking.md decision 1, security.md §8 |
| `glidex-authd` | PAM password checks | security.md decision 6, §5.3 |
| `glidex-stord` | LVM volumes and device access for VM units | storage.md S12, S17, S18 |
| polkit rule | lets `glidex` start and stop `glidex-vm@` units | reconciliation.md D2 |

The web UI's server, `glidex-ui`, runs as its own user with no authority
of its own: it serves files and proxies `/api` (security.md decision 4).

**Why.**

- netd is root "from the first milestone" (networking.md decision 1).
  The control plane is the policy point for users; netd only decides
  which local processes may ask it for what (security.md decision 2,
  §8), so netd doesn't need Cedar.
- PAM: a non-root process can't check other users' passwords with
  `pam_unix`. authd is separate from netd "so netd stays network-only"
  (security.md decision 6).
- stord: creating and activating logical volumes needs root, and "the
  control plane must stay unprivileged". Its allow-list of volume groups
  and its volume-name rule mean the control plane can make and remove
  Glidex's own volumes and nothing else (storage.md S17).
- Local callers are identified by `SO_PEERCRED`, never by claims in the
  request (security.md decision 5).

**Alternatives considered.** Running the control plane as root (the
simplest option, and common for VM managers); one root helper for
everything. The specs reject the second explicitly, each time keeping a
helper to one job.

**Consequences.** Each helper is a protocol to version and a unit to
install. Some things the control plane can't do for itself: it can't
widen its own sandbox, which is why datastores must be mounted under
one root, `/srv/glidex` (storage.md S11), and why per-VM CPU binding is
done by the shim rather than by systemd drop-ins (host-topology.md H9).
Cloud Hypervisor still needs `cap_net_admin` on its binary to bring taps
up (networking.md decision 9). See [Access control](../operator-guide/access-control.md)
and [Installation](../operator-guide/installation.md) for what the
installer sets up.

## State and clustering

### ReDB as the store

**Decision.** All control-plane state is in one ReDB file. Values are
serde JSON.

**Why.** ReDB is an embedded, copy-on-write, ACID key-value store,
"chosen over SQLite to avoid a C dependency and over sled for its
simpler transactional model"
([data-model.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/data-model.md#storage)).
See the [redb project](https://github.com/cberner/redb).

**Alternatives considered.** SQLite and sled, as above. An external
database is discussed in the next section.

**Consequences.** No SQL: queries are code over tables, and migrations
are code with a schema version. Every write goes through one store API
(`Db`/`Tx`), which records the write set; a lint in CI
(`scripts/lint-store-writes.sh`) keeps it that way.

### Embedded Raft (openraft), not etcd or an external database

**Decision.** In a cluster, the ReDB database is replicated by Raft
embedded in the control plane, using the
[`openraft`](https://github.com/databendlabs/openraft) crate, pinned to
an exact version. The state machine is the existing ReDB database
(clustering.md D1). The store and its Raft integration are the
`glidex-raftstore` crate.

**Why.** "No new service to install, secure or upgrade." Every table,
migration and test keeps working on ReDB (D1). Losing a minority of
servers doesn't stop management, and VMs keep running through any
control-plane outage anyway (clustering.md §2).

**Alternatives considered** (from D1):

| Option | Why not |
|---|---|
| etcd | A separate daemon, value-size and per-transaction operation limits, and a rewrite of every table access |
| dqlite (Incus's choice) | C, and a move to SQL |
| An external database such as PostgreSQL | Not discussed directly; it falls under the "no new external database" goal (clustering.md §2) |

**Consequences.** Glidex owns its consensus code paths: snapshots,
membership changes, and a voter that lost its state must never rejoin as
the same voter (D18). The replicated store holds metering history,
about 12 MB per VM, on every server; that sets the ceiling of roughly
5,000 VMs (§4.1). Past it, the plan is to move metering history out of
the replicated store first. `openraft` is pre-1.0 and is upgraded
deliberately.

### Leader-computed write sets

**Decision.** A write runs once, on the leader, against its applied
state. The result, an ordered list of `put`/`delete` operations on table
keys, is the Raft log entry. Applying an entry is a pure byte operation
(D2). Writes go through one lane on the leader: a write's closure runs
only after the previous write is applied locally (D3).

**Why.** Admission, quotas and claims need serialized read-then-write
logic. Replicating *commands* would need identical logic, clocks and
UUID generation on every replica and every version, which breaks under
rolling upgrades. Byte write sets are deterministic by construction and
version-independent (D2). With one lane, the closure reads exactly the
state its write set will apply to, so no conflict detection is needed;
control-plane write rates of tens per second fit in a LAN round trip
(D3).

**Alternatives considered.** Command replication (above). Optimistic
concurrency with conflict detection, which the single lane makes
unnecessary.

**Consequences.** Throughput is bounded by one lane: about 150–300
writes per second (§4.1). Status is written only when it changes, or a
resync round alone would flood the log. Pipelining the lane is listed
as later work (§18). See [Algorithms](algorithms.md) for how the lane
works.

### Standalone stays non-Raft

**Decision.** A single host keeps writing ReDB directly. The store has
two modes behind one API, local and replicated, and both take the same
write sets. `gxctl cluster init` switches a host to replicated with one
voter (D5).

**Why.** Existing single-host users carry no Raft cost and no risk until
they opt in, and the code paths stay common (D5).

**Consequences.** Both modes must stay tested. Joining a cluster is an
explicit, backed-up step (clustering.md §5.1), not a default.

### Servers and agents

**Decision.** A cluster has 1, 3 or 5 **server** hosts (Raft voters,
API, cluster controllers) and any number of **agent** hosts (node role
only) (clustering.md §2). Agents serve no API: an agent's web UI
redirects browsers to a server (host-page.md W5). Node liveness is held
in the leader's memory; only transitions go through Raft (D7). There is
no automatic failover of VMs (D8), and placement is sticky (D6).

**Why.**

- Raft needs an odd, small voter set; the rest of the hosts only run
  VMs.
- Root on a server already holds the whole database; root on an agent
  holds only its own VMs and must not escalate to the cluster, so
  break-glass access is honoured on servers only (D14).
- A heartbeat per node every 5 s through Raft would be pure log churn
  (D7).
- A partitioned node may still be running its VMs. Starting copies
  elsewhere would put two writers on one disk (D8), and "at most one
  instance per VM, ever" (reconciliation.md D8) comes first.
- One origin for the browser: SSO, passkeys and cookies work
  (host-page.md W5).

**Alternatives considered.** Automatic restart of a lost host's VMs
elsewhere, rejected without fencing (clustering.md §2, D8).

**Consequences.** When a host dies, its VMs are `Unknown` until an
operator acts. A VM whose disks are all on shared datastores can then be
placed again after `node forget --fenced` (storage.md S10). Fencing and
automatic evacuation are later work (§18). See
[Clusters](../operator-guide/clusters.md).

## API

### One service layer under REST and RPC

**Decision.** Every operation is a transport-neutral service function.
REST and RPC adapters only decode, call it and encode (grpc.md G-D1).
RPCs are served on the same listeners and port as REST (G-D2). REST/JSON
stays permanently, for curl, scripts and HTTP-only protocols (OIDC
callbacks, SCIM, the console WebSocket) (grpc.md §1).

**Why.** Authorization, quota and audit are written once. "Two copies of
a Cedar check is exactly the kind of drift that becomes a cross-tenant
bug" (G-D1). One port means no new firewall rule or certificate name, and
the existing TLS, pinning and peer-uid identification are reused (G-D2).
The RPC side gives typed contracts, generated clients, a compatibility
check in CI, and server streaming for watch (grpc.md §1).

**Alternatives considered.** Hand-written REST types mirrored by hand in
`gxctl`, which is what Glidex had before (grpc.md §1). gRPC as a
replacement for REST, rejected: REST stays.

**Consequences.** Every operation declares whether it reads or writes,
because every RPC is a `POST` and cluster forwarding must still tell
reads from writes (G-D6). See [API overview](../api/README.md).

### Proto as the source of truth

**Decision.** Every API type is defined in protobuf, in the `glidex-api`
crate. REST JSON is the proto3 JSON form of the same messages (G-D3),
with field names in `snake_case` (G-D11). Packages are versioned,
`glidex.<area>.v1` (G-D7). `buf` lints, checks breaking changes and
generates TypeScript; Rust code is generated in `build.rs` from a
descriptor set made by `protox` (G-D9).

**Why.** Two type systems for one API drift apart; one definition serves
REST, gRPC, `gxctl` and the UI (G-D3). proto3 JSON defaults to
`lowerCamelCase`, and the REST API is `snake_case`; declaring the name in
the proto keeps every generator on the same names (G-D11). Contributors
and packaging build with `cargo` alone, with no `protoc` or `buf` (G-D9).
Rolling upgrades run mixed versions, so field numbers and names are the
compatibility contract (G-D7).

**Alternatives considered.** Rewriting descriptors at build time to fix
JSON names (rejected in G-D11). A transition release carrying both REST
shapes, waived because no release had shipped the proto shapes yet
(G-D12).

**Consequences.** Porting a family of endpoints changed its REST shape
once (G5). `build.rs` refuses an RPC without its operation option, a JSON
name that isn't the field name, or a secret field that can reach a
response.

### connectrpc rather than tonic

**Decision.** The RPC runtime is
[`connectrpc`](https://github.com/connectrpc) for Rust, with `buffa`
messages, pinned to an exact pre-1.0 version (G-D10). One tower service
answers Connect, gRPC and gRPC-Web.

**Why.** It replaces `tonic`, `tonic-web`, `tonic-health`, `prost` and
`pbjson` with one stack from the Connect project, the same protocol
family as the browser client. Its messages carry their own proto3 JSON,
which REST needs. It passes the ConnectRPC conformance suite (G-D10).

**Alternatives considered.** `tonic` with its companions, above.

**Consequences.** A pre-1.0 API that may still move; it is upgraded
deliberately, like `openraft` (G-D10).

### Connect-ES and gRPC-Web in the browser

**Decision.** The web UI uses
[Connect-ES](https://connectrpc.com/docs/web/getting-started)
(`@connectrpc/connect-web`) with a gRPC-Web transport and TypeScript
generated by `protoc-gen-es` (G-D8). Session cookies are accepted only
for gRPC-Web from `glidex-ui` on its socket (G-D4).

**Why.** gRPC-Web works over HTTP/1.1 without HTTP/2 trailers, so
`glidex-ui` keeps proxying `/api` unchanged. The UI gets typed clients
from the same protos as `gxctl`, and server streaming for watch (G-D8).
Keeping cookies on the one browser path keeps CSRF and Origin rules where
browsers are (G-D4).

**Consequences.** A few calls stay REST in the UI: login and logout,
`whoami` (which provides the CSRF value), OIDC redirects, CSV exports
and the console WebSocket (PR #41).

## Authorization

### Cedar

**Decision.** Authorization is [Cedar](https://www.cedarpolicy.com)
policy, evaluated in process with the `cedar-policy` crate (security.md
decision 9, §7). Roles are template-linked policies; invariants are
`forbid` policies; every policy is validated against a schema. Every
route maps to one Cedar action, and a route without one fails a test
(decision 7). Operators add site policies through the API (decision 10).

**Why** (security.md §7):

- roles, project scoping, grants and host-wide rules are policies
  instead of `if` chains spread over handlers;
- strict validation against a schema: a typo in a policy fails startup
  instead of quietly allowing or denying;
- `forbid` always overrides `permit`, so invariants such as step-up and
  same-project-only can't be overridden by any role or site policy;
- sites add rules without code changes;
- every decision names the policies that produced it, which goes into
  the audit log.

What stays in code: authentication, quotas (they need counts), path
canonicalization and netd's peer check.

**Alternatives considered.** Not compared in the spec. The two usual
alternatives are role tables in the database (RBAC), which can't express
the `forbid` invariants or site rules without code, and an external
policy service such as [OPA](https://www.openpolicyagent.org/), which
would be another service to run; security.md says "there is no separate
policy service".

**Consequences.** Contributors change the schema and policies
(`crates/glidex-control-plane/policies/`) along with handlers. Tenants
can't author Cedar; site policies belong to operators and directory
owners (tenancy.md D28), because tenant-authored policies would need
per-tenant validation scopes and lock-out rules. See
[Access control](../operator-guide/access-control.md).

## Tenancy and directories

**Decision.** A **tenant** is an organization's account. Every project,
VM, disk, network and credential belongs to exactly one tenant
(tenancy.md D1). Each tenant is in exactly one **directory**, which holds
its users, teams and connectors to the organization's own identity
provider (D2). Operator tenants operate clusters; only their members pass
host-scoped actions, enforced by a `forbid` (D4). A cluster trusts a
directory only after a pairwise handshake (D8), keeps a read-only replica
of what the directory sends it (D12), and accepts only tokens addressed
to it (D11, §7.3).

**Why** (tenancy.md):

- Organizations keep their own identity and records; nothing about one
  is stored in another's directory (D2).
- Single sign-on is something organizations choose by sharing a
  directory, not something Glidex arranges across them (D3).
- Independent organizations each decide whom they trust; adding a
  cluster or a directory touches only the pairs involved (D8).
- Organizations and datacenters fail and partition independently; a
  cluster, compromised or not, can't write a directory on anyone's
  behalf (D12).
- A cluster can't replay a credential it received to another cluster or
  directory (§7.3).

**Alternatives considered.**

- A global registry or shared store across clusters: rejected in favour
  of pairwise trust and feeds ("no Raft across clusters or directories",
  D12). Fleets broker trust at scale without becoming a shared store
  (D33).
- SAML connectors: rejected. Every listed IdP offers OIDC, and XML
  signature verification is a long-running source of bypasses (D30).
- A built-in identity provider is a non-goal at the host level (spec
  README); a directory is an OIDC provider for its own users, which log
  in through their organization's IdP.

**Consequences.** A cluster cut off from a directory keeps running
workloads and serving credentials it can verify, and stops accepting that
directory's credentials after `max_staleness` (D13): an operator-chosen
balance between availability and revocation. The model is large (over
seventy decisions); the implemented parts are tracked in tenancy.md §23.

### Workload federation

**Decision.** A tenant can trust an external JWT issuer (GitHub Actions,
GitLab CI, any OIDC workload issuer) and map matching tokens to a
service account; `POST /auth/exchange` returns a short-lived token acting
as that service account (D26, D48–D51). Rules match exact claim values
only and must name a repository, project path or subject (D50).

**Why.** CI uses the identity it already has (D26). Rights stay in one
place, the service account's role links, and a leaked exchanged token is
short-lived and tied to one job (D48).

**Alternatives considered.** Long-lived API tokens stored as CI secrets,
which is what federation replaces.

**Consequences.** Exchanged tokens last at most an hour and can't be
renewed. Identity for Glidex's own VMs (a metadata endpoint and SPIFFE
IDs) is a separate draft,
[workload-identity.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/workload-identity.md),
not implemented. See [Workload federation](../operator-guide/workload-federation.md).

## Networking

### Open vSwitch, driven through netd

**Decision.** VM networking is Open vSwitch. The control plane asks
`glidex-netd` (root) for bridges, uplinks, NAT and VM ports. Glidex can
install OVS from distro packages by profile (networking.md decision 6),
or from a pinned source build when the distro lacks features (decision
10). Addressing is DHCP plus NAT through the host's existing route
(decision 4).

**Why.** OVS covers every port type Glidex uses under one model: tap and
vhost-user VM ports, and kernel, AF_XDP and DPDK uplinks (networking.md
§2; clustering.md D15). It is also the base OVN needs for clusters. Its
bridge-port counters are the one metering source that covers every port
type, since vhost-user ports have no kernel network device
(metering.md D5).

**Alternatives considered.** Linux bridges on a single host. They are
simpler and in every kernel, but the maintainers chose OVS everywhere
for **one configuration model for a single host and a cluster**: the
same bridges, ports and counters on a standalone host as on a cluster
node, so a host joins a cluster (and OVN) without its networking being
redone. Linux bridges also have no userspace datapath for vhost-user or
DPDK and no path to OVN.

**Consequences.** OVS is a large host dependency, and an OVS upgrade
restarts `ovs-vswitchd` and interrupts VM traffic, so the installer
leaves OVS upgrades to the distro (installer.md). Static guest addressing
and persistent host network changes are non-goals. See
[Host networking](../operator-guide/host-networking.md).

### OVN for cluster networks

**Decision.** Networks that span hosts use [OVN](https://www.ovn.org/) on
the OVS each host already runs. The leader's network controller writes
the OVN northbound database; netd only joins the host to OVN and plugs VM
ports (clustering.md D9). Node-scoped OVS networks remain (D10). IPAM
belongs to the control plane, not to OVN (D12). NAT egress is
centralized on high-availability gateway chassis (D11).

**Why.** OVN provides the overlay, logical switches and routers, DHCP,
SNAT gateway HA, port security and, later, multi-chassis port binding
for live migration. The northbound database is reached over TLS, so the
unprivileged control plane can write it while netd keeps everything
privileged (D9). Centralized SNAT needs one external IP per router
instead of one per VM, and is OVN's standard HA gateway pattern (D11).
One IPAM source of truth survives restarts and serves port security
(D12).

**Alternatives considered.**

- An eBPF datapath: rejected (D15). It would cover tap only, so Glidex
  would maintain two datapaths, with no migration or performance gain for
  tap VMs.
- Distributed SNAT: needs an external IP per VM (D11).
- OVN's dynamic addressing: not used (D12).
- Converting node networks to cluster networks: out of scope, because it
  means renumbering running VMs (D10).

**Consequences.** Two Raft groups run on the servers, Glidex's and
OVSDB's, kept separate on purpose (clustering.md §4). External traffic
on OVN is metered from conntrack accounting in each router's SNAT zone,
because OVN exposes no counters on logical objects (D22). Routed
networks, floating IPs and security groups are later work (§18).

## Storage

### Datastores behind a CSI-shaped driver trait

**Decision.** A **datastore** is a cluster-scoped record naming where
disks and images live (storage.md S2). A driver creates, sizes, deletes
and opens volumes in it, and a topology says which nodes reach it (S4).
The drivers are `dir` (node-local; the built-in `local` datastore),
`shared-dir` (a filesystem the operator mounts on every node: NFS,
CephFS, GPFS…) and `lvm` (node-local LVM-thin). Glidex's driver trait,
`StorageDriver`, follows CSI's split between controller and node
operations and its topology and capability model, but Glidex does not
host CSI plugins yet (S1).

**Why.**

- Nearly every vendor and open-source system offers an NFS or POSIX
  mount. A mount keeps qcow2 and its features (linked clones, sparse
  files, resize and shrink) and needs no root, because the mount is done
  outside Glidex (S1).
- The existing directories become `local` with no file moves; nobody
  sees a change until an operator adds a datastore (S3).
- New disks stay on `local` by default: it is the fastest store, and
  choosing shared storage is the operator's call (S13).
- LVM-thin gives the same thin, overcommitted, fast-clone behaviour as
  qcow2 files, on the devices a site gives VMs (S19).

**Alternatives considered.**

- **[CSI](https://github.com/container-storage-interface/spec) as the
  first interface**, rejected for now (S1, §12.1). Many plugins assume
  Kubernetes sidecars and objects (Secrets, CRDs, node labels); node
  plugins run as root, usually in privileged containers; VMs need CSI's
  `Block` mode, which gives up qcow2; each plugin is another per-node
  service with its own release cycle; and nobody has asked for a
  particular plugin. The trait keeps the door open: a CSI adapter is
  milestone S7, gated on a real need (§12.3).
- **Ceph built in.** Not discussed as such. Ceph is reachable as CephFS
  through `shared-dir`, and an `rbd` driver is planned after `lvm`
  (S19). Running a storage cluster is outside what Glidex installs:
  "glidex never mounts" shared filesystems (S1), and README goal 4 asks
  for minimal host dependencies.

**Consequences.** Moving a VM is explicit and offline, and needs every
disk on a shared datastore (S10). Exactly one node acts on a volume's
files at a time, its **worker** (S6), and Glidex takes its own lock file
on shared volumes, because placement alone can't stop a partitioned node
that kept running (S16). Mount points must live under `/srv/glidex`
(S11). Block volumes are raw, grow and never shrink (S19). Live
migration, snapshots and per-datastore quotas are out of scope for now.
See [Datastores](../operator-guide/datastores.md).

## Images

### A catalog of checksum-verified cloud images, and linked disks

**Decision.** `POST /images {"catalog": …}` downloads a distro cloud
image and verifies it against the checksum file the vendor publishes
next to it, fetched over HTTPS (images.md §4). Firmware is different: its
digest is pinned. A VM's root disk is usually **linked**, a qcow2 overlay
whose backing file is the image. Files are named only by id.

**Why.**

- Cloud images are rebuilt weekly with security fixes, so pinning their
  digests would ship stale, vulnerable guests; a "current" image plus the
  vendor's published checksum avoids that (images.md §4). One tested
  firmware build is what guests should boot, so firmware is pinned
  (§4.1).
- Debian's OVMF build is used because upstream EDK2 publishes no
  prebuilt OVMF and nightly builds can't be pinned (§4.1).
- Files named by id: renaming a record never touches the file, and a
  name can't escape the directory (§2).
- Orphan files and missing files are reported, never deleted: Glidex
  never destroys data because it guessed wrong (§2).
- Everything runs as the control-plane user; no step needs root (goal
  4).
- On datastores, an overlay names its backing file by a relative path,
  because nodes may mount a datastore at different paths (storage.md
  S8).

**Alternatives considered.** Pinned digests for cloud images (above).
Full copies instead of overlays remain available (`clone: full`).

**Consequences.** An image can't be deleted while a linked disk uses it
(images.md §3). A linked disk needs its image copy in the same
datastore (S8). Disk snapshots, image building and non-cloud images
(installer ISOs) are non-goals. See
[Images and disks](../user-guide/images-and-disks.md).

### Kernel extraction inside a VM

**Decision.** To boot a cloud image's own kernel directly, Glidex reads
the image's filesystems **inside a short-lived VM**, never on the host.
It boots a pinned extractor kernel and initramfs with the image attached
read-only and no network; the extractor writes the boot files to a raw
disk in a simple stream format that the host parses with strict limits
(kernel-boot.md K9).

**Why.** No new host packages, no root, no loop devices, and the host
never parses an untrusted filesystem (K9). A disk image, especially from
a URL or a VM's own disk, may hold a filesystem crafted to attack its
parser; inside the extractor, the worst outcome is a failed extraction
(§8). Extracting from the image also guarantees that the kernel matches
the image's modules (K3).

**Alternatives considered** (kernel-boot.md §9):

| Option | Why not |
|---|---|
| Host tools per filesystem (`debugfs`, `btrfs restore`) | Parse untrusted filesystems on the host; nothing for XFS |
| [libguestfs](https://libguestfs.org/) | Also uses a VM, but adds a large host dependency whose appliance needs a readable host kernel |
| Downloading distro kernel packages | No initrd |

**Consequences.** Extraction costs a VM boot per image, on a node of the
image's architecture. Firmware boot stays the default; kernel boot as
the default is to be revisited "once boot-time numbers exist" (K2). See
[Kernel boot](../user-guide/kernel-boot.md).

### A generated cloud-init seed

**Decision.** Before each launch, the VM controller builds a NoCloud
seed, a FAT volume labelled `CIDATA`, with `mkdosfs` and `mcopy`
(`cloud_init.rs`). A VM gets a login only if it names a stored
credential; there are no host-wide default keys or passwords
([credentials.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/credentials.md)).

**Why.** Distro cloud images ship with no usable login and wait for
cloud-init. `mkdosfs`/`mcopy` build the volume without root or loop
mounts, the same approach as Cloud Hypervisor's own script. One host-wide
key or password would open VMs in every project (security.md §6.2).

**Consequences.** The seed holds a password hash and is created `0600`.
cloud-init provisions users once per instance id, so changing a
credential later doesn't change an already-provisioned guest. See
[Guest credentials](../user-guide/credentials.md).

## Devices and topology

### PCI passthrough, device pools and NUMA

**Decision.**

- A device is identified per node, `(node, address)`; VFIO claims are
  per node and by IOMMU group (host-topology.md H3).
- Each node reads its topology from sysfs, with no new dependency (H1). A
  small summary goes in replicated node status for the scheduler; the
  full PCIe tree stays on the node (H2).
- Users request devices by class from **pools** the operator defines,
  not by raw PCI class codes; pools are what tenants are granted
  (H10, H11, H17).
- VMs choose a NUMA policy (`none`, `preferred`, `strict`, and
  `aligned` for multi-GPU VMs) and a CPU policy (`shared` or
  `dedicated`) (H5, H6, gpu-vms.md G2).
- The scheduler, not the node, picks exact CPUs (H8). Hugepages are a
  resource of their own, never overcommitted (H19).
- Glidex can bind a device to `vfio-pci` through netd, but never changes
  the kernel command line or firmware (H12).

**Why.** The scheduler needs topology on the leader, but the full tree
is only for display, so Raft state stays small (H2). Address-wide claims
broke once there were several nodes (H3). Pools let operators name
devices by vendor, model or label and grant them, instead of every user
knowing addresses (H10). One writer for CPU sets means two VMs can't take
the same CPU (H8). `aligned` is the only layout that keeps every GPU
local once a VM outgrows one NUMA node, and a guest topology that mirrors
the host makes `nvidia-smi topo` and NCCL see the real layout (G2, G3).

**Alternatives considered.** `hwloc` or `lspci` for discovery (rejected
for a dependency-free sysfs reader, H1). systemd drop-ins for CPU
binding (dropped: the unprivileged control plane can't write them, H9).
Guessing a device's NUMA node from its bus number (rejected, H4).
Running NVIDIA Fabric Manager on the host for NVLink (an option, not the
default; a service VM keeps the driver off the host kernel, G6).

**Consequences.** Kernel parameters (IOMMU, hugepages) remain the
operator's job. Device health is reported, not used to refuse devices
(H18). See [PCI passthrough](../operator-guide/pci-passthrough.md) and
[Host resources](../operator-guide/host-resources.md).

## Console

**Decision.** Each VM has one console (a serial port or virtio console on
a PTY). The **shim** owns the PTY master, writes `console.log`, and
serves any number of clients on a console socket. A new client first
gets the current log replayed, then live output
([console.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/console.md)).
Logs are appended across restarts and rotated once at 16 MiB
(reconciliation.md D14).

**Why.**

- Output the hypervisor wrote stays readable on the master after the
  hypervisor exits. When Cloud Hypervisor owned the master, its hangup
  on exit threw away unread output, so a guest's last line ("reboot:
  Power down") was routinely lost. Owning the master also captures
  firmware output from before boot completes (console.md, "Why the shim
  owns the master").
- The shim, not the control plane, because whoever holds the master
  decides when the guest's terminal hangs up; while the control plane
  held it, a restart killed or deafened every VM.
- Replay gives late-joining browsers the boot output (README goal 3).
- Appending keeps the output from before a crash after the crash-restart
  (D14).

**Alternatives considered.** The hypervisor's own PTY mode (above).
A console held by the control plane (the design before PR #4).

**Consequences.** The browser reaches the console through a WebSocket
with a single-use ticket, `gxctl` through a bidirectional RPC. The
browser terminal is [ghostty-web](https://github.com/coder/ghostty-web)
by default, with xterm.js as a choice, because ghostty-web renders to a
canvas that screen readers can't read (PR #50). See
[Console](../user-guide/console.md).

## Metering

**Decision.** The meter runs inside the control plane (metering.md D1).
It samples cumulative counters and stores deltas (D2), into an hourly,
UTC ledger that is immutable once closed, with a per-source cursor
written in the same transaction as the deltas it produced (D8). Sources:
the VM unit's cgroup for CPU and memory (D3), the hypervisor for disk
operations (D4), OVS port counters for traffic (D5). Bandwidth and disk
I/O also get a 5-minute 95th percentile per billing month (D15, D16).

**Why.**

- The control plane already knows every VM, disk and NIC and holds the
  database; a separate daemon would duplicate adoption logic. Counters
  are cumulative, so downtime loses no data (D1, D2).
- Without the cursor in the same transaction, a crash between "record
  delta" and "advance cursor" would count a delta twice or never (D8).
- The shim writes a final counter snapshot when the hypervisor exits,
  because the cgroup and counters vanish with the unit (D12).
- 5-minute p95 on the larger direction is the industry convention for
  burstable billing, so customers can check figures with their own
  tools. Group figures are the p95 of the summed series, because summing
  p95s over-bills (D15). Disk I/O uses read+write combined, because
  reads and writes share one queue (D16).
- No disk latency for Cloud Hypervisor VMs, because its latency fields
  can't give a correct average for any period, and a wrong figure is
  worse than none (D17).

**Alternatives considered.** A separate metering daemon (D1). Rates
computed upstream (D2). OVS flow statistics or eBPF for external traffic
(rejected for conntrack accounting, clustering.md D15, D22).

**Consequences.** Metering history lives in the replicated store and is
its largest table, about 12 MB per VM (clustering.md §4.1); moving it
out is the first step past the scale ceiling. Usage outlives the VM and
keeps the project and name from when it was sampled (D13). See
[Usage](../user-guide/usage.md) and [Algorithms](algorithms.md).

## TLS and sign-in

### Self-signed by default, pinned by fingerprint

**Decision.** The control plane (port 8841) and the web UI (port 5173)
serve HTTPS on every address by default, with a self-signed ECDSA P-256
certificate unless one is configured (PR #7). `gxctl` trusts a
self-signed control plane by pinning the leaf certificate's SHA-256,
trusted on first use at `gxctl auth login` (security.md decision 18,
gxctl-auth.md A4). A verify-nothing mode exists only as an explicitly
confirmed, per-profile, loudly marked escape hatch (A5).

**Why.** A fresh host has no name a public CA would sign, but its API
still must not be plain HTTP on the network. Pinning keeps signature,
date and name checks running against the pinned certificate, instead of
skipping verification (A4). A profile records the cluster id, and a
server reporting another id is a hard error (A6). The certificate is
reused until near expiry so the fingerprint stays stable (PR #7).

**Alternatives considered.** Plain HTTP on loopback, the earlier default
(replaced in PR #7). A "skip verification" flag as the normal way to
reach a self-signed server (rejected, A4, A5). Running a private CA for
every standalone host (not discussed; clusters do have their own CA,
clustering.md D20).

**Consequences.** Browsers show a warning for the self-signed
certificate, and HSTS is sent only with a configured certificate,
because it would make that warning impossible to bypass (PR #7). See
[TLS](../operator-guide/tls.md).

### Tailscale certificates for the web UI

**Decision.** On a host on a tailnet, `glidex-ui` may serve the node's
Tailscale (Let's Encrypt) certificate for its `ts.net` names, fetched
from the host's `tailscaled` and chosen by SNI; every other name keeps
the usual certificate (tailscale-tls.md T1–T3). It is opt-in (T4). The
control plane keeps its own certificate (T8).

**Why.** Browser-trusted HTTPS with no certificate management. Opt-in
because the node's name is published in Certificate Transparency logs
(T4). A Tailscale failure never fails a handshake; `ts.net` names fall
back to the default certificate (T5).

**Alternatives considered.** Embedding Tailscale's Rust library,
tailscale-rs: it doesn't issue certificates yet and is a later phase
(T1).

**Consequences.** The installer must grant `glidex-ui` access through
`tailscaled`'s `TS_PERMIT_CERT_UID`, and refuses when another user
already holds it (T6).

### Passkeys

**Decision.** Users of a local directory can sign in with
[WebAuthn](https://www.w3.org/TR/webauthn-3/) passkeys. Credentials are
discoverable, user verification is required, and a passkey sign-in counts
as multi-factor (passkeys.md P3). No attestation is trusted (P1). Only the
user adds its own passkeys, and a user can't be left with a single
passkey as its only sign-in (P4). The checks are implemented in Glidex
(`auth/webauthn.rs`, pure Rust).

**Why.** No account names to type or enumerate; with verification, a
passkey is possession plus a factor (P3). Trusting attestation would
need an allow-list of authenticator makers that nobody asked for (P1).
Losing one device must not lock a person out, and nobody can plant a
passkey on another person's account (P4). Passkeys belong to a
configurable relying-party id so that passkeys made on one name of the
UI work on its others and on other servers (P2).

**Alternatives considered.** Trusting attestation (P1).

**Consequences.** The ceremonies are HTTP-only, like OIDC callbacks,
because WebAuthn is a browser protocol (P6). `gxctl` keeps its own
logins. See [Authentication](../operator-guide/authentication.md#passkeys).

## Web UI

**Decision.** The UI is a Vite + React + TypeScript single-page app,
managed with [Bun](https://bun.sh/) (`bun.lock`). A small Rust binary,
`glidex-ui`, serves the built files over HTTPS and proxies `/api` to the
control plane; `glidex-ui --dev` runs the Vite dev server instead
([web-ui.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/web-ui.md)).

**Why.** `glidex-ui` is a proxy with no authority of its own; the
control plane authenticates and authorizes every request (security.md
decision 4). Running it as its own user means a UI compromise can't
reach what the control plane can (security.md §4). Proxying keeps the
browser on one origin, which cookies, CSRF checks, SSO and passkeys rely
on. React, Vite and Bun were chosen for speed and ecosystem: **Vite and
Bun** for fast builds, dev-server reloads and dependency installs;
**React** for its ecosystem of components and libraries, and its
TypeScript support, which the generated Connect-ES types build on.

**Alternatives considered.** Serving the UI from the control plane
itself; not discussed in the specs.

**Consequences.** Building the UI needs Bun and the JavaScript
dependencies; the installer installs a pinned Bun and verifies it.
Generated Connect-ES code is committed, and CI fails if it is stale.

## Installer

**Decision.** Glidex is installed from a source checkout with
`cargo run -p glidex-install`. The installer is one linear,
non-interactive and convergent program: each run detects what is missing
or outdated and fixes just that, so the same command installs Glidex and
later keeps it up to date
([installer.md](https://github.com/CMKL-APEX/glidex/blob/main/spec/installer.md)).
It installs system dependencies through the host's package manager
(apt, dnf/yum or pacman). `--prebuilt` uses binaries already built in
the checkout.

**Why.** README goal 4: minimal host dependencies and one command that
stands the system up. Keeping all "check and fix" logic in one place
lets the other crates assume their dependencies are present
(installer.md "Philosophy"). Downloads are pinned and verified: the
firmware and Cloud Hypervisor by sha256, and Rust and Bun at pinned
versions with their published checksums (security.md §9).

**Alternatives considered.** Distro packages (`.deb`, `.rpm`) and
prebuilt binaries. Installing from source is a stage, not a final
choice: Glidex is under active development, so hosts follow `main`.
Prebuilt binaries and distro packages are planned once it stabilizes.
Much of what the installer does is host configuration that a package
would also have to script: users and groups, units and the polkit rule,
file capabilities, the OVS profile, hugepages and boot-time VFIO
bindings.

**Consequences.** Each host needs a Rust toolchain and a build, unless
`--prebuilt` is used. OVS upgrades are left to the distro, because they
interrupt VM traffic. The installer never touches the firewall. See
[Installation](../operator-guide/installation.md).
